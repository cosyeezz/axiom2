# MCP 按需接入 · 第一步：会话内可控登记

**状态：第一步实施与验收方案，尚未实现到产品。** 本轮只写文档，不修改功能代码、不启动真实 MCP 或模型、不部署。核心机制已通过独立可行性验证；不等于下述工程验收已经完成。

## 1. 目标与边界

把已验证的“可控登记 → 原生工具就绪 → 原生调用”做成 Axiom 正式的会话宿主能力。

- **Axiom 决定何时连接；Pi 负责连接、握手、发现、工具注册与调用。**
- 服务配置已知、服务已授权，不等于服务已经激活。未激活时不启动进程、不发起网络连接。
- 连接归属对应 Pi 会话，不建立后台统一转发层，不跨会话共享活连接。
- 本步先提供程序内部可控入口；不接自动首次调用和工具目录缓存。
- 默认产品行为先保持兼容。工具目录尚未接好前，不全局关闭预连接，避免模型突然找不到工具。

### 本步不做

工作空间工具缓存格式/持久化、缓存占位工具、首次调用自动触发、Skill 发现投影、执行池身份/hash 调整、空闲回收、新前端面板、第三方扩展安装体系。后续步骤另行确认，不随本文自动获得实施授权。

## 2. 当前依据与 Pi 能力边界

核查基于当前安装的 **Pi 1.1.0**。实施前重核版本和源码，依赖升级须重新验证。

现有 [capability-resources.ts](../app/src/server/capability-resources.ts) 的 `capabilityExtensions()`：

1. 没有选中 MCP 时，直接跳过宿主集成。
2. `loadConfig` 返回全部选中服务，Pi 在 `session_start` 主动连接 enabled 服务。
3. `getMcpServers` 被包装成空列表，动态注册的服务无法进入这条原生集成路径。

可复用的公开接口与限制：

| 能力 | 实际语义 | 本步用法 |
| --- | --- | --- |
| `pi.registerMcpServer(name, config)` | 加载期登记在 session_start 连接；运行期登记异步触发连接；返回 void | 由宿主受控激活，不能 await 其返回值冒充就绪 |
| `pi.unregisterMcpServer(name)` | 移除动态登记，并触发原生工具撤回/连接关闭；返回 void | 撤销登记，不把方法返回当作传输已经关闭 |
| `pi.getMcpServers()` | 返回动态登记配置，不返回客户端或连接状态 | 保留会话内受控登记，不暴露未授权条目 |
| 传给原生 factory 的 `registerTool` 包装 | 原生登记工具时可观察定义；委托成功后注册表已刷新 | 建立“目标工具已登记”信号，仍须检查 generation、exposure 和调用过滤 |
| `ctx.executeTool()` | 通过当前工具注册表和原生管线执行、校验实参并运行调用钩子 | 验证原生调用可达；本步不增加缓存 stub 自动转交 |

还须遵守：

- `loadConfig` 中同 namespace 的条目优先于动态登记，**即使该配置 disabled 也会遮蔽动态服务**。待用配置不能作为同名占位塞进原生配置。
- `codemode`、`deferred`、`hidden` 是工具曝光方式，不是延迟连接开关。
- `mcp_servers_change` 没有结构化连接结果；不同 emit 可交错，同配置重复登记也不代表重连。因此事件处理结束不等于连接成功。
- 原生没有完整公开的连接状态订阅或 ready 句柄。内部 `McpServerConnection` 不作为持久方案深导入，不修改 node_modules。

## 3. 实现方案

### 3.1 分开可用配置与动态激活集合

在会话宿主内维护：

- **可用配置集合**：本会话按现有能力选择/授权规则允许使用的 MCP 配置。仅保存配置，不触发连接。
- **已激活集合**：当前登记给 Pi 的服务。只有这里的 enabled 服务才触发原生连接。

继续沿用当前 MCP 选择/授权边界，不把 Skill 引用、目录可见或工具名已知当作启动授权。未选中或已撤销授权的服务不能从内部入口绕过现有限制；仅撤销激活但仍获授权的服务，可在旧代际收尾后显式重新激活。不得向模型暴露命令、环境变量、凭据或完整连接配置。

控制器是会话 factory 内的轻量配置/生命周期协调对象，不持有另一个 MCP client，不代理 MCP 请求。原生 MCP 与工具观察包装保留在同一 factory/API 所有权下，避免跨扩展同名工具优先级造成遮蔽。

### 3.2 内部操作契约

以下为拟实现语义，不是声称已有这些 SDK API，也不是新增模型可调用工具：

| 操作 | 输入与职责 | 完成含义 |
| --- | --- | --- |
| 激活服务 | 服务身份；验证当前授权与配置 revision，合并同服务请求，再调用原生登记 | 受控登记已提交；不承诺已连接 |
| 等待目标工具 | 服务身份、完整原生工具名、调用 signal、就绪期限 | 当前 generation 的真实定义已登记且可通过会话调用过滤；不是工具执行成功 |
| 撤销服务 | 服务身份；使 generation 失效、拒绝相关等待者、撤销原生登记 | 登记和新调用已被撤销；关闭完成须另有观察证据 |
| 会话收尾 | 停止接受激活，拒绝等待者，执行/等待既有原生 shutdown 流程并清理观察资源 | 无旧代际工具重新放行，连接关闭过程已按宿主生命周期收尾 |

操作只接受可用配置集合中的身份，不允许调用者传任意 command、URL 或凭据。就绪期限作为宿主可配置参数，测试使用短期限；本步不把可行性测试的 250ms 写成产品默认值或性能承诺。

### 3.3 改造接入路径

1. 在现有能力宿主旁增加会话级控制模块，集中管理上述集合、pending 请求和 generation；具体文件名在实施时确定。
2. 原生 MCP 集成支持空初始激活集合。不要因为暂时没有连接就跳过安装，否则后续运行期登记无处理者。
3. 取消 `getMcpServers: () => []` 的硬遮蔽，改成只让本宿主拥有且当前获准的动态登记进入原生集成。保留现有 `registerCommand` 策略及 [modelToolTransport](../app/src/server/integrations/model-proxy-tools.ts) 传输适配。
4. 原生 `loadConfig` 不携带受控动态服务的同名条目，避免优先级遮蔽。配置读取/校验仍沿用当前来源，保留诊断、项目来源和 `autoEnableCodemode` 等设置，不为此再造 MCP 配置解析器，也不改变无效配置 reload 保留原基线的语义。
5. 包装原生 `registerTool`：先检查注册归属/代际并委托原始注册，再记录真实定义、检查实际可达性，最后释放对应目标工具等待者。优先使用会话公开的 callable 工具集合判断；`hidden`、被工具 allowlist 排除、未 active 的 direct 工具或已撤销的定义不能算就绪。
6. 如果需要包装原生事件 handler 观察尝试结束，只能用于清理或辅助检查；不能用一个全局“change 完成”信号解开所有服务的等待者。

就绪必须基于真实目标定义，不能凭名称已存在就成功；后续引入缓存 stub 时，stub 本身也不能被当作真实定义。名称/冲突哈希以 Pi 实际登记为准，不自行猜测命名规则。

**保留服务来源相关的传输契约：**Pi 动态登记会将 `source` 改为宿主 extensionPath、`scope` 改为 extension，不能假定原始 entry 元数据原样保留。当前传输适配依赖 `name + scope + source` 识别内置 REA，再执行组件环境准备并将 env 作为已解析的字面值。控制模块须按受控服务身份与 generation 保存原始 entry，在 `createTransport` 包装中为既有适配恢复必要的可信来源语义，或显式传递内置服务身份；不要通过伪造 Pi 扩展来源解决。尤其不能把 REA 的字面 `$`、`${...}` 或以 `!` 开头的值再次插值/当作命令执行。非内置同名服务不得冒充 REA。参见 [REA 资源来源](../app/src/server/integrations/rea-resources.ts) 与 [传输分支](../app/src/server/integrations/model-proxy-tools.ts)。

### 3.4 并发、取消和代际

- **单服务 single-flight**：相同会话、配置 revision 的并发激活合并，不重复登记/握手；不同服务不共用一个成功或失败信号。
- **调用取消只取消该等待者**：不因首个等待者取消而关闭其他调用正在等待的共享建连。会话关闭、服务撤销才拥有终止服务生命周期的权限。
- **generation 隔离**：会话 reload、配置替换、服务撤销均使旧 generation 失效。目标工具登记、超时、关闭和迟到回调都要检查所属 generation，旧结果不得改写当前状态。
- **失败有界**：连接失败、鉴权未完成、零工具或目标工具被移除时，不假装就绪；无法精确分类时返回脱敏的“目标工具未在期限内就绪”，不伪造根因。
- **显式重试**：相同配置再次 register 不保证重连。重试须协调旧登记撤销及旧连接收尾后再激活，不能自动重放可能已经执行的业务工具调用。

### 3.5 撤销和关闭

撤销时先禁止新调用、失效等待者，再驱动原生撤回/关闭。对于已经发出的调用，沿用 Pi 现有取消/关闭语义，不宣称可回滚服务端副作用。

原生注销返回 void，不能立刻标记“传输已关闭”。可在现有 `createTransport` 包装中记录该代际传输的创建与 `close()` 完成，或追踪可归属的原生生命周期处理 Promise；只观察，不重写协议。关闭证据无法归属当前代际时，不得结算成当前服务关闭成功。

会话收尾还要考虑尚未创建传输的 pending 激活：先使代际失效，阻止迟到登记，再执行既有 shutdown。等待器、计时器、监听器都须清理。不能仅依赖 `session.dispose()` 就假定原生 shutdown 事件已执行。

### 3.6 默认兼容策略

本步仍保留产品当前“选中的服务启动时预连接”的行为，但让它走同一套受控登记路径：加载期登记当前选中服务，由原生 session_start 建连。

测试宿主使用空初始激活集合，再显式调用内部激活入口验证按需路径。两种初始策略共用同一控制模块、同一个原生 MCP 集成及传输适配，不建设双客户端，也不新增面向用户的模式开关。

不得因本次重构改变 direct/deferred/codemode 曝光、现有工具过滤、能力选择和 reload 语义。工具缓存与自动触发接好以前，不切换生产默认策略。加载期连接不产生对应运行期 change 完成事件，就绪观察必须同时覆盖启动登记和动态登记。

## 5. 验收方案

### 5.1 分层测试

1. **控制器单元测试**：假配置/时钟/事件，检查授权、single-flight、generation、等待器与清理。
2. **Pi 原生集成测试**：真实 AgentSession + createMcpExtension + 原生客户端，内存假传输替代服务端。直接通过工具管线调用，不请求真实模型。记录 start、initialize、tools/list、tools/call、close 计数。
3. **Axiom 兼容回归**：现有 worker、能力选择及 reload 测试。本地模拟 HTTP 模型与模拟 stdio 服务可以使用，但属于 fixture 集成测试，**不是零请求/零子进程测试**；不得误连用户真实 MCP、模型或凭据。

内存测试应拒绝出网和子进程创建；fixture 集成测试仅放行受控回环地址及测试脚本。使用独立临时目录，绝不读取/覆盖用户实际 Pi 配置和凭据。测试结束检查关闭与清理，不能只看进程退出码。

### 5.2 必须通过的用例

| ID | 场景 | 验收断言 |
| --- | --- | --- |
| A01 | 可用服务存在，初始激活为空 | 宿主已安装；枚举可用配置不建连；start/initialize/list/call 均为 0 |
| A02 | 显式激活并等待目标 | 真实工具登记后才放行；原生调用返回预期结果；只有 1 次 initialize 和 tools/list |
| A03 | 同服务 10 路首次激活/等待 | 只建立 1 条连接；全部目标等待正确结算；后续业务调用仍使用该连接 |
| A04 | 两个不同服务交错连接，一成功一失败 | 成功服务可独立就绪；失败服务不借用他方信号，不发送业务调用 |
| A05 | 未授权/未选中/已撤销授权的服务 | 激活被拒绝，零新增连接；仅有 Skill 引用也不能启动；其他扩展在加载期或运行期登记均不能绕过现有选择约束 |
| A06 | 一个等待者取消，另一个仍等待 | 前者及时退出且不发送业务调用，后者成功；共享连接未因单个调用取消被关闭 |
| A07 | 连接失败、挂起、零工具、目标不存在 | 在规定期限内非成功结算；没有递归或错误业务调用；错误信息脱敏 |
| A08 | hidden、被工具过滤排除或未 active 的 direct 目标 | 即使原生登记了定义，也不报告为可调用；同名旧定义不能充当新代际的真实目标 |
| A09 | 撤销与配置替换发生在连接中 | 旧等待者失效；旧工具回调不使新代际就绪；旧超时/旧关闭完成迟到时不清除新工具、不结算新等待者、不覆盖新状态 |
| A10 | 已连接服务撤销 | 新调用被拒绝，原生工具被撤回；注销返回不冒充已关闭，最终有该代际 close 完成证据 |
| A11 | 传输创建前/建连中会话 shutdown 或 reload | 两阶段分别覆盖；无迟到工具重新放行；等待者结算；已创建传输关闭；shutdown 后拒绝新激活；无残留计时器/监听器 |
| A12 | 默认启动与 reload 兼容（分别断言） | 启动预连接及启动期就绪观察有效；direct/deferred/codemode 与 allowlist 行为保持；空配置 reload 新增、同名配置替换、旧连接清理均正确；待用条目不因同名 disabled 静态配置遮蔽而失效 |
| A13 | 配置或目录包含敏感字段 | 状态/错误/断言输出不泄漏环境变量、认证头、密钥及完整私有配置 |
| A14 | 失败后同 revision 显式重试 | 撤销旧登记并等旧代际 close 完成后，才创建新连接；重激活成功；仅显式业务调用执行一次，无自动重放；未创建传输的失败也可完成收尾并重试 |
| A15 | 动态登记后的内置 REA 传输契约 | 不启动真实 REA，以注入替身检查环境准备分支仍执行、env 字面值保持、原始来源身份不丢失，非内置同名服务不能进入内置分支 |

补充规则：重复激活失败服务不算“已重试成功”；测试禁止通过自动重放业务调用来掩盖不确定结果。A12 同时保留现有无效配置 reload 不覆盖已应用基线的断言。
