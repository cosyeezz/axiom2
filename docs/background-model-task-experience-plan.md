## 1. 状态与定稿范围

**方案定稿阶段状态：用户已确认体验要求和布局，查询承载对齐最新业务定案；当时底层组件与交互机制待讨论，尚未按本通用体验方案实施。**

**后续隔离实现：**用户之后明确授权在独立 Worktree 接入现有过程、错误和状态反馈，并要求不影响正常使用、子代理卡片不大改。该后续实现的具体接入点、隔离验证和未合并/未部署边界见[实现与接入说明](background-model-task-experience-implementation.md)。它不代表原技术草案中的通用执行器重构、查询子会话或新操作能力已获批准；本文其余未更新的状态描述保留方案定稿时间语义。

本方案固化本轮已确认的方向：**统一的任务与过程展示能力，配合一次性作业、多轮会话两种执行模式；卡片按业务归属就地展示，不把所有后台任务塞进聊天。**

方案定稿阶段仅整理方案及衔接文档，没有修改产品代码、调用真实业务模型、运行产品测试、迁移或清空数据、重启、提交或部署。用户对布局和要求的确认，不等于批准先前技术草案中的具体字段、接口、调度方案或服务拆分。

**后续范围收敛：**用户明确排除 Codemode 等**工具内部模型调用**，本轮不调整其执行、事件/历史投影、错误、产物或费用展示，也不新增该场景的验收任务。第5.6节仅保留排除说明；原盘点事实不因此被否定。

**已有能力边界：**普通任务的 `delegate`、`cancel`、`append`、`read_result` 沿用现有输入/返回契约、权限、操作目标及生命周期语义。本方案补充真实过程、错误和状态反馈，不重设计这些能力；接入观察/展示可能修改相关代码，不代表改变其使用方式。其他业务不因共享卡片就自动获得委派、取消或追加能力；新增能力或改变规则须另行讨论确认。

**并行业务变更对齐：**[最新记忆业务定案](memory-refactor/purpose-flow-coverage.md)已选择直接 `memory_query({ question })`、同步工具返回，替代先前的查询子代理承载示例。因此记忆查询保留原工具卡和已有处理记录，不依赖委派、通知、`read_result` 或新增查询业务卡。实时过程和错误要求不变；本方案不重新决定查询接口，也不把通用组件改造设为现有查询的前置依赖。

## 2. 要解决的问题

后台有队列，只解决了“何时获得执行机会”，没有充分解决以下问题：

- 用户不知道任务是在等资源、准备材料、请求模型，还是校验、保存和应用结果。
- 部分错误需要任务结束后进入深层记录才能发现，甚至被吞掉或被外层成功掩盖。
- 后台任务分散在不同入口，离开相关面板后难以发现异常。
- 执行结束、业务结果生效和通知送达容易被合并成一个“完成”。

目标不是为了统一而把所有业务变成普通子代理，而是让用户在正确位置实时回答：**什么任务、为什么运行、正在做什么、哪里出错、什么结果仍然有效、可以做什么。**

## 3. 两种执行模式

| 模式 | 含义 | 适用场景 |
| --- | --- | --- |
| 一次性作业型 | 输入和业务范围确定，由程序控制执行步骤，输出后经过业务校验及保存/提交/应用 | 标题生成、直接工具式记忆查询、受控记忆整理与批量分类、原生上下文压缩 |
| 多轮会话型 | 给定目标，模型根据中间结果继续调用允许的工具、读取材料，直至交付 | 普通研究/分析/测试；其他确需独立会话的业务另行确认 |

边界：

1. **一次性作业不等于只发一次模型请求。**一个整理批次、一次工具查询或原生压缩内部可以有多步和多个调用，仍是一项有明确输入和结束边界的作业。程序逐层导航并请求模型，不因此等同于独立 AgentSession。
2. **多轮会话不等于允许用户任意追加或改写。**多轮可以仅发生在模型与受控工具之间；是否接受追加、重试或恢复由业务规则决定。
3. 执行模式不决定业务权限、模型用途和卡片位置；不能因为切成会话型就继承普通研究任务的 Shell、提示词、预算或报告限制。
4. 两种模式都必须有实时过程与错误反馈。一次性任务不能只剩最终成功/失败，多轮任务也不能只展示最终报告。
5. 主会话自身的记忆维护、自动续接保留主执行过程，不再造第三种通用执行器；工具内部模型调用不属于本轮接入范围。
6. 压缩继续使用原生压缩及安全应用流程；上述模式划分不把原生压缩改成自由文本摘要聊天。

## 4. 卡片位置总表

**执行模式决定怎么执行，业务归属和发起位置决定在哪里展示。**

| 场景 | 主要展示位置 | 关联入口与去重要求 |
| --- | --- | --- |
| 会话发起的研究、分析、测试 | 会话中对应委派调用的任务卡 | 可展开子会话和真实执行过程；不另建一张独立后台副本 |
| 直接 `memory_query` 记忆查询 | 会话内原查询工具卡，关联已有处理记录 | 同步返回结果，原位补过程/错误；不新增专门查询业务卡或子会话 |
| 会话自身记忆维护、自动续跑 | 原主会话执行过程 | 标明触发原因及实际工具过程，不伪造一次子任务委派 |
| 手动或自动压缩 | 现有压缩面板内、对应压缩卡片 | 原位补充过程和错误；不再往聊天插一张重复卡 |
| 后台记忆整理、目的批量分类 | “全局记忆”面板内，当前工作空间视图顶部、目录/记忆树上方 | 全局记忆入口显示运行/异常状态；完成批次进入原有处理记录 |
| 会话标题生成 | 会话标题附近或会话顶部的轻量状态入口 | 点击展开过程卡；成功收起，失败保留入口；不为每次尝试增加聊天消息 |

同一次执行可以有多个导航入口，但应指向同一事实记录；**不能重复创建任务、复制状态源或累计费用**。

## 5. 各场景布局与行为

### 5.1 会话发起的任务与查询

- 研究/分析/测试卡跟随原委派调用，保留与当前问题的上下文关系；需要详情时打开原执行会话及工具过程。
- 使用真实业务名称，不全部写成无区别的“子代理协作”，也不为统一外观强制创建新任务。
- `memory_query` 保留直接工具调用，在原工具卡和已有处理记录中查看实际查询阶段、耗时、结果与错误；同步返回，不新增查询业务卡或子会话。
- 所有入口均实时展示实际阶段和异常。对委派任务，结果已保存、通知待送达、结果已读取可以分别呈现；直接工具查询不强行套用这条委派交付链。
- 查看、展开和刷新不触发重跑；完整已保存结果不因卡片摘要长度而被截断。

### 5.2 会话自身的维护与续跑

- 保留在原主会话过程里，不将同一次主会话执行包装为另一个后台代理。
- 执行状态以任务是否正常进行、是否需要用户干预为准；不常驻展示“手动继续执行”“任务结果通知后续跑”等不可操作的内部触发来源，也不新增替代提示。内部来源保留用于溯源，真正中断时仍显示原重试入口。
- 提醒已送达不等于记忆已更新，自动续跑开始也不等于用户目标已经完成。

### 5.3 压缩

- 使用现有压缩入口和详情区域，在对应卡片内展示本次压缩进程。
- 区分准备快照、生成摘要、校验/等待应用、应用完成；仅展示真实存在的阶段。
- **摘要生成成功但未应用，不能标为压缩成功。**修订或分支冲突应显示未应用及原因，保留产物和已发生费用。
- 取消、失败、中断保留可查记录；不能用普通任务报告替代原生压缩产物与安全应用规则。

### 5.4 后台记忆整理与批量分类

这是工作空间级索引维护，一次批次可能包含多个来源会话的已完成目的，不能挂到恰好正在查看的会话下面。

**主位置：现有“全局记忆”面板 → 当前工作空间 → 目录/记忆树上方。**

展示分为两层：

1. **队列摘要：**待整理数量、当前是否有活动批次、可确认的等待原因。等待批次触发与等待执行资源不能混为一谈；不知道排队位置或预计耗时时，不编造数值。
2. **活动批次卡：**本批范围/数量、实际模型、当前阶段、已运行时间、结果或错误摘要，展开查看真实过程。停止、重试等操作只有业务允许时才出现。

布局示意（数字仅为示例，不另行规定批次、预算或触发参数）：

```text
全局记忆 · 当前工作空间

记忆整理    待整理 23 个目的 · 当前批次运行中
┌ 批量分类 · 50 个目的 ─────────────────┐
│ 当前阶段：校验分类结果                │
│ 已运行：18 秒                        │
│ [展开执行过程]                       │
└──────────────────────────────────────┘

分类目录 / 记忆树
```

异常和历史行为：

- 原活动卡立即显示失败阶段、具体原因以及本批是否发布；不只是给失败计数加一。
- 批次未提交不影响此前已发布内容的事实；若整体过程存在部分提交，明确范围，不笼统声称全部成功或全部回滚。
- 完成批次收进已有处理记录，主区域不无限堆积大卡；错误仍可定位和查看。
- “全局记忆”按钮显示运行/异常状态角标，面板关闭时也能发现问题；打开后能定位相关工作空间和批次，不要求用户先翻历史日志。
- 来源会话可提供关联目的的已入队/已整理状态或跳转入口，但不重复铺开跨会话批次，也不把整理结果当作当前会话的模型回复。

分类规则、入队/批处理参数和目的索引业务约束继续由[目的索引要求](memory-refactor/purpose-flow-coverage.md)维护，本方案不另造整理流程。

### 5.5 标题生成

- 归属会话，使用标题附近或会话顶部的轻量入口；不是独立聊天消息。
- 生成中显示状态，点击展开同款过程详情；同一执行及其尝试保留关联，不为每次尝试插入大卡。
- 成功后更新标题并收起过程，历史仍可查看；失败保留原/兜底标题以及可展开的异常入口。
- 无需生成是正常跳过；用户手动改名优先，执行结果被取代不伪装成模型失败。
- 非致命失败不打断主聊天，不为解释标题错误再唤醒主模型，也不反复弹窗制造噪音。

### 5.6 工具内部模型子调用（本轮排除）

用户后续明确不处理本场景。原工具和内部模型调用保持现有行为，本轮不做子调用接入、事件/历史投影、嵌套错误、产物或统计展示改造；此前相关建议不再构成本轮需求、接入缺口或验收项。

## 6. 共用展示能力

### 6.1 摘要与详情分层

| 层次 | 展示要求 |
| --- | --- |
| 收起的卡片或轻量入口 | 业务名称、状态、真实阶段、必要归属/触发来源、耗时、结果或错误摘要；可取得时显示实际模型及用量 |
| 展开的执行过程 | 准备、模型请求、工具/读取、校验和提交事件，保留先后关系及必要诊断；无该步骤时不伪造 |
| 按需查看的详情 | 授权可见的输入、输出、来源关联、业务产物、原始费用事实和错误详情；脱敏并明确截断 |

卡片外观和共用能力一致，不要求所有业务使用同一个详情页面。委派任务继续进入原执行会话，直接查询留原工具卡并关联处理记录，压缩进入压缩详情，后台整理可进入已有处理记录。

### 6.2 阶段与状态

共同阶段语义可表达为：

```text
排队 → 准备 → 模型请求 → 工具/业务处理 → 校验 → 保存/提交/应用 → 终态
```

这不是要求每个任务强行走全套阶段，也不是已定稿的程序状态枚举：

- 阶段来自真实程序和执行事件，不由模型自报百分比生成。
- 模型调用代码已进入，不等于供应商确认受理；没有证据不能显示更强的事实。
- 状态区分执行、业务结果及交付；不能把原有中断、失效、不确定等原因全部压成一个失败。
- 已请求停止与已停止、已生成与已应用、已保存与已通知分别表达。
- 过程展示不要求获取或暴露模型私有推理；真实工具过程、可公开输出和诊断已经足够。

## 7. 实时错误与结果反馈

### 7.1 错误不等任务结束才出现

- 错误一旦由程序确认，就更新原卡片和相关状态入口，不等整个队列完成或用户打开历史记录。
- 用户能知道哪个业务、哪个阶段、发生什么、影响什么、已有产物或提交是否仍有效，以及有哪些被允许的操作。
- 区分排队/准备、配置/权限、模型/供应商、输出/读取、校验/提交、取消/中断等原因；不以模糊“执行失败”代替全部信息。
- 非致命不等于静默，失败也可能已发生费用；未知费用不显示为零。

### 7.2 不把业务结果误报为错误，也不把错误伪装为空结果

| 场景 | 应表达的事实 |
| --- | --- |
| 查询无相关目录、目的命中但无有效依据 | 是不同业务结果，不等同于模型或读取失败 |
| 关键资料缺失但有部分依据 | 明确不完整及缺失影响，可保留有效部分 |
| 压缩摘要已生成但应用冲突 | 产物保留，本次未应用，不显示已完成压缩 |
| 整理批次失败或部分提交 | 标明本批及已提交范围，不抹去此前已发布结果 |
| 标题被手动改名取代 | 保留新标题，记录未应用/被取代，不伪造供应商错误 |
| 结果有效但通知失败/不确定 | 结果与交付状态分开，不因此改写业务结论 |

### 7.3 通知与操作边界

- 页面或面板关闭时，相关入口仍能反映运行或异常；不为每次阶段变化弹窗。
- 异常可查看、可操作与自动重试是不同概念。沿用所属业务已有的取消、重试、追加或恢复能力及其授权/阶段规则，不为统一外观新增操作；卡片只展示当前真实可用的操作。
- 不通过重复发送来探测未知状态，不自动重放不确定的模型请求、脚本、批次或通知。
- 多入口引用同一执行事实；角标、卡片和详情不能各自维持互不一致的“完成状态”。

## 8. 实时、历史与复用约束

以下确定体验与复用边界，不在此指定新的事件或存储协议：

1. 运行中实时更新状态、实际阶段和错误，不能只在终态回看；具体订阅和推送机制下一轮讨论。
2. 刷新、重新打开或断线重连后可取得可验证的状态和已有结果；仍无法确认时明确未知/中断，不假装恢复成功。
3. 摘要与大体量输入输出分层读取，详情按需授权访问；不向公共日志、通知或所有订阅者广播敏感正文。
4. 查看卡片、展开记录、刷新页面是只读行为，不隐式调用模型、重跑任务或重新应用产物。
5. 继续复用现有任务、处理记录、执行资源、原生压缩及用量能力；不平行新建执行池、业务队列或第三套任务数据库，也不为此额外建设一个独立“总后台任务页”。
6. 卡片和入口是已有事实的展示，不是新的模型调用或账源。同一调用只计一次，实际模型身份和费用未知事实保留。
7. 不为所有业务强制一个 runner、一个模型或相同工具和操作。普通研究任务的提示词、Shell、报告限制和预算总结不成为全业务默认。
8. 原生压缩安全、工作空间/会话归属、业务提交、结果保存与通知等可靠性边界不因换卡片被削弱；其具体接入和实现仍待设计。

## 9. 后续体验验收清单

以下是未来实现应满足的验收要求，**本轮只验证文档，不宣称产品已通过**：

- [ ] 一次性作业和多轮会话都能在运行中看到真实阶段及错误，而不只看到排队和终态。
- [ ] 研究/分析/测试卡跟随原委派位置，展开的是对应执行；完整已保存报告仍可读取。
- [ ] `memory_query` 保留直接同步工具，在原工具卡/处理记录查看实时过程和错误；不新增查询业务卡、子会话或委派依赖。
- [ ] 主会话维护/续跑有真实来源说明，不出现伪造的第二份子任务。
- [ ] 压缩原位展示生成、校验及应用；生成成功但未应用不显示为完成。
- [ ] 整理卡位于全局记忆当前工作空间的树/目录上方，队列与活动批次可辨，不挂错来源会话。
- [ ] 关闭全局记忆面板仍能从入口发现运行/异常，打开能定位；历史批次进入原处理记录。
- [ ] 整理失败能说明提交范围和已有内容影响，不只展示一个累计失败数。
- [ ] 标题生成使用轻量会话入口，成功收起，失败保留可查记录；不刷聊天消息，不覆盖手动改名。
- [ ] 普通委派任务的 delegate/cancel/append/read_result 契约、权限及生命周期语义不变；其他业务不因共享卡片自动获得这些操作。
- [ ] 多入口、刷新及重连看到一致且可验证的事实；未知状态明确，不自动重放请求。
- [ ] 按业务能力提供操作，停止请求与生效可辨；查看或展开不会触发执行。
- [ ] 展示执行、业务结果和交付区别；同一次执行及调用不重复创建、重复计费。
