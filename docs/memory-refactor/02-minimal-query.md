# 第二阶段草案：最小加载与查询答案

## 状态与目标

**状态：目标已按用户反馈澄清；实施方案仍为草案，未批准。第一阶段原范围实现及隔离验收已完成；用户进一步将“按目的组织主题”的上游工作归入[第一阶段补充](01-purpose-organization.md)，先确认整理结构，再推进本阶段读取与回答。**

目标：沿历史记忆中已有的导航路径和详情，直接取得可复用的现成结果，避免主会话重新探索。查询者可以直接问需要的东西，不必先知道记忆中的路径或来源。按需读取是实现手段，不是让查询者审阅证据或检索过程。

例如，提问“系统提示词在哪里”，查询内部定位相关记忆并读取必要详情后，只返回已记录的系统提示词文件位置及必要的入口说明，不附记忆来源、引用编号、来源会话或检索流水。目标文件路径是答案本身，不属于应省略的来源引用。

可复用结果不只包括最终成功答案，也包括文件或入口路径、实施方案、具体做法、失败尝试及其限制。失败方案应在整合结果中直接说明，例如“该路径在某版本或条件下已尝试不可用，原因是……；可采用的替代方案是……”。仅在历史记录有依据时给出原因和替代方案，不编造缺失信息，不把一次或特定条件下的失败扩大成永久不可用。省略的是来源引用，不是影响选择的关键条件、失败经验或必要分歧。

前置条件：承接第一阶段“同源更新、相同合并、不同共存”的历史经验整理机制，不依赖已被放弃的全面失效门禁。历史结果使用前仍需结合实际核对；查询不承担全面核验当前项目状态的职责。

## 用户明确的查询路径

以记忆文件中已经记录的“目的”为导航依据，提取目的目录。一个会话后续可以追加多个目的，不能强制把整个会话压成唯一主题。

查询路径：**直接提问 → 匹配目的目录 → 读取命中目的对应的任务过程与详情 → 汇总相关现成结果。**

- 目录回答“历史上做过什么”，只负责找到相关工作，不要求目录本身装下全部答案。
- 命中目的后再读取相关过程与详情，从中取得位置、方案、做法、结果和失败经验；过程用于理解和总结，不原样倾倒给查询者。
- 按问题汇总必要结果，不附记忆来源引用。不同目的涉及同一问题时，可以合并相关结果并保留不同条件。
- 用户可以直接问具体需要，不必先知道目的的原文或记忆路径；匹配不能退化成标题字面相等。

## 拟定范围

- 围绕现有目的和任务详情建立导航与查询链路，支持同会话多个目的。
- 读取命中目的所需的过程和详情，避免默认展开无关目的的全部资料。
- 区分无关资料读取失败、关键结果缺失、执行失败与真正无命中。
- 查询答案直接包含相关成功结果和失败经验，内部导航关联不外露。

优先复用现有记忆结构，不预设新的段落索引、修订绑定片段存储或复杂逐段取证系统。目的目录如何与现有Topic/Section及整理记录衔接，需要核对当前代码后确定，不将用户方向直接解释为重建存储。

不做原文自动迁移或全局UI改版；保留只读、工作空间隔离、无原始聊天回查等边界。

## 实施步骤草案

1. 核对现有目的、任务标题、详情关联与整理查询代码，明确如何复用已有结构形成目的目录；暂不假定存在专门的多目的字段。
2. 支持从目录命中相关目的，再读取对应过程与详情，而非默认加载整个会话或所有分支。
3. 将相关路径、方案、成功结果和失败限制汇总为直接答案；保留必要条件与分歧，不附来源和检索流水。
4. 用多目的会话、具体问题匹配宽泛目的、相关失败方案、无关大资料和坏链接等夹具验证；保持读取权限和隔离边界。
5. 记录实际读取量、请求量及返回长度，检查是否存在重复读取或无界扩展，不在未测量前承诺提升比例。

旧草案中的强制段落定位、复杂多轮取证设计不再作为必做项。只有实际代码和验证表明有必要时，才提出最小补充方案。

## 实施前待核对

- 目的目录与现有Topic/Section的对应关系，以及同会话新增目的如何被整理更新。
- 目的到相关过程、详情的现有定位能力；旧记忆没有明确目的时的兼容方式。
- 目的较宽时如何命中具体问题、材料过大时如何按任务详情继续读取，避免漏掉现成答案或无限加载。
- 真实模型评估需要另行授权；在授权前只能证明读取和返回契约，不能证明语义质量达标。

## 验收

- 同一会话包含多个目的时，目录能表达各目的；查询命中相关目的并读取其过程与详情，不自动加载其他目的的全部资料。
- 直接问具体所需内容时，无需使用目录目的原文，仍能进入相关目的取得结果。
- 查询端口时不读取同源无关大报告，断言实际读取记录和模型请求内容。
- 无关坏链接不导致已有充分依据的查询失败。
- 必要二级引用可以按需读到；循环引用不会无限展开。
- 关键证据缺失明确不完整，不以成功空答案掩盖读取失败。
- 如使用片段定位，源修订变化时不得把旧定位应用于新正文；不以此引入全面历史失效核验。
- 同一条件的重复结论不因多来源重复输出；必要限制和冲突不丢失。
- 历史存在失败路径或方案且与当前问题相关时，将不可用结论、已知原因及适用条件整合进答案；有依据的替代方案一并返回，不只提取成功结果，也不把局部失败泛化。
- 问“系统提示词在哪里”时，返回已有定位中的目标文件路径及必要入口信息，不附来源会话、记忆文件引用或检索过程；目标路径不得被误当作引用删除。
- 工具正文不附记忆来源引用或审计元数据；内部诊断与面向查询者的答案分离。
- 记录改造前后的读取字符/字节、请求输入量、模型调用次数、耗时与答案长度；数值目标在本阶段确认时填写，不伪造提升比例。

## 风险与恢复

过细筛选可能漏掉决定性上下文，应保留按需扩展和明确不确定性；不能以恢复“读取所有文件”作为默认降级。请求失败沿用可选记忆语义，不阻断主任务。旧存储格式需有明确适配；不修改原文实现定位。

## 确认与执行记录

- 用户已明确查询目标：找到历史已有路径，取得现成结果，不需要知道结果来自哪里；可直接提问需要的东西。典型例子是查询系统提示词的位置，答案直接给位置。
- 用户补充：需要的结果也包括路径、方案等；失败方案可整合为“这个路径不可用”等结论。查询应复用正反两类经验，保留影响判断的条件，不要求来源说明。
- 用户进一步明确：记忆已有目的，后续会追加多个目的；提取目的形成目录，命中后读取相关过程并总结。第二阶段据此收敛为“目的目录→相关过程与详情→现成结果”，不再以复杂逐段取证为默认路线。
- 上述澄清不等于批准存储重构、预算或代码实施；不据此删除用于内部导航、整理和更新的来源关联。
- 实施步骤和预算定案：待结合当前代码提出简单、低维护成本的方案后确认。
- 实际变更：仅更新本阶段讨论文档，尚未修改查询代码、运行实现测试或部署。
- 阶段交付后：回写事实，再讨论第三阶段，不自动继续。
