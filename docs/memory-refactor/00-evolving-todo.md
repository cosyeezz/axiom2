# 第零阶段：用一份可演进的 todo 记录会话工作

[返回总路线](README.md)

## 1. 状态与用途

**状态：当前理解的讨论基线，已获授权写入文档，未获授权实施。**

用户要求先把这一理解作为第零阶段保存，之后基于文档继续讨论，避免上下文压缩造成语义损失。本文不是已经定案的完整技术方案，也不是现有功能说明。

第零阶段先讨论基本原理。原第一至第六阶段保留为审查后的旧方案，不能直接按原顺序开始实施；需要结合本阶段讨论结果重新评估。

## 2. 用户的核心想法

核心原理应简单，避免因为机制复杂而增加维护成本和出错概率。

对于一个会话，最重要的是：**做过什么，接下来要做什么。**

记忆最初可以是空文档。模型通过语义理解知道自己要做什么后，开始写预计步骤，也就是 todo list。它可以像技术文档一样先形成背景、探索、方案、测试等大章节，再逐渐展开；章节只是示例，不是每个会话必填的固定模板。

计划不要求一开始就完整，也不必先把章节顺序排死，但总脉络要清楚：可以先探索、再决定，先列大框架，再在实践中逐渐丰满。大章节下面允许展开，展开力度要控制，不能无限细分。

用户进一步明确：叶子项不必是能够独立交付的任务，也可以是第一次尝试、第二次尝试这样的一段推进。主清单简述探索了什么、得到什么结果；具体访问哪里、怎样操作等放在详情文档。用户先提出详情起止行，随后认可主体方向，并进一步提出由程序生成序号、通过起止标记管理关联，主项只写编号，不写详情路径或定位说明。具体拆分原则和编号协议见下文建议，尚未授权实施。

执行允许试错。方案做了一半发现不行，可以换方案；这些变化应留下简短记录，例如“尝试了什么，因为何种原因失败”。不需要逐字保存所有过程。

用户首先强调应详细沉淀经过尝试得到、后续可能复用的结果，随后补充具体探索过程可放详情文档。最终清单可以很长，每一项都有具体内容，说明做过的尝试，对错都可以保留。错误尝试可以划掉，表示已经做过，但不能继续按这条路推进。

## 3. 当前理解：同一份清单，既是计划也是简要记录

**不是在 todo 之外另建一套过程系统，而是让 todo 本身承载必要过程。**

- 没做的部分是计划，说明准备做什么。
- 正在做的部分说明当前停点和接下来要做什么。
- 做过的部分留下简短行为、原因或结果。
- 走不通的尝试划掉而不删除，留下换路原因。
- 新理解、新步骤直接补入清单，原框架可以调整、拆分和细化。
- 可复用成果，以及接续、排错、核验所需的关键细节，放入相关详情；不要求每个小项独立创建文件。并非只有最终成功的结果才值得详记。

被划掉的旧方案、简短原因和新增事项，本身就能表达计划如何变化，不再额外维护一套“计划变更记录”。这也不是原始聊天记录或工具日志的复制。

## 4. 清单如何逐渐长出来

以下仅为表达形式示例，不代表项目实际执行记录，也不预先锁定机器字段、Markdown解析方式或UI样式。

### 开始时：只有粗框架

- 探索现有实现。
- 确定修改方案。
- 实施并验证。

### 执行中：补充尝试、结果和下一步

- ✓ **探索现有实现**
  - 发现重复读取发生在查询阶段，而不是文件扫描阶段。
- **确定修改方案**
  - ~~尝试缓存整个文件~~
    - 已尝试，但当前做法在文件变化后容易继续使用旧内容，放弃该做法。
  - ✓ **尝试只读取命中的段落**
    - 小范围验证可行，决定沿这个方向继续。
- **实施并验证**
  - ✓ 完成段落读取。
  - → 正在处理引用文档。
  - ○ 补充异常情况测试。

这里没有抹掉失败尝试，也没有因为一个子项已完成就宣布整个任务完成。粗框架随着实际工作逐渐变得具体。

### 形成成果后：保留可复用结论与必要详情

- ✓ **确定引用文档的读取规则**
  - 结果：只加载当前事项明确需要的引用，不展开整个目录。
  - 如需复用详细规则和验证依据，再关联相应文档。

普通尝试用一两句话记录即可，不必都写成长文。此前用户提出已完成内容可以归档、展示和按需查询；这一方向保留，但具体归档方式和查询机制尚未讨论定案。

## 5. 章节展开和叶子项的粒度（设计建议，待讨论）

### 5.1 章节负责组织，叶子负责表达具体推进

同一份主文档可用章节和嵌套列表组织，不增加不同层级对应的独立系统。章节说明这一组事项围绕什么问题；叶子说明具体推进了什么。无须强制每章都有相同深度。

建议的停止拆分原则：

> 一项已经能清楚说出“针对什么问题，做了或准备做什么，得到了什么结果或停在哪里”，就可以作为叶子，不再为了记录操作步骤继续拆分。

“有意义的推进”可以是验证一个猜想、尝试一种方案、排除一个原因、完成一处修改，或获得决定下一步所需的信息。它不必独立交付，也不必成功；一次尝试可以涉及多个工具操作。

- 有不同的探索问题、方案尝试或需要分别说明的结果时，才值得拆子项。
- 读取文件、运行命令、重复点击、同一方法下的常规重试，默认属于该项的过程，不各自建一层。
- 第一次和第二次尝试如果方法、条件或结论有意义地不同，可以列为同级叶子；只重复同一操作则在详情中概述。
- 不把任意操作都命名为“尝试”来规避粒度原则；也不强制固定两层或三层。出现连续空泛父标题、没有新增工作含义的缩进时，应合并或展平。
- 细节太多时转入详情，不靠继续增加层级容纳。

章节顺序用于表达脉络，不等于严格执行顺序。有必要的前置条件用一句话注明，例如“待方案确认后实施”，不引入额外依赖系统。父项是否完成看目标是否达成，不能因一个子项完成或失败项被划掉就自动宣告完成。

### 5.2 示例：主文档保留工作脉络

以下仍是虚构示例；〔17〕等表示拟由程序生成的详情编号，不是列表顺序号，不对应实际记录，也不表示已支持这种读取能力。

```text
# 查询问题排查

## 背景与目标
定位为什么一个无关引用会影响查询，确定最小修改方案。

## 探索
### 引用加载行为
- ~~第一次尝试：删除整个测试目录~~ 〔17〕
  结果：先触发入口缺失，无法验证引用行为；放弃这个实验做法。
- ✓ 第二次尝试：只删除单份引用 〔18〕
  结果：保留入口后仍复现失败，问题范围缩小到引用加载。
- → 验证该引用与当前问题无关时是否仍会失败
  当前：已准备独立样例，尚未运行。

## 方案
- ○ 根据探索结果确定最小修改范围。

## 验证
- ○ 补充回归用例；修复验证在相应修改完成后运行。
```

## 6. 详情内容与按段定位（设计建议，待讨论）

### 6.1 详情保留什么

详情用于解释主文档里的事项，不在其中再维护第二套进度清单。按实际需要记录：

- 探索对象、关键资料或访问地址，以及使用的方法。
- 关键读取/修改文件、脚本、命令及复现必要的条件；明确区分阅读、执行与修改。
- 出错的操作和诊断必要的错误片段，失败原因及换路理由；原因未知时明确写未确认。
- 关键发现、验证结果、产物位置和未确认部分。

不要求每项填满字段，不复制所有日志或原始对话，不记录无关操作。详情应在推进中按需记录，而不是等最终成功才补写。短过程仍可直接附在主项下面，只有具体过程较多时才移入详情；多个相关尝试可共用一个详情文档。

### 6.2 关联方式：程序生成编号＋详情起止标记

**最新方向：程序负责关联，模型负责语义内容。** 这替代此前让主项维护“文件＋小节标题＋起止行”的建议。行范围仍可由程序内部计算，但不再由模型填写或维护。

主项只保留简短编号，如 `〔18〕`。详情用相同编号的起止标记包住一段内容。以下仅为拟议格式示例，不是已实现协议：

```markdown
<!-- detail:18:start -->
### 单份引用实验

对象与方法：保留入口，只删除一份引用文档。
关键操作、命令和错误：按实际需要记录。
结果：实验复现了失败；进一步因果判断仍需验证。
<!-- detail:18:end -->
```

模型通过受控写入入口提交主项摘要及详情内容；程序分配编号、生成边界、维护主项引用。模型不用数行号、拼路径或自行编造编号。需要详情时，向读取入口提供编号，由程序返回对应块内容；具体接口形态另行讨论，不假称已有工具。

建议先采用最小规则：

1. **编号是身份，不是顺序。** 由程序持久分配，会话内唯一，不随事项排序、章节调整或划掉而改变；已使用编号不回收复用。跨会话读取时，程序同时携带所属会话，不能将两个会话的同号块混淆。
2. **只在需要详情时关联。** 不强制所有章节和todo都有编号。一个详情编号对应一个明确的块，多个块可放在同一文档，不要求一项一文件。
3. **边界由程序管理。** 同号起止成对且不可嵌套或重叠，保留标记语法不能混作正文。程序校验重复编号、缺失边界和无效引用；异常时返回明确错误，不猜测范围、不返回整份文档兜底。
4. **位置可变，关联不变。** 程序从块标记计算编号对应的文件与区间；任何位置缓存必须跟随文件修订校验或重建，不能拿旧偏移直接读。映射可从文件重建，不要求模型再维护一张映射表或另建独立索引服务。
5. **写入不得留下假成功。** 编号分配需避免并发冲突；主项引用与详情均可用才报告关联成功，失败不能留下指向其他内容的编号。外部编辑损坏标记时可检测并报告，但不承诺自动修复或所有写入路径已经受控。

阅读时程序可以扫描或解析必要的文件来定位，返回给模型的仍只应是目标详情块，不将完整文档放进上下文。编号解决定位问题，不会自动证明内容正确或主项摘要仍与详情一致；实质结论变化时仍需同步主项。

以上是拟议的轻量程序职责，不增加关系图或第二套任务状态。是否采用此标记语法、主项写入怎样受控、详情如何分文件以及损坏恢复方式，需后续确定最小实现；本轮不实现代码。

### 6.3 最小实现入口：一个小工具，而不是一套新系统（建议）

用户追问是否需要新工具。本轮只读核对当前代码：[memory-tool.ts](../../app/src/server/memory-tool.ts)暴露的`memory_query`按Topic和问题返回归纳答案，不承担按编号读写；[agent-worker.ts](../../app/src/server/agent-worker.ts)对通用`edit/write`的记忆操作有归属校验，但未实现编号块协议；[memories.ts](../../app/src/server/memories.ts)已有带修订校验的已有文件保存入口，可评估复用其安全检查，不能认为已具备新文件创建或多文件关联写入能力。

推荐新增一个薄的本地记忆记录工具，内部调用同一套文件/编号处理逻辑，不新增MCP服务、不调用额外模型。暂以`memory_record`作示意名，尚未决定正式接口或实现：

- **保存**：提交指定主项/插入位置、事项简述和详情。新详情由程序分号；已有详情按原编号更新。程序维护块标记和主项编号引用。首次写入位置必须明确，不能让程序凭语义猜测放在哪一章。
- **读取**：提交编号，程序校验归属并返回相应块，不进行语义检索或模型归纳。

保存中的新增/修改可以是同一操作，不必为分号、建块、改块、挂引用各暴露一个工具。主文档的章节组织仍可沿用普通文件编辑，但受管理引用不能随意重编号；是否限制通用编辑改动受管区域、如何检测外部改坏，须在实施前明确。主体位置定位、修订冲突和关联写入失败恢复也仍需细化，不能以“新增一个工具”代替这些校验。

备选是通过现有bash调用脚本，或改造通用read/edit/write来处理这些标记；它们技术上也能提供程序入口，但前者让调用约定散落在命令里，后者扩大通用工具的隐含行为。现阶段不推荐仅靠提示词让模型手写编号，也不建议把精确记录操作塞入现有语义查询工具。新增的是一个明确的调用入口，主要逻辑仍是编号、块读写与引用校验。

## 7. 保持简单的边界

### 本阶段不引入

- 独立的关系图、事件溯源或转折管理系统。
- 需要模型同时维护的多套计划、过程和记忆摘要。
- 每次工具调用对应一个todo、每个小项对应一个文件的硬性要求。
- 开始工作前必须规划出全部细节的要求。
- 全量聊天、工具输出或逐步推理的存储要求。

先前提出的“任务层／过程层／知识层”和“可恢复工作现场”等多层设计未获用户认可，不应换个名称重新夹带进本方案。

### 一个轻量补充建议，仍可讨论

划掉失败尝试时，写清失败原因及必要条件，而不是只写“方案错误”。例如“当前环境缺少某依赖，未能运行”，不能被后续模型理解为方法永远无效。

成功完成与失败放弃应在表达上有所区别。以上可以通过简短文字实现，不意味着需要增加复杂状态系统。具体状态和显示符号尚未定案。

## 8. 后续讨论的问题，不在本轮代替用户决定

1. 是否采用“有意义的一段推进”作为叶子粒度，以及章节展开的停止原则？
2. 主项的最少内容是否可收敛为事项、状态及结果/停点，需要时附详情定位？
3. 是否采用一个本地记录工具提供保存/读取两种操作？主体位置如何指定，受管区域编辑和关联写入失败如何处理？具体编号格式及异常提示仍待定。
4. 清单变长后，已完成内容如何归档、展示和按需读取，既保留脉络又不全部塞入上下文？
5. 现有会话入口、进度判断和整理机制怎样承接这一模型，原阶段路线如何调整？

以上是待讨论项，不是新增的必做模块。先把基本表达讨论清楚，再决定最小实现，不提前选数据库结构或重写现有机制。

## 9. 讨论与授权记录

- 用户要求简化核心原理，以“做过什么、接下来做什么”为中心。
- 用户明确允许粗计划逐渐丰满、试错、换方案，并要求简述过程、保留划掉的错误尝试、沉淀可复用结果。
- 本文将助手对上述要求的理解和示例固定下来，作为后续讨论依据；不把每个补充建议都当作用户已确认决定。
- 用户授权建立第零阶段文档以避免压缩后的语义损失，后续基于本文继续讨论。未授权代码修改、迁移或启动原第一阶段。
- 后续用户补充章节式展开、叶子可为一次尝试、主项简述结果及详情定位，并要求助手设计拆分原则。本文据此增补第5—6节，明确区分用户方向与待讨论的具体规则；未将建议视为已批准实现。
- 用户认可主体方向，并提出程序分配序号、通过起止标记维护详情关联，主项只写序号。第6.2节据此替代手工路径/标题/行号引用；编号作用域、稳定性、校验及受控写入等为助手建议，未视为实施授权。
- 用户继续询问怎样实现、是否需要新工具。只读核对当前代码后，第6.3节提出一个薄的本地记录工具作为推荐，保留其他入口的取舍和待细化边界；没有新增工具或修改源码。
