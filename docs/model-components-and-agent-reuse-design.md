## 1. 范围与结论

**原盘点阶段状态：源码盘点与技术建议；体验和布局已另行定稿，当时技术接口未批准，本通用组件方案未实施。**本文结合交接文档，盘点当时工作树中需要模型能力的用途，区分源码快照、业务要求和建议改动。盘点阶段仅静态审计及新增本文；其后文档定稿阶段仅补充体验方案、文档衔接并对齐并行更新的记忆业务定案，没有修改产品代码、调用真实业务模型、运行产品测试、迁移或清空数据、重启、提交或部署。盘点时实际安装的 Pi 为 **1.1.0**；工作树存在大量并行修改，本文不是正式后台已加载这些源码的证明。

**后续获授权的隔离实现：**现有过程、错误和状态反馈已另行在独立 Worktree 接入，具体实现及验证见[实现与接入说明](background-model-task-experience-implementation.md)，未合并或部署到正在使用的后台。本文件保留盘点与候选设计的历史语义，不把通用执行器重构、查询子会话或新业务操作一并视为已批准。

后续讨论已确认两种执行模式、实时反馈要求和业务卡片位置，详见[任务体验与布局方案](background-model-task-experience-plan.md)，以该文为当前体验与布局依据。**本文全篇源码判断均保留原盘点时间语义，不代表并行改动后的实现进度**；包括第2节、后续“当前”代码判断和候选改动地图，接入前均须重核，不能把“本通用方案未实施”推为其他会话的记忆改造未实施。

**记忆查询方向已被后续定案替代：**最新[目的流程覆盖](memory-refactor/purpose-flow-coverage.md)与[当前机制](memory-tree-query.md)采用直接 `memory_query({ question })`、同步返回、逐层完整候选、一跳引用及原 `memory_usage` 账源；不依赖子代理、通知、`read_result` 或新增查询业务卡。本文第5.2–5.4节的查询子会话提案仅保留历史，不是当前契约或待实施缺口。其余具体 kind/活动引用、事件、预算、租约、存储和调度提议仍属技术草案，不因体验定稿而自动获批。

**本轮进一步收敛：**用户明确排除 Codemode 等工具内部模型调用，不做其执行、事件/历史投影、嵌套错误、产物或费用展示改造。第2、7、8、13节相关内容只保留原盘点事实，不构成本轮接入、修复或验收要求；当前接入地图、P0和验收已排除该项。

**已有能力保持：**普通任务的 `delegate`、`cancel`、`append`、`read_result` 沿用现有输入/返回、权限、操作目标、预算与生命周期语义；本轮目标是接入真实过程和错误反馈，不重设计这些能力。观察/展示接入可能修改相关代码，但不代表接口或使用规则改变。第5.1节及候选地图中的业务类型/策略抽象是未来另行确认的技术候选，不是本轮必须扩展的接口，也不为标题、分类等自动开放委派、取消或追加。

这里的“全部”指**原盘点的覆盖范围**：Axiom 源码中可定位的模型消费者和内置集成可达的模型入口；不包括任意外部 MCP 服务、扩展、Shell 命令内部不可见的模型调用。盘点覆盖不等于本轮改造范围，不能从工具名推断内部行为。

### 核心判断

1. **适合复用子代理执行的，是需要独立上下文、多轮工具导航、异步交付的业务。**普通研究/测试已经如此；其他业务须分别判断。目的索引查询改成子任务的原提议已被直接工具定案替代，不是本轮接入目标。
2. **单次结构化请求、元数据生成和原生压缩，不必变成普通子会话。**复用现有执行资源、过程入口、错误、结果和统计；分别保留独立 completion、原生 compaction 等执行策略。
3. **后台不是完全没有过程展示。**已有 Task/AgentThread 和 ProcessingRecords/ProcessingPage 两条链。本轮关注入口与状态没有贯通、准备阶段信息不足和标题生成静默失败。工具内模型失败的盘点事实已排除，不作为本轮修复项；其余连通现有能力，不新增第三套记录平台。
4. **非致命不能等于不可知。**标题生成失败可以不打断聊天，但必须有可查看的失败事实；查询失败不能伪装成“没有记忆”；摘要生成成功不能冒充压缩已应用。
5. **不再造资源池，也不强制一个 runner、一种提示词或一个模型。**共享身份关联、生命周期观察、模型配置解析、既有取消/结果交付的状态及费用展示，保留原有操作能力与业务权限、输入、校验及提交边界。

### 2.3 不应误算成独立推理用途

- **记忆归并/树发布：**当前 memory-tree 的同层字符串聚合、关联绑定与事务发布是确定性程序操作；语义重归类附在整理请求中，没有单独的“全库语义归并模型”。
- **旧目录 summary 字段：**当前整理成功路径写空 summary/keywords，不能因遗留字段声称仍有独立会话目录摘要请求。
- **各种名称：**首消息截取兜底标题、旧 `<title>` 提取、子任务 delegate 入参标题、记忆标题解析不是额外命名模型。主模型维护任务树标题也不应再算一次独立调用。
- **压缩短摘要、子代理预算总结：**前者从同次原生摘要解析；后者仍在该子会话生命周期中，可能继续请求，但不是另一个摘要服务。
- **模型控制面：**checkAuth、本地凭据、目录 GET /models、OAuth、代理启动/端口检查、延迟观测、ping、版本检查不生成内容。认证成功、目录可读、端口就绪均不证明推理可用。
- **REA/OpenCLI/普通 MCP 工具：**Axiom 自检和工具执行代码未见独立推理消费者证据；外部工具内部行为未审计。Codemode 内置模型 API 是上面单列的例外。
- **代码定位 Locator：**[contracts.ts](../app/src/server/code-index/contracts.ts) 已有 LocatorLaunch、模型预算、工具白名单和 usage_events 契约；未发现运行引用、注册或调度接线，putUsage 也只是准备能力。可作为未来适配候选，**不是当前已运行组件**。

## 3. 业务边界：不能被通用任务约束替换

### 3.1 目的索引记忆查询：按最新工具定案

当前业务以[目的流程覆盖](memory-refactor/purpose-flow-coverage.md)与[当前机制](memory-tree-query.md)为准；[旧查询要求](memory-refactor/02-purpose-query-requirements.md)开篇已明确委派承载被替代。以下是对通用组件的约束，不是本会话对并行实现的运行验收：

- 保留直接 **`memory_query({ question })` → 同步工具结果**。问题应自足并包含必要条件，不传 Topic、目的ID或任意路径；不依赖子代理、委派通知、`read_result` 或新增查询业务卡，也不重新建设专用执行管理器。
- 由程序捕获最新已发布索引，始终将当前层完整候选交给模型逐层语义导航，可多分支；不关键词预裁、截断或默认灌入全树全文。**3k候选阈值未采用，不是待本组件确认的参数。**
- 程序验证目的身份、映射与授权，读取相关目的，选择必要详情；完整读取所选详情及其直接显式文本引用，**只展开一跳，不递归引用**。不读聊天、任意仓库或通过 Shell 绕过权限，历史资料不能扩大授权。
- 查询沿用 PooledMemoryRunner、原执行池、模型用途及 `memory_usage`/Costs，不创建查询子会话 transcript，不向父工具结果重复附加费用。
- 主会话常驻一级目录为≤1000字符的纯名称/关键字，无ID、来源或位置；它是分支快照，而查询每次取最新已发布索引，两者不能混用。目录与压缩联动见第5.5节。
- 答案直接给可复用结果，保留成功/失败经验、适用条件与分歧；内部轨迹可查，答案所需目标项目路径不得删掉。历史结论仍由主代理核对当前适用性。
- 无匹配、无有效依据、不完整与模型/权限/读取/修订等错误保留不同语义，不把失败变成成功空答案，也不以程序校验证明答案语义正确。

旧四字段、Topic参数、旧快照和旧查询逻辑不兼容，不做双轨或全库扫描兜底；当前仍使用 `memory_query` 名称不代表继续旧协议。历史原文和账单保管不授予删除权。查询已不以本通用组件为前置依赖，本方案只讨论复用其真实过程和错误展示，不重做已独立定案的业务流程。

### 3.2 已完成目的的批量分类

分类业务已在独立记忆改造中定案，实施与边界以[最新覆盖](memory-refactor/purpose-flow-coverage.md)为准；本通用方案不把它重新列为尚待实现的索引功能：

- 程序只提取结构合格的一级已完成目的，维护稳定ID和来源关联；不合结构跳过，不调用模型补目的或兜底摘要。同文件其他目的未完成不阻止合法目的入队。
- 按50条或30分钟两入口互斥触发固定批次；模型接收已有目录、目的ID/文本与程序冻结的相邻目的标题/状态语境，不读取来源正文、不生成正文，不把普通 append 当作批次输入。
- 分类树可任意深；ID覆盖、归属、树结构及版本校验通过，树与来源关联事务发布后才标已整理。失败保留未提交事实，已发布内容不得因重试重复入库。
- 这更适合**受控结构化请求＋程序提交**；不需要研究子代理的 Shell、通用读文件和自由探索循环。旧四字段草案是历史讨论，不应成为新组件默认输出契约。

## 4. 分三类复用，不把所有东西塞进普通子会话

| 类别 | 适用组件 | 建议共用什么 | 必须保留什么 |
| --- | --- | --- | --- |
| A：复用子代理执行 | 普通研究/测试；未来真正接线且获准的 Locator 等可再评估 | Tasks 的身份、子会话、调度/预算、结果保存/通知/读取、AgentThread 和统计 | 各自输入、工具策略、资源加载、输出校验、预算及允许操作；不为形式统一迁入现有工具查询 |
| B：共享过程与管理底座，保留执行策略 | 直接工具式记忆查询、标题、批量分类、原生压缩 | 已有池/Profiles、生命周期观察、ProcessingRecords、原位入口、错误、取消及费用展示 | 查询的程序导航/PooledMemoryRunner、completeSimple/原生 compact、分类事务、标题更新和压缩安全应用；不伪造子会话 |
| C：保留专用流程 | 主聊天与其维护/续跑；认证/目录/代理控制面；确定性发布和名称派生 | 仅在有价值时共享状态外观、脱敏错误与触发来源说明 | 主会话单写者/授权；控制面协议；确定性算法。不能为“通用”额外增加模型调用 |

**选择标准：**需要独立多轮上下文与可审计工具链，才优先 A；固定输入/固定输出或原生专用算法，优先 B；本来不推理或必须继续主上下文，保留 C。

A/B/C 是复用边界，不是三套执行组件；后续已确认以“一次性作业型/多轮会话型”区分执行方式。一次作业可含多次请求，多轮不等于自由追加；主会话保留原流程，工具内部模型调用不接入本轮组件。具体组件映射留待讨论，见[已确认的执行模式](background-model-task-experience-plan.md#3-两种执行模式)。

### 建议结构

```text
模型委派 / 用户命令 / 程序自动触发
                  │
          可信业务策略与适配
     输入、模型选择、权限、预算、校验、提交
                  │
       ┌──────────┴───────────┐
  Tasks + 子会话           现有业务控制器
  records/scheduler/       查询 / 标题 / 分类 / 压缩
  delivery                 + ProcessingRecords
       │                         │
  agent-session       isolated-completion / native-compaction
       └──────────┬──────────────┘
        已有 ExecutionPool / Profiles / Lease

展示：共享入口卡片 → TaskViews/AgentThread 或 ProcessingPage/业务详情
统计：读取原账源，不因新增卡片或业务记录再次计费
```

物理 worker 的 entry（agent/memory/compression）、池的 ExecutionKind 和业务 kind 是不同层。不能仅新增一个 kind 字符串就认为工具权限、调度、结算和UI已经通用化。也不需要动态插件平台、任意脚本配置或一个替代所有 manager 的巨型执行服务。

## 5. 最小组件边界与接口草案

### 5.1 先让“普通任务”成为一种策略

**以下策略拆分是未来候选，不是本轮必做的能力重构。**当前先保持普通任务的委派、取消、追加、结果读取和预算/生命周期规则；不为接入过程展示就扩展工具参数或重新定义操作。新增独立会话业务时，才另行讨论下面的抽象与准入。

原盘点时 agent-worker 的 input.task 分支统一加载研究/测试政策、工具、资源禁用和预算总结行为，Tasks 也默认研究会话。可讨论把以下少量决策集中为**代码内可信策略**，先以 research 验证边界；其他真正需要独立会话的业务另行确认，**不以当前记忆查询迁入 Tasks 为接入目标**：

| 业务策略职责 | 组件共同负责 | 适配负责 |
| --- | --- | --- |
| 输入与身份 | workspace/session/task/run/result，幂等请求与归属校验 | 输入 schema、索引/批次/快照捕获与适用条件 |
| 模型配置 | 共用 Selection 校验、runtime/provider/代理及环境快照机制 | 选择现有哪个偏好；禁止失效配置静默切换 |
| 会话与工具 | 建立/复用会话、租约、事件、停止、持久化 | system/context、资源加载范围、工具白名单及宿主授权 |
| 预算 | 可观测排队/运行时限与预算结算 | 各业务期限和读量；research 的无工具总结不能成为所有业务兜底 |
| 结果 | 不可变结果保存、通知与读取 | 输出格式、来源复核、业务 outcome、事务提交/安全应用 |
| 操作 | 按已验证能力显示按钮及拒绝越权请求 | append/retry/cancel 的可用阶段与副作用语义 |

research 工具说明中的“报告≤2000字符、context≤200字符”不是业务输出的全局限制；现行 read_result 返回完整记录，不能通用化时擅自截断。后端另有 context/task 各12000字符、短标题1–30字符等输入校验，通用化应保留安全输入上限并按业务建模，不能混淆软报告约束与硬输入验证。

原盘点的 TaskScheduler 在启动、追加/恢复及 preferencesChanged 时使用统一研究预算，到期进入三分钟无工具总结。未来若接入其他获准会话业务，需由对应策略控制预算；**研究设置不能成为全业务默认**。当前工具式查询继续由原业务链路控制期限，不因组件化继承研究总结；共同容量上限不变。

### 5.2 delegate/read_result：扩展原入口（已替代的历史提案）

以下是历史草案，不是当前可调用参数，也不是待实施接口：

```json
{
  "context": "当前问题及必要背景",
  "tasks": [
    {
      "kind": "memory.query",
      "input": {
        "question": "系统提示词在哪个入口组装？",
        "conditions": "需要当前 Axiom 源码相关的历史定位结果"
      }
    }
  ]
}
```

- 旧 `{title, task}` 不传 kind 时默认 research，**普通研究任务**的调用、历史报告和完整读取行为保留；这不要求兼容旧记忆查询/Topic 协议。用判别联合而非自由字典表达业务输入，按 kind 校验允许字段；卡片短标题可由程序生成，不要求模型再调一次命名。
- 新查询由服务端准备可信索引上下文、来源映射和读取策略。调用者不能注入 SQL、任意路径、工具列表、系统提示、环境或越权 scope。**kind 不是权限提升开关。**
- 首批模型可委派类型只开放 research 与获准接入的 memory.query；标题、整理、压缩仍由已有程序入口触发，不因注册策略就开放给主模型任意执行。
- read_result 仍按 taskId/resultId 读取不可变结果，不用于进度查询。可增加可选业务 kind/outcome/payload，旧 report 保持兼容；默认给主代理的答案与详细来源轨迹分开，完整内部关联受归属校验保护。
- append 对 research 保持既有契约；查询首版建议不允许自由追加，改问题创建新任务，避免混用来源与结果。取消可复用原入口但仍检查所属任务和当前阶段；结构化批次/压缩不沿用普通 append。
- 能力校验必须覆盖**所有服务端入口**，不是只改工具 schema 或隐藏按钮：task.append、子会话 prompt（含附件、Skills、rewrite）、agent.resume 及模型切换均依据持久化业务 kind、阶段与策略判断。查询首版拒绝未经业务授权的追加、历史重写和恢复，不得从直接命令绕过受限上下文与结算。
- 查询应先形成可校验的最终业务结果，再保存和通知。当前 TaskDelivery.save 以最后一条正常 assistant 文本形成报告、按 run.status 结算；需增加业务结算钩子，不能等到 read_result 时才发现结果无效，更不能把模型正常停机直接判成查询成功。

### 5.3 查询执行器：受限 agent-session（已替代的历史提案）

查询确需多轮导航，可以使用已有子会话运行与事件通道，但只注册**受控目录导航、目的读取、必要详情读取**能力。具体工具命名可后定，程序需落实：

1. 读取参数是宿主签发/校验的目录、目的或引用身份，不是任意文件路径；workspace 与来源映射在宿主校验。
2. 不开放通用 read/bash/write/edit、递归委派、外部扩展、任意 Skills/资源包；不把项目 AGENTS.md 等无关上下文带进受限业务。仅靠提示词说“只读”不成立。
3. 按当前问题供给目录与材料，记录实际读取关联、修订、字符量、轮数与耗时；必要引用跨层展开时去重、防循环并保留关键缺失事实。
4. 预算耗尽返回明确不完整或失败，不触发研究任务的“无工具短总结即完成”；也不另发一次模型自评来证明语义质量。
5. 保留 queryModel 现有偏好语义，不能在迁移到 Tasks 后误用普通子模型默认值；仍只共用解析/校验和模型环境管理。

### 5.4 调度与父会话生命周期（已替代的历史提案）

现有同步查询可携带有效 parentLease，池只允许 memory-query 使用嵌套叶子保留席位。新查询是异步任务，**不能直接复制这个条件**：父 run 自然结束后旧租约失效，但异步查询仍应继续；父显式停止/冻结后又不能由迟到结果擅自唤醒。

建议首版按普通异步子任务队列调度：主代理继续无依赖工作；只剩查询依赖时结束当前 run、释放执行资源，等待既有结果通知续跑。不要在持有主 worker 租约时轮询 read_result。用小容量池验证饱和活性、停止/冻结及恢复行为；不能把当前同步查询的叶子保证当成新流程已经具备的保证。

若后续确需主 run 持租约等待，应在**原池**中扩展由宿主验证的受限叶子准入及依赖规则，单独设计/确认；不能把所有 agent 标成叶子绕过上限，也不能另开查询池。业务并发/总期限仍由对应 manager 持有，不搬进物理池变成第二套业务调度。

### 5.5 记忆替换完整性与主会话/压缩联动

“遵守已有机制”不等于“维持旧记忆逻辑”。以下是组件接入时不得破坏的业务约束，**不是本轮新增的待实施清单**；独立改造的完成情况以[最新覆盖](memory-refactor/purpose-flow-coverage.md)为准：

- 旧四字段提取、Topic/Section 路由及旧查询参数/消息退出运行链路，不为旧ID、参数或快照另设适配和兜底；保留当前 question-only `memory_query`。独立 memory worker 仍承担查询、分类、标题等用途，不能连带误删。
- 一级纯名称目录的生成、真实 context_with_system 注入、快照写读、分支恢复及环境预览一致，内部来源映射不混入常驻文字。沿用会话开始/选定分支的快照规则，普通请求、reload、首输入编辑不刷新；查询每次捕获最新发布索引，不能借观察层刷新改变分支快照。
- **目录不写入压缩摘要；压缩成功后由程序注入最新目录且去重。**目录格式/标记变更时同步改排除规则和压缩元数据的生产/消费；保留原生 compact、split-turn 摘要约束、快照修订、安全应用及允许的新增尾部，不把目录改名后意外混入摘要。
- 查询、分类索引、API/订阅/离线空值、UI、处理记录、模型设置与费用归属成套切换，不在生产链路双读双写旧四字段；既有研究任务与主会话、权限、原文修订、压缩安全测试保留并适配新契约，旧四字段专属预期不成为保留旧逻辑的理由。

完整业务替换表以[目的索引联动覆盖](memory-refactor/purpose-flow-coverage.md)为准，本文只规定组件接入边界，不重做目的树/队列设计，也不把以上设计要求当作本轮实施授权。

## 6. 统一可见性，但不统一所有状态枚举

### 6.1 共用卡片外壳，详情保留原载体

卡片按业务归属放置已经确认，具体布局见[任务体验与布局方案](background-model-task-experience-plan.md#4-卡片位置总表)。以下轻量活动视图引用（例如 task/processing/run 的引用联合）仍是技术建议，**只作现有数据的投影，不新建活动数据库/第三套历史**：

- 研究/分析/测试委派仍由工具 callId 锚定，显示业务名、实际阶段、结果概要和允许操作，打开原子会话详情。
- 直接 `memory_query` 保留原工具卡及已有处理记录，原位补查询过程和错误；不新增查询业务卡、子会话或委派通知链。
- 后台整理/批量分类放在“全局记忆”当前工作空间视图的目录/树上方，展示队列摘要与活动批次；入口显示运行/异常状态，完成批次归入已有处理记录。来源会话只保留关联状态或跳转，不承载跨会话批次。
- 压缩在现有压缩面板对应卡片内补实时过程和错误；标题在会话标题附近/顶部使用轻量状态入口，展开过程、成功收起、失败可查，不刷聊天消息。
- 自动标题、整理和压缩不伪造 delegate/callId，引用真实执行/处理记录；主会话维护留原执行过程；工具内部模型调用本轮不接入。同一执行的多个入口不重复创建任务或计费。
- 共用状态图标、耗时、模型/用量摘要、错误摘要、展开操作；详情分别进入 TaskViews/AgentThread、ProcessingPage 或 CompressionDetail。无需为每个 completion 创建空子会话。
- ProcessingRecords 写入后发布轻量失效通知，沿用现有 transport 订阅再读取摘要/选中详情；避免每次广播或轮询传输巨大请求正文。现有4秒轮询可作兼容回退，终态详情可停止无条件轮询，手动刷新保留。

现有证据：[TaskCards.tsx](../app/src/client/tasks/TaskCards.tsx) 依赖 delegate 锚点且写死“子代理协作”；[TaskViews.tsx](../app/src/client/tasks/TaskViews.tsx) 打开子 AgentThread；[ProcessingPage.tsx](../app/src/client/pages/ProcessingPage.tsx) 已持续轮询列表/详情，不是静态历史页，但不是实时事件订阅。

### 6.2 三个事实轴分开

| 事实轴 | 示例 | 不能混淆的结论 |
| --- | --- | --- |
| 执行 | 排队、准备、请求、工具执行、校验、提交/应用、取消中、终态 | 没有调用不等于无匹配；进入请求代码不等于供应商确认收到 |
| 业务结果 | 有依据、无匹配、无依据、不完整；标题已更新/被手动改名取代；分类已发布；压缩已应用 | 运行正常结束不保证答案正确；摘要完成不代表已应用 |
| 交付 | 结果已保存、通知待发送/不确定/已送达、结果已读取 | 通知失败不应改写业务结果；通知送达不证明主代理已理解或采用 |

不直接把 Processing 的 invalidated、Task 的 interrupted、通知 unknown 全压成同一个 failed。UI 可以共享外观映射，但底层保留原始状态与原因。`no_match`、`no_evidence`、`incomplete` 等可以作为业务 outcome；超时/权限/模型错误仍是执行失败，不用“成功空答案”代替。

### 6.3 阶段来自真实程序事件

共同可观察的阶段语义可包括：**等待资源 → 准备环境/绑定 → 进入模型调用 → 工具/业务阶段 → 校验 → 保存/应用 → 清理与交付**。具体业务可省略不适用阶段，不能凭模型自报进度生成百分比。

- 池已有 onMetric 与执行阶段指标，当前未见应用消费者；需要接入与 task/run/processing/call 的可信关联，并保存必要脱敏准备失败原因。预热/实例清理属于资源事实，不伪装成业务步骤。
- Processing 的 sentAt 是代码已进入调用的观测点，不是服务端接收回执；没有精确证据时不能显示“供应商已受理”。
- 展示实际请求状态、工具/读取事件、可公开输出和诊断；不以获得或展示模型私有推理作为验收要求。
- 查看过程、展开记录、刷新UI不得隐式启动模型或重跑业务。

## 7. 错误显式反馈：解决静默，不制造噪音或重放

### 7.1 最低错误契约

在原有错误字段上渐进增加可选的稳定 code、阶段、可读说明及安全操作提示，首要区分：输入/授权、配置/模型不可用、排队满/超时、环境准备、模型/供应商、输出格式/预算、资料不可读/关键缺失、来源修订变化、提交/应用冲突、取消/中断、输入或通知投递不确定。

每个错误同时回答：**哪个业务、停在哪一步、有什么仍然有效、是否产生了费用/部分副作用、用户可做什么**。原始异常需脱敏；“可重试”只是操作资格，不是自动重放授权。未知状态不能靠重复发送来探测。

### 7.2 各组件的反馈策略

| 场景 | 建议反馈与行为 |
| --- | --- |
| 标题生成失败/非法输出/超时 | eligible 后建立 session.title 处理记录；保留原/兜底名称，标题附近/会话顶部的轻量状态入口保留失败提示和详情，不打断主聊天、不另唤醒主模型解释错误；合并同一尝试组通知，避免每次失败都弹窗 |
| 标题无需生成或被手动改名取代 | 没资料/已命名等正常跳过不报供应商失败；执行中用户改名导致 CAS 不再适用，记录被取代/未应用事实，不覆盖新标题 |
| 查询无匹配/无依据 | 作为不同业务结果保存；索引不可读、映射损坏、模型失败不能归入其中。有效部分可返回，但关键缺失明确不完整 |
| 整理/分类失败 | 保留未提交或部分已提交范围；显示批次/来源与阶段；只对授权且幂等的范围重试，不全库静默重做 |
| 压缩生成成功但应用冲突 | 显示“未应用”及冲突原因，保留已有账单/产物；不覆盖新分支，不用模型重写原会话；成功只在安全应用落盘后发布 |
| 主会话自动续接/维护被拒绝或取消 | 标明触发来源和停止原因，保留正常回执；自然结束不等于用户停止，显式冻结后不再自动唤醒 |
| 服务重启/强杀/通信不确定 | 旧执行记中断/不确定，保留已存结果/费用；从可验证历史对账，不自动重放未知模型请求、脚本或通知 |

**本轮排除的盘点事实：**Codemode 曾观察到顶层脚本结果与子调用状态可能不同；未知模型、模型类型或输入错误可能发生在子调用行创建前，截断行的 cancelled 也不能反推用户主动取消。此前实时/历史投影和嵌套失败展示建议已退出本轮范围；本轮不修改这些链路、不新增相关验收，也不重放脚本。

### 7.3 记录安全

已有 ProcessingRecords 做工作空间授权、归属校验、常见密钥脱敏及单 payload 2,000,000 字符截断；这不代表敏感资料完全不会泄露。应让默认卡片只含必要摘要，正文按需授权读取，不经公共日志/通知广播，截断明确标识。不要把原始图像/base64、鉴权头或任意扩展 details 全量透传到共享卡片。

## 8. 模型配置与费用：共用机制，不共用错误归属

### 模型配置

保留主会话、普通子模型、查询模型、整理模型和压缩模型的独立用途。共用解析、可用性校验、provider/runtime、代理与快照修订机制，而不是新增一组平行配置，也不是把所有业务强绑一个模型。标题继续取触发 run 模型，除非后续明确提出专用偏好。

每次执行记录**实际生效的选择及其来源**。只有未设置偏好才走已声明的继承；已保存但失效的配置必须报错。读取历史账单不能按当前模型/单价反算或重标供应商。

### 唯一原账源

| 调用类型 | 原账源建议 | 复用时避免的重复 |
| --- | --- | --- |
| 主聊天及其自动维护/续跑 | 主会话 transcript 的原生 assistant usage | 不能因新增 origin 活动卡再记一份“维护模型费用” |
| 普通子任务 | 子会话 transcript 原生 usage，由父会话 Costs 汇总 | 结果读取或新增卡片不能再次累计同一调用费用 |
| 当前工具式记忆查询、标题、批量分类 | 既有 memory_usage 独立调用账源，带实际模型身份 | 查询不创建子执行 transcript，父工具不二次计费；ProcessingRecord 只引用/展示，不成为另一账源 |
| 原生压缩 | 既有 compression billing/usage 与已应用历史按 compressionId 去重 | 生成、应用、处理记录不能各加一份；取消也保留已发生费用 |
| Codemode 分类/图像（原账源盘点，本轮不调整） | 已有 toolResult.usage | 仅保留原盘点事实，不接入子调用拆分或新增展示/账源 |

共享请求/call 身份与账源引用即可先保证唯一归属，不必先重建一个全量费用账本。迟到用量归原 run/lease，不修改新任务；强杀、未返回 usage 或无法读取历史时，明确“费用不完整/未知”，不是零费用。业务失败也可能已付费，不能只给成功结果记账。

现有依据：[costs.ts](../app/src/server/costs.ts)、[memory-runner.ts](../app/src/server/memory-runner.ts)、[compression-worker.ts](../app/src/server/compression-worker.ts)、[request-usage.ts](../app/src/server/request-usage.ts)。

## 9. 保留业务提交与所有权边界

- **普通研究：**保留输入回执、预算、追加/恢复、多次结果和“不自动重放”；研究结果正确性由实际证据与必要验证判断，不新增通用模型裁判。
- **查询：**question 输入 → 捕获已发布索引 → 逐层导航/必要详情及一跳引用读取 → 归纳 → 修订/授权复核 → 同步工具返回与处理记录。保留既有工具/PooledMemoryRunner 的取消、超时及用量链路，不引入子任务通知、独立 transcript 或父会话等候续跑依赖。
- **分类：**捕获批次与基准版本 → 请求 → ID/树校验 → 同事务提交关联并标已整理。取消与提交竞态以可验证落盘为准，不能已提交后显示“全部未执行”；固定批次不被任意追加文本改写。
- **压缩：**安全时机统一见[会话安全点契约](session-safe-points.md)，[compression-context.ts](../app/src/server/compression-context.ts) 保留单写者、真实会话身份／产物基本合法性、工具配对、幂等 ID 与新增消息保留校验。应用不再比较快照字节前缀，也不因历史编辑或分支变化拒绝；快照后已有新的原生压缩时，迟到 Axiom 摘要失效。工具校验防止新切断已有配对，不是拒绝全部历史缺失结果的调用。原生 compact 与 apply 之间不可用普通 TaskResult 文本替代。
- **标题：**只更新受 pending 条件保护的元数据；不写聊天历史，不覆盖用户改名；取消后即使模型有迟到响应也不应用。
- **自动主会话触发：**建议加 origin（用户、任务通知、记忆续接、压缩准备、重载续跑）及关联ID，解释“为什么又调用模型”；这些仍是主会话执行，不私自转移到失去必要上下文的子会话。

TaskStatus、业务 outcome、压缩应用状态与通知 delivery 应保留各自事实，不以一个通用 completed 替代所有提交协议。

## 13. 本轮证据与未验证项

本次核对了 Axiom 主/子会话、记忆、标题、压缩、执行池、处理记录、费用、模型控制面及能力集成入口，并以安装版 Pi SDK 和 Codemode 实现补查条件性模型入口。主要纠正了两个容易遗漏的现状：**记忆/压缩已有过程展示；Codemode 可能真实调用非聊天模型且子失败不等于脚本失败。**

仍未验证：运行中后台加载版本、用户实际 MCP/非聊天模型配置、真实模型可用性/语义质量、运行时费用完整性、外部工具内部推理及该设计的产品回归。后续已核对最新记忆业务文档并纠正旧查询承载，但未重审其实现或复跑其测试；历史修复和其他会话的实施/测试记录均不作为本次工作树验收。

原盘点交付为本文及源码静态核对，后续补充了[已确认的任务体验与布局方案](background-model-task-experience-plan.md)，仅做文档衔接。体验定稿后仍需讨论底层组件及交互，再另行确认实施范围；两份方案均不自动启动重构、迁移、清空或部署。
