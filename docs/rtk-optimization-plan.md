# RTK 接入优化定稿

状态：**宿主实现与已保存快照验证通过；最新共享工作区等待稳定后完成验收**。连续补验后，其他任务再次修改了 `RtkTool.tsx` 等文件；需暂停相关并行编辑后定向复验，或由用户确认按已验证快照验收，不能直接将旧结果套到新源码。用户已授权“实现”；未安装外部插件、升级生产 RTK 或重启后台，源码与构建验证不代表运行中的后台已经切换。

## 一、已确认的技术路线

**官方 RTK 引擎 + 参考 Pi 插件的宿主接入优化。**

| 项目 | 定稿决定 |
|---|---|
| RTK 底座 | 使用 [官方 RTK](https://github.com/rtk-ai/rtk) 二进制，不维护 Axiom 自有 RTK 分支或替代引擎 |
| 后续升级 | 继续使用官方发布版本；不切换为插件自带或第三方修改的 RTK |
| 优化位置 | Axiom 宿主的工具调用与结果处理层，不修改模型工作方式 |
| 主要参考 | [`@estebanforge/pi-rtk-optimizer`](https://github.com/EstebanForge/pi-extensions/tree/main/packages/pi-rtk-optimizer)，审查快照为 1.0.4 |
| 最小基线 | [官方 Pi hook](https://github.com/rtk-ai/rtk/blob/v1.1.0/hooks/pi/rtk.ts) 的 `tool_call → rtk rewrite` 机制 |
| 接入形式 | 内置适配，不直接叠装整个插件；主会话和子代理遵守各自的宿主权限与开关 |
| 模型侵入 | 零新增提示词、零额外模型调用，不新增要求模型主动使用的 RTK 工具 |

插件是实现参考，**不是 RTK 引擎或升级来源**；1.0.4 不是新增的运行依赖。命令映射和压缩由官方 RTK 决定；Axiom 只做安全范围检查与托管程序绑定，不复制另一套重写规则。

## 二、实际执行路径

```text
模型正常调用 Bash
  → 所有现有 tool_call hooks 检查原始请求
  → 末位宿主 RTK gate 检查开关、调用类型和安全语法
  → 受监督地调用托管官方 rtk rewrite（2 秒、限额、可取消）
  → code 0/3 且有合格候选：将命令位置 RTK 绑定到托管绝对路径
  → 经公开 extensionRunner.emitToolCall 重放所有 hooks 检查候选
  → 获准且候选未变、配置仍有效：SDK 执行业务命令一次
  → 已采用前置的结果不再 RTK pipe，包括执行失败
  → 未采用前置：原流程执行；仅合格的成功结果可走旧安全后处理
```

- 保留模型原始 assistant/tool-call 历史；只改变 SDK 校验后用于执行的参数，不新增模型工具或 RTK 建议消息。
- 官方 code 1、不可用、超时、无有效候选可以在业务执行前保留原路径。**code 2、候选权限拒绝／异常、检查中候选被修改则阻断**，不能借回退执行原命令。
- 配置 revision、可执行路径和自定义 shell 门禁在执行采用前复核。每个调用 ID 分别管理重入与采用状态，不把并发调用误判成权限重放。
- 通过 Pi 1.4.0 公开 runner 做的是**验证重放，不是 nested 工具执行**。它可能再次触发第三方扩展的审批、日志或其他副作用；不承诺任意外部 hook 都具有幂等性，也不新增 OS 沙箱保证。
- **业务命令已经执行后，绝不为回退、补原文或测基线再执行一次。** 隔离测试中的基线／启用配对不属于产品回退路径。

## 三、本轮开放范围

| 等级 | 前置采用范围 | 保留的后处理 |
|---|---|---|
| 保守 | 不前置重写 | 既有可识别的成功测试／检查输出，至少 2 KiB、净缩减至少 20% |
| 均衡 | 官方候选 `rtk git status`、`rtk git log`、`rtk ls` | 原有路径列表等安全成功结果，至少 1 KiB、净缩减至少 10% |
| 强力 | 均衡范围 + `rtk grep`、`rtk git diff` | 原有搜索／补丁等安全成功结果，至少 512 B、净缩减至少 5% |

前置采用不设后处理的体积／净缩减门槛：执行前没有真实未压缩输出基线，因此**不保证每次采用都变小**。

首批仅默认 Bash 的受控字面命令列表：普通、部分 `&&`／`||`／分号复合、多行，以及可确认未压缩生产者的末端搜索管道。引号与原始字符偏移用于区分参数、赋值和命令位置；不会替换参数中的 `rtk`。以下保持原执行路径：

- Windows／PowerShell 前置、真正的 nested／Code Mode 调用、自定义 `shellPath` 或非空 `shellCommandPrefix`。
- 继承 `BASH_ENV`／`ENV`／`SHELLOPTS`／`BASHOPTS`／`BASH_FUNC_*`，或 `RTK_DISABLED=1`；已有显式 RTK 命令、RTK 环境前缀。初始化环境和 shell 设置在采用前再次检查。
- 非 Bash 分隔空白（包括 NBSP、U+2003、VT、FF，即使位于引号内也保守旁路）；未引用 glob／tilde、变量／命令替换、重定向和无法确认的语法，不做空白标准化。
- shell 保留字、`time/env/command/sudo` 等包装器，或 `eval/source/alias/hash/history/fc` 等状态修改指令；任一段出现即整段旁路，不只绑定其他段而留下 PATH RTK。候选未知位置的裸 `rtk` 也不采用。
- 被压缩命令位于管道生产者；机器格式输出标志，如 JSON、porcelain、NUL 分隔或自定义 format。
- 未开放的 RTK 子命令；不能因为官方生成了候选就认为其语义已经通过宿主验收。

### 官方 1.0.1 的 find 限制

真实隔离验证发现：`rtk find missing-path` 可能把原退出码 1 和路径错误变成退出码 0、无 stderr；在 `&&`、`||`、多行中会改变后续控制流。

因此本轮**整段含原始 find 命令位置的请求不做前置；所有 `rtk find` 候选也不采用**，包括 `rg --files` 等映射到该子命令的候选。不修官方压缩器、不维护 fork、不靠失败后重跑补救。`find` 等符合旧安全契约的成功输出仍可后处理；错误、截断和混合输出保护不放宽。

## 四、管理、数据与恢复边界

1. 沿用主／子开关、官方二进制安装／检查／卸载管理链与原有后处理，不叠装第二套插件管理。
2. 托管绝对路径避免误用 PATH 中另一版本；前置调用关闭 telemetry、recall、tee，并绑定 Axiom 私有 RTK 数据库路径。生产托管实测版本是 **1.0.1**，不是 PATH 的 0.45.0。
3. 统计新增独立 `rewrite` stage：检查、采用、耗时和原因；原 SQLite 10 列表加 stage，旧行默认为 `postprocess`。前置事件字节 0 是**未知哨兵，不是测量值**，不计入旧后处理的字节、次数或耗时分母。
4. UI／JSON 导出分别展示前置采用和后处理实测。采用不等于节省，字节不等于真实 token／账单；5,000 条／30 天滚动记录混合两种 stage，不能当完整长期分母。
5. 保留 `structuredContent`、details、非文本内容契约，不引入通用 content-only 裁剪；nested 程序化结果不前置也不后压缩。
6. **原文恢复边界**：旧后处理在采用前保存过滤前工具文本，保留 7 天／最多 200 条并附回查路径。前置只观察到官方 RTK 返回结果，不能恢复未观察到的未压缩原文，不伪装完整原文，也不重跑来补齐。

实现入口：[安全候选绑定](../app/src/server/integrations/rtk-rewrite.ts)、[前后互斥与权限 gate](../app/src/server/integrations/rtk-runtime.ts)、[worker 接线](../app/src/server/agent-worker.ts)、[分账统计](../app/src/server/integrations/rtk-stats.ts)、[管理界面](../app/src/client/pages/RtkTool.tsx)。

## 五、官方版本升级原则

- 沿用官方发布渠道和受控版本管理；实现宿主适配不等于立即升级，也不等于无校验自动追随最新版。
- 引擎和接入层分别管理。官方升级后重验 rewrite 协议、支持命令、shell 行为、退出码和失败诊断；不能仅凭版本号或 peer semver 开放范围。
- `find` 等被旁路能力，须由官方修复并通过相应语义回归后才考虑重新开放，不自动启用。
- 失败时按既有管理机制恢复已验证的官方版本，不能用重试业务命令代替版本回退。

## 六、本轮明确不做

- 不引入插件的提示词注入、suggest 对话建议或模型 RTK 使用指南。
- 不开启 read 源码有损压缩、泛化输出裁剪，不新增 RTK 专用模型工具。
- 不接入 Code Mode、大结果索引／落盘、历史裁剪或模型摘要；相关研究只保留参考，不自动排期。
- 不安装整包 Pi 插件、不修改上游 RTK、不增加该插件运行依赖。
- 不因测试通过而擅自升级生产二进制或重启后台。

## 七、验收与证据

最终硬化后验证：

- **RTK 50/50 通过**；指定 8 个相关宿主测试文件 **48 通过、5 项平台条件跳过、0 失败**。
- 完整 `tsc --noEmit → vite build → server tsc` 成功，仅非阻断 chunk 大小警告；最新构建前后 1,632 个受监测源码／测试／配置文件 SHA256 一致；之后的宿主入口定向补验也通过，未将复验加算为不同用例。
- 托管官方 1.0.1：主 43、补 16 命令 × 两档共 **118 对，采用 60、旁路 58，接纳项退出码不匹配 0**。18 项断言通过；8 对 stderr 非逐字相同但关键错误诊断保留。另 50 对包装器／状态／空白等危险输入及 12 个状态候选注入探针全部旁路。
- 真实生产 worker／SDK／本地 loopback provider 的 8 次隔离运行：每次 2 个 provider 请求、业务 `git status` 一次，原始历史与 assistant 命令不改；工具文本配对合计 **46,123→45,977 B，仅净减 146 B**。4 个启用样例仅普通 status 一例前置采用，其余机器格式保持旁路；不能泛化成整体节省率、token 或账单收益。
- 最新真实管理页、暗／亮 × 320／390／1200、独立分账与 JSON 下载通过；无全页横向溢出、pageerror 或 RTK 程序执行，20 个 UI 直接相关源码／样式／图标文件哈希前后一致。此项使用预置统计数据，不证明引擎压缩收益。

早期 find 失败、语法收窄和共享工作区并行变更均保留历史证据；不把中间成功构建或错误探针断言冒充最终通过。详细边界、命令与证据见 [验收记录](evidence/rtk-front-rewrite/README.md)。这些验证不覆盖全平台、所有第三方 hooks、全部 shell 语法或商业模型账单。
