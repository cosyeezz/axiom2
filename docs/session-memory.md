# 会话渐进式记忆与全局查询方案

状态：方案已整理，尚未实施。本文是本主题的统一方案文档，描述目标行为与实施约束，不表示现有产品已经具备这些能力。后续调整直接修改本文，不另建同主题版本或追加方案沿革。

本文作为 [产品设计](design.md) 的后续专项方案独立实施。现有 pi 会话、压缩、主／子 Agent 与工作空间隔离仍遵循产品设计；涉及会话删除、资源池和记忆加载的行为变更，应在实施时同步修改对应产品设计与 README，不提前标记完成。本次仅生成方案文档，不实施产品功能。

## 1. 目标与基本原则

长时间执行和多轮上下文压缩可能丢失目标、约束、决定及执行细节。本方案通过持久资料和渐进读取，帮助当前会话恢复工作，也让其他会话查询已有经验。

整体机制：

1. 主会话维护自己的简要入口与详细资料。
2. 后台定时整理这些资料，检查相关记忆中的冲突，按证据修正或删除具体条目，并生成独立的全局摘要索引。
3. 主 Agent 调用一个同步记忆查询工具。
4. 工具内部使用独立 pi Agent，按需读取摘要、详情和原始对话，整理后返回。
5. 查询执行池复用已加载资源，每次查询使用干净的会话上下文。

基本原则：

- **事实与来源优先**：根据会话中的实际陈述、操作和结果记录，不捏造，不凭模型主观判断裁定对错；允许依据用户明确纠正和可核实证据修正或删除记忆。
- **简要不等于遗漏**：入口压缩表达，必要细节保存在专题资料中，重要事实应有可追踪的阅读路径。
- **渐进加载**：先读入口或摘要，涉及细节再读资料，无法确认时回查原始对话。
- **职责独立**：主会话维护日常记忆，后台生成派生摘要，并仅针对已核实冲突或用户明确否定的条目清理来源记忆；查询 Agent 保持只读。
- **历史可追溯**：压缩和会话列表删除不删除原始对话及回查所需关系。
- **上下文隔离**：资源可以复用，查询消息、权限归属和执行状态不能串入下一次查询。
- **现状如实表达**：正在进行、尚未验证、资料过期、召回截断和查询未完成都须明确标记。

## 2. 系统组成与职责

| 部分 | 职责 | 写入范围 |
| --- | --- | --- |
| 主会话 Agent | 维护目标、约束、进度、结论、专题资料和证据引用 | 所属会话的记忆目录 |
| 记忆存储服务 | 校验归属、修订和路径，保存资料与元数据 | 记忆文件及所属元数据 |
| 后台整理任务 | 定时检查记忆冲突，核实后修正或删除条目，直接处理用户明确否定，生成摘要和检索信息 | 对应会话记忆条目、相关入口和引用、全局摘要索引；不改原始对话 |
| 历史查询服务 | 定位原始消息、组织完整交互单元、处理扩展与截断 | 可重建的定位缓存，不改原始对话 |
| pi 查询 Agent | 检索摘要、阅读资料、回查证据，整理查询结果 | 不写会话记忆和项目文件 |
| 查询执行池 | 预加载固定能力、分配查询实例、回收资源 | 运行管理状态 |

原始 pi JSONL 继续作为真实对话的恢复与证据来源。记忆是补充资料，不替代 JSONL，也不成为从另一份对话副本重建 pi 会话的机制。

本方案中的查询 Agent 是同步工具内部的专用执行者，不改变现有 delegate、append、cancel_task、read_result 四个独立工具的契约，不递归委派。

## 3. 会话记忆目录与入口

### 3.1 统一存储

资料保存在 Axiom 应用数据目录，不写入用户项目的设计源目录：

```text
memory/
  sessions/
    <sessionId>/
      MEMORY.md                # 会话入口
      references/              # 需求、决定、调查、实施等详细资料
      scripts/                 # 与本次工作有关的脚本
      artifacts/               # 需要保留的产物
  catalog/                     # 后台生成的摘要与检索索引
```

每个主会话拥有独立目录，并保存与工作空间的稳定归属。目录路径示意不代替归属校验；外部传入的路径或 sessionId 不能直接成为读写授权。

详细资料不限制文档个数，按自然主题拆分，可使用相对路径引用所属目录下的其他文档、脚本和产物。引用项目中的当前文件与保留的历史产物时须明确区别，避免把变化后的文件当成历史快照。

### 3.2 MEMORY.md 内容

| 内容 | 记录重点 |
| --- | --- |
| 目标与范围 | 用户最终要达成什么、验收条件、尚未明确的范围 |
| 要求与约束 | 用户明确要求、限制、偏好、纠正及已授权事项的适用范围 |
| 进度 | 已完成、进行中、未开始、阻塞 |
| 结论与决定 | 会话形成的结论、采用的方案与原因 |
| 验证情况 | 实际检查内容、结果、尚未验证事项 |
| 接续位置 | 下一步、待处理问题、进行中的子任务与结果位置 |
| 资料入口 | 主题、路径、简要用途和何时需要阅读 |

入口应简洁但全面。不能只列文件名，也不能省略重要要求后没有任何详情入口。入口优先保留当前目标、有效约束、正在进行的工作和接续位置；细节移入专题，而非丢弃。

入口建议以约 1,000–2,000 Token 为整理目标，不作为直接截断正文的硬规则。详细资料数量不设固定上限；单次读取预算、分页及总体查询预算另行配置，不能每轮加载全部文件。

### 3.3 详细资料与证据

详细资料包括需求、决定及原因、调查发现、实施变更、验证输出说明、未解决事项等。每份资料维护主题、状态、更新时间和修订标识。关键结论各自关联来源，不只在文档末尾放一个无法对应具体结论的引用列表。

锚点使用 `sessionId + messageId`；其中 messageId 对应原生持久化 entryId，不使用页面临时 ID、行号或显示顺序。根据需要保留分支身份、工具调用 ID、taskId、resultId 和产物位置。

示例仅表达内容结构，ID 为占位符：

```markdown
## 会话恢复通知

用户要求恢复会话后不得重复投递通知。
来源：session=<sessionId>，message=<entryId>

当前状态：修改已完成；普通恢复检查通过，进程中断场景尚未验证。
验证来源：session=<sessionId>，message=<toolResultEntryId>

详细实现：./notification-recovery.md
```

脚本应记录用途、适用条件、是否实际执行以及当时结果。脚本存在不等于执行成功；查询 Agent 阅读脚本内容，不自动执行脚本。

## 4. 会话记忆维护与恢复

### 4.1 更新时机与所有权

主会话在下列事实发生后及时更新记忆：用户调整目标或约束、形成重要决定、获得调查证据、完成阶段、得到验证结果、出现阻塞或改变接续位置。不能等到压缩前再临时回忆整个任务。

子任务结果通过现有交付机制返回主会话，由主会话阅读后纳入本会话记忆。子 Agent 不共同写主会话记忆目录；来源可以指向子会话原始消息或不可变结果。

用户可以修改记忆。保存应校验修订号，冲突时重新读取并合并，不能用旧内容覆盖用户新修改。所有权、写入工具与持久格式由后续实施契约具体定义。

其他会话默认只读来源资料。发现不同结论时，在本会话记录新事实并关联旧来源，不直接改写其他会话的记忆。后台整理任务依第 6 节处理已核实冲突或用户明确否定，是跨会话清理来源记忆的限定入口，同样须校验归属与修订。

### 4.2 内容演进

入口始终表达当前有效状态；重要的目标变化、被替代方案及其原因保存在详细资料中，并指向原始来源。重复内容可以整理，必要证据不能因缩短入口而消失。已核实不符合事实或用户明确否定的记忆条目按第 6 节修正或删除；真实历史不因现状变化而自动删除。

专题拆分、移动、合并或条目清理时，同步维护入口和引用。记忆对象使用稳定标识与修订信息，使摘要可以检测来源变化；不能让旧摘要静默指向无关的新内容，或让已删除条目继续从旧摘要中召回。

### 4.3 压缩与加载

会话启动、恢复和压缩完成后，在后续模型请求前提供最新会话入口；入口更新后也应在后续请求中生效。详细资料仍按需读取。

加载由程序保证，不依赖模型从压缩摘要中记住路径；避免把入口在每轮反复追加成多份持久聊天消息。

后台压缩基于较早快照生成的摘要不得覆盖执行期间更新的记忆。原生压缩与会话记忆保持独立；原始 JSONL 的恢复规则不变。

## 5. 原始会话保留与历史查询

### 5.1 会话列表删除

目标行为是逻辑删除：按既有停止边界结束所属活动执行，再从 Axiom 普通会话列表移除。保留原始 JSONL、记忆、工作空间与会话关系、分支定位信息，以及被引用的子任务结果和托管附件。列表删除本身不触发记忆条目清理；条目的修正或删除另按第 6 节处理。

逻辑删除后的会话仍可作为历史记忆来源，查询结果应标明其状态。外部文件引用不能保证永久存在，缺失时明确报告，不伪造已保留副本。

如将来提供永久清除，应作为独立明确操作；普通列表删除不承担物理清理语义。存储迁移与清理策略不能破坏这一保留规则。

### 5.2 查询入口与身份

提供独立历史查询工具，暂名 `history_read`，按 sessionId 和 messageId 查询。来源工作空间、会话、分支与读取权限由服务端校验，不能依据模型给出的标签直接授权。

首次查询返回锚点所属完整交互单元。结果保留原始消息身份、角色、顺序、时间、调用关系、实际状态和可用边界游标。定位索引与原始记录身份绑定；文件变化或索引失效时重新核对。

只沿明确的分支扩展，不拼接其他分支。被重试或上下文编辑排除的原始记录，如被明确回查，应标记其历史状态，不冒充当前有效上下文。

### 5.3 完整交互单元

| 原始内容 | 单元划分 |
| --- | --- |
| 普通用户消息 | 一条消息为一个单元 |
| 无工具调用的助手消息 | 一条消息为一个单元 |
| 含工具调用的助手消息 | 该消息及其发出的全部工具调用与对应结果为一个单元 |
| 中断造成缺失结果 | 保留实际存在的调用及结果，标明缺失，不补造配对 |

同一助手消息发起多个工具调用时，结果应完整归回所属单元。按原生调用 ID 配对，不按相邻位置猜测。

可以预处理并增量维护消息到单元、调用配对及上下边界映射。预处理生成可重建缓存，不改写原始 JSONL。尚未落盘的结果不能标为已有原始证据。

### 5.4 扩展规则

每次扩展只能选择以下一种：

- 向上一个完整单元；
- 向下一个完整单元；
- 上下各一个完整单元。

不接受任意扩展数量。边界到达时明确返回，不跨分支补足。后续扩展使用稳定边界游标，避免重复返回和跳过内容；调用方合并后仍保留每条消息和调用的来源。

### 5.5 单个工具调用的截断

2K 定义为 **2,000 个 Unicode 字符**，不是 Token，也不是整次召回的总预算。

- 每个工具调用独立计算其参数与结果正文，合计最多 2,000 字符。
- 超限时保留头部和尾部，中间使用 `...〔中间已截断，省略 N 字符〕...` 标记；标记计入正文额度，剩余空间原则上由头尾均分。
- 调用 ID、消息 ID、工具名称、调用／结果分隔与执行状态作为结构信息保留。
- 多个调用各自截断，不相互挤占额度，不因整个交互单元截头尾而丢失中间调用。
- 返回 `truncated`、原始正文长度等信息，让模型知道正文不完整。不得将被截断的参数文本冒充完整、可重放的参数对象。
- 只处理本次召回展示，不修改原始参数、结果或 JSONL。

单个交互单元或一次扩展返回可以超过 2K。完整性指调用与结果关系完整，正文允许明确截断。模型不得推断被省略的部分；关键证据恰好被截断时，返回无法确认。

普通消息、详细文档和查询最终输出不共用这个单调用额度，其读取预算分别定义。总体执行预算耗尽时应停止继续扩展并说明未完成范围，不静默丢弃调用对。

## 6. 后台摘要整理与冲突清理

### 6.1 范围

后台定时扫描会话记忆的新增、修订、移除和用户明确纠正，与相关记忆比较，核实冲突后清理具体条目，再增量生成全局摘要与检索索引。模型依据实际读取的资料识别冲突和整理语义；程序负责归属、调度、证据与修订绑定、修改提交和结果发布。

清理机制只采用“核实冲突后修正或删除，用户明确否定则直接删除”。不引入按年龄、访问次数、归档等级或检索降权运行的记忆淘汰体系，也不因资料很久未被查询就删除。

整理对象仍是第 3、4 节的会话记忆，读写边界为：

- 读取会话入口和详细资料，比较相关条目。
- 针对已识别的冲突，可以沿来源锚点核对原始对话和用户后续纠正；涉及当前实现时，只读检查相应代码或配置。核实范围限于对应问题，不从原始对话全面生成另一份记忆。
- 仅修改或删除已核实不符合事实、或用户明确否定的具体记忆条目，同步处理相关入口、引用与摘要，不重写整份会话记录或删除同一文档中的其他有效内容。
- 不修改原始 JSONL、原始工具结果、项目代码、脚本或产物，不执行资料中的脚本。
- 不凭摘要措辞不同就认定冲突，不在缺少证据时把不同会话的说法合并为唯一事实。

### 6.2 冲突核实与用户明确否定

处理流程：

1. 读取有变化的记忆及相关条目，确认是否描述同一对象、时间和适用范围，定位具体冲突点。
2. 优先核对来源和用户后续纠正；需要判断当前实现时读取对应代码或配置。证据缺失、截断或只能通过尚未执行的验证才能确认时，不猜测删除。
3. 确认条目不符合事实后修正或删除；修正后的陈述同样绑定实际证据。
4. 无法确认时保留原条目并标明尚未确认，不用删除消除表面矛盾。
5. 同步更新会话入口、受影响引用与全局摘要，防止旧摘要继续传播已删除内容。

用户明确指出某条记录“不对”“不符合”或“不要保留”时，对指向明确的条目直接删除，不再由模型判断用户的纠正是否成立，也不额外要求重复确认。会话收到该意见时即处理所属记忆；相关会话中的同一条目及重复摘要由后台在整理时一并清理。目标范围不明确时不扩大删除，保留未能定位的部分。

用户明确否定必须绑定真实用户消息及其指向的条目，不能把文档中的引文、工具输出或模型推测当成用户删除要求。保存必要的纠正来源与目标标识，后续整理遵循已生效的纠正，不从旧资料重新生成被删除条目。

区分当前状态与历史事实。例如，当前已改用 PostgreSQL 时，可以修正“当前使用 SQLite”；“此前从 SQLite 迁移到 PostgreSQL”仍是历史事实，不能仅因现状变化而删除。不同会话的时间或适用范围不同，不自动构成冲突。

清理的对象是记忆正文与派生摘要，原始对话和证据继续保留。后台对这些证据只读，不因删除记忆而改写真实历史。

### 6.3 摘要条目

| 字段 | 用途 |
| --- | --- |
| 稳定记忆标识、主题、摘要、检索词 | 发现和定位相关历史 |
| workspaceId、sessionId | 来源与范围 |
| 详细资料位置、证据锚点 | 渐进读取入口 |
| 来源状态 | 进行中、已完成、待验证、已被来源明确替代等 |
| 来源修订标识与资料更新时间 | 判断适用版本 |
| 整理时间与索引状态 | 表达新鲜度、失败或待更新 |

索引可以从当前会话资料重新生成。会话保存后直接读取应能看到新版本；普通内容更新允许在下一次后台整理前存在明确的索引延迟。涉及删除或纠正的条目，其旧摘要须失效，不得等待下一次成功生成才停止召回旧内容。

### 6.4 一致性与失败

核实、修改和摘要生成都绑定读取时的来源修订与实际依据。提交前校验目标资料未被用户或会话更新；修订冲突时重新读取并核对适用范围，不能用旧证据覆盖新内容。每次只提交已核实的对应条目，不覆盖整份文档中的无关修改。

摘要发布前复核修改后的来源。来源变化时不得将旧结果标为最新；未受删除或纠正影响的上次成功摘要可以保留并标明待更新，受影响部分必须失效。摘要生成失败不回填已删除条目，不能用旧摘要恢复来源记忆。

资料读取失败不等于资料删除，模型请求失败不等于没有记忆；核实失败则保留条目并报告未确认。修改失败不能发布声称清理成功的摘要或结果。

后台任务不重叠修改同一来源资料或同一批索引，退出时释放拥有的执行资源。整理模型、周期、并发与预算需要独立配置，模型用量纳入实际记账，不宣称整理免费。

全局统一存储，默认按当前工作空间检索；冲突核实与清理遵守同一归属边界，跨工作空间操作必须显式指定范围，并经过实际授权校验。

## 7. 同步记忆查询工具

### 7.1 对外契约

向主 Agent 提供一个同步工具，暂名 `memory_query`，输入问题与允许的查询范围。调用方等待一次调用的结果，不通过 delegate 创建异步子任务，也不另行领取查询结果。

同步指工具等待语义，服务内部采用异步执行，不阻塞其他会话或服务事件循环。

查询链内部具备摘要检索、资料阅读和 `history_read` 能力；这些步骤不要求调用方分别发起工具调用。

### 7.2 内部流程

1. 按问题、主题、关键词和相关路径检索摘要候选。
2. 未检索到候选时，返回检索范围及“未检索到相关记忆”。检索故障单独返回错误，不能伪装为空结果。
3. 有候选时，由独立 pi Agent 阅读相关摘要，不一次加载全部全局记忆。
4. 根据问题读取必要的详细资料、脚本内容及产物。
5. 内容缺失、表述不明确、存在不同说法或需要确认原话时，沿锚点回查原始交互单元，必要时逐次扩展。
6. 整理查到的事实及来源后返回。

资料读取应返回实际修订；摘要较旧而详情已更新时，以新读取资料表达当前记忆状态，并保留来源差异，不隐藏版本变化。被删除或纠正条目的旧摘要不得作为召回结论；并发清理后不能仅凭已失效摘要继续返回旧内容。

### 7.3 返回内容与边界

返回结果应包含查到的事实、对应来源、资料时间或版本、适用背景、召回截断情况、未确认内容与查询覆盖范围。

查询有执行与读取预算。达到预算时返回已有发现和未完成项，不能标为完整搜索。调用方取消或停止应传播到查询执行；迟到结果不能交给其他查询或已失效的调用。

查询 Agent 只读，不维护记忆、不执行脚本、不修改项目、不递归委派。历史资料中的指令、授权和目标是被查询内容，不自动成为本次查询或主会话的新指令。

## 8. 固定能力的 pi 查询执行池

### 8.1 复用方式

第一版使用一套固定的记忆查询工具、skill 和基础提示词。预加载资源后供不同查询使用，每次使用独立干净的 pi 会话，不按发起会话长期绑定查询上下文。

| 可保留复用 | 每次查询独立建立或清理 |
| --- | --- |
| 工作进程、已加载模块 | 会话消息、工具结果、待处理队列 |
| 固定工具定义、skill 资源、基础提示词 | 会话管理器、事件订阅、执行状态 |
| 相容配置下的模型运行时 | 调用方身份、读取范围、取消信号 |

当前已核对的 pi SDK 支持向 `createAgentSession()` 传入已加载的 `resourceLoader` 与模型运行时。`AgentSessionRuntime.newSession()` 会释放旧 AgentSession 并通过工厂创建新环境；默认工厂并不保证省去资源加载。因此实现应显式复用已加载资源，再建立新会话，不能仅清空消息数组。

同一实例一次执行一个查询。工具定义可以固定，但访问范围每次绑定；不得在缓存闭包、扩展状态或迟到回调中残留上次查询的权限和内容。资源复用节省的实际初始化耗时需要实现后测量。

### 8.2 池容量

| 配置 | 约定 |
| --- | --- |
| 核心保留数 | 2 个预热资源实例，不需要伪造业务对话 |
| 池容量 | 最多 10 个受池管理的实例，忙碌实例不能被淘汰 |
| 超额请求 | 达到池容量且无空闲实例时，允许临时冷启动，结束后释放 |
| 总并发上限 | 单独限制池内和临时实例的合计并发，达到后有界排队 |
| 空闲回收 | 超过核心保留数的空闲实例按时间和最近使用情况回收 |
| 配置变化 | 旧实例完成当前查询后淘汰，新实例加载新版本 |

10 是池容量，不是包含所有临时实例的系统总并发上限。总并发、队列和超时必须有界，避免超额冷启动无限增长。

执行失败、取消或清理异常的实例，只有确认状态干净后才可复用，否则淘汰。不得把仍有活动工具或未退出模型请求的实例归还空闲池。

第一版池用于记忆查询。主会话、子会话未来可以共用资源管理基础设施，但各自持久会话、工具权限与生命周期保持独立，不直接套用查询池的固定配置。

## 9. 事实、来源与可信边界

会话记忆、后台摘要和查询结果统一遵循以下表达规则：

| 来源事实 | 允许表达 | 不允许扩大为 |
| --- | --- | --- |
| 用户说已经修复 | 用户表示已修复 | 当前代码已确认无问题 |
| Agent 报告测试通过，没有关联输出 | Agent 报告通过，未关联验证输出 | 已核实所有检查通过 |
| 工具当次退出码为 0 | 该命令当次退出码为 0，附实际输出来源 | 整个系统正确 |
| 不同会话出现不同结论 | 比较时间与适用范围，核实前并列来源，核实后仅修正或删除对应条目 | 无依据地选一个作为真相 |
| 用户明确否定具体记忆 | 删除指向明确的条目及重复摘要，保留纠正来源 | 擅自扩大范围或再次裁定是否接受纠正 |
| 未检索到资料 | 本次检索未找到，附范围 | 从未发生 |
| 召回内容截断 | 明确被省略内容及无法确认项 | 根据缺失部分猜测结论 |

不裁定对错指不凭模型主观判断裁决，不妨碍依据用户明确纠正和可核实证据修正或删除记忆。应区分用户陈述、Agent 判断、工具观测和未经验证的计划；无法核实的部分继续保留并标明不确定。

旧记录能证明当时的陈述和操作，不能直接证明当前代码、环境或测试仍然如此。后台清理可针对已识别冲突只读核对现状；需要执行测试或其他操作才能确认时，由执行任务的主 Agent 验证，后台不擅自运行。不得把“现在不成立”等同于“过去没有发生”。

## 10. 实施边界与待细化参数

本方案确定职责、资料层次、历史召回、单调用截断、同步查询和资源池语义。以下细节在实施设计中确定并更新本文，不预写为已实现：

- 会话记忆写入工具的最终名称、参数、修订提交和用户编辑入口。
- 后台整理的模型选择、定时间隔、并发、失败重试与费用归属；冲突证据绑定、条目修改及对应摘要失效的提交接口。
- 查询模型选择、执行预算、详细资料读取预算和最终返回长度。
- 池的总并发上限、队列容量、等待时间、空闲回收时间与预热时机。
- 普通历史消息的读取预算，以及非文本产物的按需读取方式。
- 会话逻辑删除的数据库迁移、归档查询和托管附件保留实现。
- 稳定记忆身份、来源修订、分支游标与调用配对索引的具体持久格式。

这些参数不改变已确定的规则：历史工具调用各自最多 2,000 字符；每次扩展最多向上一个、向下一个或上下各一个完整单元；核心保留数 2、池容量 10、超额允许临时冷启动但受独立总并发限制。

## 11. 建议实施顺序与验收

### 11.1 实施顺序

1. 建立会话记忆存储、归属、修订保存及入口加载机制。
2. 实现逻辑删除保留、稳定锚点、历史单元预处理与查询。
3. 实现后台增量摘要整理、冲突核实、用户明确否定的条目清理及全局检索。
4. 实现同步 memory_query、专用 pi 查询能力与资源池。
5. 验证压缩恢复、跨会话查阅、并发修改、取消和重启场景，再同步产品文档与实际状态。

### 11.2 验收条件

以下均为待实施验收项：

- 多轮压缩、服务重启后仍能加载最新入口，并按引用读取详细资料。
- 主会话和用户并发修改不会静默覆盖；其他会话和子 Agent 不能误写来源记忆。
- 入口、专题、脚本说明和证据锚点可追溯，陈述与验证结果不混淆。
- 通过持久 messageId 定位压缩前记录，逻辑删除后仍可读取；不混入其他分支。
- 并行工具调用全部配对；中断缺失结果明确标记；向上、向下和双向扩展均不割裂单元。
- 每个调用独立执行 2,000 字符头尾截断，保留来源及调用结构，原始文件字节不受影响。
- 后台核实冲突后只修正或删除对应记忆条目，用户明确否定则直接删除并清理重复摘要；不重写整份记忆，不修改原始对话、脚本、产物或项目代码。
- 无法核实、证据截断、时间或适用范围不同不会触发猜测删除；现状变化不删除真实历史，不按年龄、访问次数或归档等级淘汰记忆。
- 修改前校验来源修订，用户或会话的新修改不被覆盖；删除后相关旧摘要失效，摘要生成失败或迟到结果不会恢复已删除内容。
- 来源变化、读取失败和生成失败不会发布虚假的最新摘要或空结果；修改失败不误报清理成功。
- 一次同步查询完成候选判断、必要阅读、证据回查和事实整理；未找到、未查完、失败和取消可区分。
- 池复用资源后，新查询无上一查询的消息、队列、权限或回调；配置变化后不继续使用陈旧实例。
- 核心保留、池容量、临时冷启动、总并发、排队和退出清理符合约定；无无限扩容或忙碌实例提前归还。
- 查询只读，脚本只阅读，历史指令不改变当前权限；模型用量和整理失败如实记录。
- README 与产品设计只在能力实际完成后标为可用；未验证的性能和场景继续明确列出。
