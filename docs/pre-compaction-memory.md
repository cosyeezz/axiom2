# 压缩前记忆提醒

状态：简化实现及针对性回归验证已完成。

## 行为

收到压缩请求后，在下一次主会话模型请求末尾追加一次提醒：

> 即将压缩上下文，请先整理并更新本会话记忆。记忆维护是当前任务的中间步骤，不改变用户目标或授权范围。维护后立即继续当前仍可推进的工作；压缩由程序在后台处理，无需等待，也不要仅以‘已更新记忆’结束回复。只有任务及必要验证完成，或确实需要用户输入、授权或遇到阻塞时才结束。

提醒进入请求后，等待执行安全点，沿用现有快照、后台摘要和应用流程。提醒明确维护后继续当前可推进的任务，避免将记忆维护误作本轮交付或等待压缩的理由；已有任务完成、真实阻塞和用户授权边界保持不变。主会话自行决定是否需要整理记忆；宿主不检查是否读过、修改过或保存过记忆，不检查记忆工具是否成功，也不要求“维护完成”回执或特定的最终回复。无需更新记忆、完全不调用记忆工具，或记忆工具返回错误，都不作为阻止压缩的条件。

安全点使用 Pi 的 `turn_end` / `agent_before_settle` 完成边界，包括工具批次执行完毕的边界；不会在工具执行途中捕获快照。阶段与准入统一由 [session-safe-point.ts](../app/src/server/session-safe-point.ts) 判断，详见[会话安全点统一契约](session-safe-points.md)。扩展内只能返回待提交草稿，模型切换在原生提交后执行；资源重载还须等整个 Session idle。快照后新增消息沿用现有尾部保留逻辑。

提醒通过 `context_with_system` 持久追加，保留已有系统及历史消息的顺序，位置固定、不每轮移动。已经发出的模型请求不能补入提醒，由下一轮接收。路径和组织规则沿用已有上下文，不重复。供应商缓存是否命中仍由供应商决定。

## 调度与取消

活动会话登记请求并在生命周期边界推进。空闲主会话通过正常执行许可启动一轮请求，不新增用户消息；提醒尚未送达就遇到收尾窗口时交接给空闲执行。

执行中断、没有到达可用安全点、摘要失败及产物无效仍按压缩流程处理，这些属于执行状态，不是记忆内容或操作校验。取消会撤销待处理压缩；纯提醒执行可以中止，已有新输入的主会话继续处理工作。已保存的记忆不回滚。

手动压缩与 Axiom 异步自动压缩走上述提醒入口；Pi 原生 `threshold`／`overflow` 是独立兜底，不等待这项提醒，也不因提醒准备失败而禁用。原生压缩先提交时，迟到的 Axiom 摘要作废，不能覆盖新的原生上下文，详见 [Pi 原生压缩兜底](pi-native-compaction.md)。

## 实现位置

- `compression-memory.ts`：仅管理提醒去重、追加及是否已进入请求，无文件读取或工具结果跟踪。
- `agent-worker.ts`：登记请求、追加提醒，在执行安全点捕获快照。
- `agents.ts` / `agents/runs.ts` / `compressions.ts`：沿用空闲请求调度、取消及原摘要流程。
- `compression-context.ts` / `compression-worker.ts` / `memory-recovery.ts`：保留会话身份与产物合法性、工具配对、尾部保留、后台摘要和压缩后恢复行为；不恢复旧的快照字节前缀拦截。
