# CLI Provider 技能通用化验证合同

## 问题与范围

将Kiro专用技能改名为cli-native-provider，整合REA的相关定位/证据工作流，形成可复用的CLI供应商原生接入流程及模板。验收的是文档、历史保全和技能发现，不是任何供应商或REA运行效果。

- 允许：新增技能/参考/模板、归档旧6文件、更新两份普通文档引用、只读加载Pi技能解析器和包发现器、隔离临时目录、保存白名单文件SHA/验证结果。
- 不允许：修改生产/依赖/安装配置、运行官方目标、调用模型/受保护接口、抓包、重启、运行旧case/verifier、读取凭据或生成带secret的证据。REA集成只据已安装6.8.0技能方法整理，不调用分析工具。
- 旧docs/evidence/kiro-macos-transition三文件保持原字节；原路径变化通过source-snapshot.json映射，不改旧manifest伪造历史验证。

## 成功判据

1. 新技能frontmatter合法、名称与目录一致；当前Pi1.4.0 parser无diagnostics，repo/app两个cwd的隔离package discovery均能找到唯一新技能。
2. 主技能、参考及模板中的本地链接可解析；没有硬编码个人目录/临时凭据/旧case执行指令。供应商个案不得成为通用默认模型/UA/重试参数。
3. 旧6文件归档SHA与操作前一致；3冻结证据SHA不变；普通迁移文档可达新入口。测试不加载扩展、不联网、不触发真实模型。
4. 内容走查覆盖源码充足/JS bundle/native目标/REA不可用四条入口，含全授权链、独立Provider、SDK适配、取消和重试归属、分层验收及停止规则。

## 预算与失败动作

新验证脚本每次≤60秒；只读指定文档和已装Pi，外部网络调用0、目标执行0；每个结果文件只保存一次，不覆盖失败。格式/链接/夹具错误可修正后重跑受影响检查并保留旧结果。不能把文档校验失败转化为旧供应商实验重试。

验证顺序：文档冻结后并行运行结构/发现检查和独立diff检查；期间不改被测文件。必要修复后只重验受影响范围。最终保存实际命令、退出码、覆盖和限制，不声称当前会话热加载或通用接入成功。
