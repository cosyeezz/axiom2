## 1. Transport: significant target difference, not a proven URL-path difference
- Factory `mMi` (char ~7,874,850; `client-factory.js.txt`) creates `Bge` KiroRuntime client with region `e.region || t.region || us-east-1`, endpoint override or `https://runtime.${region}.kiro.dev`, token from `authProvider.getToken()`, adaptive retry strategy, custom user agent and proxy-aware request handler. Calls `Uge` custom event-stream deserializer and shared header middleware.
- Runtime configuration (`runtime-config.js.txt`, char ~5,478,940) explicitly selects `protocol: ... ?? Lht`, service target **KiroRuntimeService**, bearer auth. `rpc-serializer.js.txt` establishes Lht = awsJson1_0; RPC serializer starts path `/`, updates endpoint, method POST; derived serializer appends slash, sets `content-type: application/x-amz-json-1.0`, `x-amz-target: ${serviceTarget}.${t.name}`.
- Therefore default shared runtime request statically resolves target **KiroRuntimeService.GenerateAssistantResponse**, JSON RPC at runtime root. Axiom `kiro-chat.ts:142-148` sends **AmazonCodeWhispererStreamingService.GenerateAssistantResponse** to `kiroChatEndpoint` runtime root. This is a directly evidenced desktop/shared target mismatch.
- IMPORTANT: SDK operation schema DOES contain POST `/generateAssistantResponse` (`wire-operation.js.txt`), but active runtime default is RPC Lht, not REST. Do NOT recommend changing Axiom path solely from the schema trait. The earlier broad SDK snippets can otherwise mislead.
- Axiom region uses profile ARN region else us-east-1 (`kiro-catalog.ts:30-35`), desktop factory uses configured/auth-provider region; these are not equivalent selection rules. No claim that either region is universally wrong.

## 2. Request envelope and origin
`request-command.js.txt` char 5,606,870: `_streamResponseChunksOnce` creates `new pAi({conversationState:t, profileArn:await authProvider.getProfileArn(), additionalModelRequestFields:e.additionalModelRequestFields, agentMode:this.agentMode, systemPrompt:s})`. Nonstream `_generate` has same envelope.
`conversation-builder.js.txt` char 5,615,095 builds conversationId, rootConversationId, agentContinuationId, agentTaskType, currentMessage:last, history:all-but-last, chatTriggerType:MANUAL. Axiom protocol lines 178-180 has only conversationId, MANUAL, currentMessage, conditional history and profileArn; no root/continuation/task/agentMode/top-level systemPrompt. Their absence is a difference, not evidence all fields are mandatory.
Origin mapping (`origin-map.js.txt`): kiro-ide=>AI_EDITOR, kiro-web=>KIRO_WEB, kiro-cli=>KIRO_CLI; default AI_EDITOR except web transport/context. Converse class default origin is AI_EDITOR and factory allows explicit origin. All converted human/tool turns get modelId and origin, and current turn is restamped after sanitization. Axiom uses KIRO_CLI and stamps modelId on current turn only. Presence of KIRO_CLI mapping is NOT CLI execution evidence.

## 3. UUID provenance — distinguish the identifiers
- Execution (`execution-identity.js.txt` char ~5,436,500): conversationId = t.conversationId ?? t.chatSessionId; rootConversationId = sessionServices.rootConversationId.
- Serialization (`history-identity.js.txt` char 4,809,409): every LangChain message receives additional_kwargs conversationId/rootConversationId; optional continuation/task metadata.
- Builder scans original messages in reverse for latest conversationId; if missing uses **crypto.randomUUID()**. Root scans similarly, defaults to selected conversationId. It logs fallback accounting if either metadata missing. No evidence these are machine IDs.
- Auxiliary bmt/bQ (`aux-uuid.js.txt` char ~4,921,350) use node crypto randomUUID default for separate invocation conversation IDs and retain supplied root.
- SDK invocation ID is independent: retry middleware stamps headers[iwl]=Tyr() once before retry loop and updates attempt per iteration (`sdk-retry-uuid.js.txt`, char ~4,181,300). iwl is amz-sdk-invocation-id. Tyr=Ovl(getRandomValues); Ovl prefers crypto.randomUUID, otherwise random 16-byte UUIDv4 with version/variant masks (`uuid-generator.js.txt`, `uuid-binding.js.txt`).
- Axiom: conversationId is deterministic SHA256(namespace + sessionId), sliced 32 hex and hyphenated (no UUID version/variant masking), else randomUUID (`kiro-chat-protocol.ts:178`); invocation header independently randomUUID (`kiro-chat.ts:146`). Cannot infer server UUID validation from this difference.

## 4. System and history
- Builder extracts first human message as top-level systemPrompt ONLY when t.length>1 and feature `system_field_injection` is enabled; removes that message from wire history. First content is concatenated text only, no explicit system-role conversion at this point. Feature default false (`feature-defaults.js.txt`); account/experiment override unresolved.
- With extraction disabled it leaves messages in conversation history. Upstream `nte` inserts an AI “I will follow these instructions.” after a forced first message when second is human (`system-ack*.js.txt`); conditionally present, not a universal acknowledgement requirement. Same-role merge exists upstream in `yU/k6o`.
- Axiom collapses Pi system messages then injects `<axiom_system>...` in first user; no fake ack, no top-level field. This differs from either desktop representation, but desktop cannot justify replacing Axiom identity or policies.
- Desktop sanitizes history with xAr, including synthetic Hello/Continue/understood, reorder/merge tool results, duplicate removal, synthesized error results for missing calls (`history-sanitize.js.txt`, `tool-constants.js.txt`). Axiom does strict pairing, rejects many invalid histories and omits outstanding calls at normalized user boundary with explicit Axiom recovery policy. Desktop recovery semantics are not safe drop-in fixes.

## 5. Tools and images
- Desktop assistant toolUses {toolUseId:id,name:$N(name),input:args}; $N normalizes invalid characters to underscore and truncates to 64; collision helper rQo adds numeric suffix. Axiom aliases invalid names with truncated name + SHA suffix. Both preserve tool IDs and structured args. Desktop specification converter supports multiple LangChain/OpenAI-style tool shapes and fallback descriptions; J0r normalizes JSON schema (drops title/default/examples/$id/$schema and unused defs, defaults type object, nullable-array normalization). Axiom expects object JSON schema and preserves it. Do not infer service requirement from normalizer.
- Desktop results afu: {toolUseId,content:[{text:fFe(content)}],status:success===false?error:success}. Tool-result images are lifted into parent userInputMessage.images by serializeMessage; fFe text joins with blank lines. Axiom similarly lifts images, keeps multiple separate text blocks, includes local empty-result placeholder. Shapes substantially align; text segmentation differs.
- Wpu accepts data-URL image blocks, maps png/jpeg/gif/webp, Buffer.from(base64) to SDK bytes; unsupported format throws, URL with no comma logs/skips. SDK image source is blob bytes. Axiom accepts validated canonical base64 and emits source.bytes base64 string (correct JSON blob representation), supports same four plus mime alias image/jpg. Desktop also supports documents (not Axiom image-input union). No evidence to weaken Axiom validation.

## 6. Thinking / effort
- Current desktop discovers enum/default from model.additionalModelRequestFieldsSchema, searching properties.output_config.properties.effort then properties.reasoning.properties.effort (`effort-catalog.js.txt`, `effort-builder.js.txt`). OAt produces ONLY {output_config:{effort}} or {reasoning:{effort}}; modelStream2 supplies when model.effortLevel AND effortSchemaPath exist. No `<thinking_mode>` or budget_tokens occurrence in this bundle. Absence is scoped to this artifact, not all Kiro clients/backends.
- Desktop signed native reasoning replay sfu requires same originating reasoningModelId as current model: redacted=>Uint8Array from base64, otherwise nonempty reasoning text + string signature=>{reasoningText:{text,signature}}. Unsigned reasoning or model mismatch is dropped. Response reasoning events preserve text/signature/redacted, and retry can strip reasoningContent after THINKING_SIGNATURE_INVALID. See image-and-tools and request-assembly exploration file for full sfu; focused excerpt includes its implementation.
- Axiom kiro-thinking.ts uses static ID profiles/budget defaults; adaptive mode adds both XML-like prefix and output_config effort; budget mode uses prefix only. Axiom catalog does not consume effort schema (descriptor lines54-71). Axiom deliberately omits all historical thinking/signatures in protocol lines74-96. Current desktop supplies evidence for schema-driven effort and signed same-model native history, but NOT support for arbitrary model IDs, budgets, or cross-client replay compatibility.

## 7. Headers and auth boundaries
- Shared bearer signer sets Authorization Bearer token (`bearer.js.txt`); runtime content type/target above.
- C5o sends x-amzn-codewhisperer-optout:true only when content collection disabled (factory default disabled); Axiom always true. $C maps external_idp=>EXTERNAL_IDP, machine_token=>KIRO_MACHINE_TOKEN, api_key=>API_KEY, IdC=>SSO_OIDC; other methods omit TokenType. Axiom methods builder-id/identity-center/social have no direct shared enum mapping and no TokenType header. Do not equate labels without auth-provider provenance.
- Shared optional x-amzn-kiro-client-attribution from callback; shared x-kiro-attempt=`attempt;max=N` derived from SDK amz-sdk-request and strategy, adaptive retries. Axiom only amz-sdk-request attempt=1;max=1 plus independent invocation UUID and fixed Axiom UA. Actual shared UA depends on caller/getCustomUserAgent and SDK; not resolved to a literal device identity.
- Request schema models agentMode as x-amzn-kiro-agent-mode header, but command supplies agentMode and active serializer is AWS JSON RPC. Exact placement of this modeled member in serialized wire was not fully traced; do not claim header presence from schema alone. Axiom has neither field nor header.
- Axiom auth source was inspected for interface and endpoint constants only; no stored credential was read. This report is not an OAuth parity audit.
