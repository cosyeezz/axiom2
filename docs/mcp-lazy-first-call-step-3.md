# MCP 按需接入 · 第三步：缓存发现与首次调用交接

**状态：设计定稿，尚未实施到产品。** 本轮仅交付方案与验收标准，不修改功能源码、不请求真实 MCP/模型、不安装依赖、不编译部署或切换默认连接策略。

前置为[第一步：会话内可控登记](mcp-session-control-step-1.md)的 A01–A15，以及[第二步：工作空间工具目录缓存](mcp-tool-catalog-step-2.md)的 B01–B23 工程验收。前两步文档和此前内存假传输可行性验证，不替代正式产品验收。

## 1. 目标与边界

把前两步接成“模型发现 → 首次调用 → 按需连接 → 原生执行”闭环：

```text
获准且有效的缓存目录 → Pi 工具占位定义（stub）→ 原生发现
                                              ↓ 首次调用
                                当前授权/配置复核 → 激活目标服务
                                              ↓
                         当前真实工具 gate → 原生管线校验并执行
```

- Axiom 只协调发现投影、激活时机和一次交接；Pi 仍负责 MCP 传输、握手、真实发现、工具注册、参数校验和调用。不增加另一套 MCP client、调用网关或跨会话活连接池。
- 目录可见、占位工具可执行、真实工具已就绪是三个不同事实；占位工具 callable 只表示可进入受控激活路径，不表示后端已经在线。
- 相同 Pi 会话首次连接后复用原生工具；其他会话仅共享目录，各自持有连接。
- 本步不实现 Skill B、执行池身份重构、idle 回收、新前端面板或用户扩展安装体系。资源读取/资源正文不进入本次缓存工具交接范围。
- **生产默认预连接暂不切换。** 空初始激活是受控测试宿主的初始策略，不新增面向用户的模式开关；默认上线另行授权与验收。

## 2. 当前依据与实现入口

核查基于安装的 **Pi 1.1.0**；实施时按第二步正式快照能力的实际版本重核，不能假定未来版本的注册/调用语义不变。

- [capability-resources.ts](../app/src/server/capability-resources.ts) 是现有会话 factory 接入点；第一步须先解决空激活安装、动态登记与来源/REA 传输兼容。当前产品仍是选中服务预连接，尚无本文控制器或 stub 集成。
- 同一 factory 的 `registerTool` 同名登记覆盖自身 Map 并刷新注册表；不同 factory 同名可能首个胜出。stub 与原生 MCP 必须共用同一工具所有权，不依赖跨扩展抢名。
- `ctx.executeTool(name, args, { signal, onUpdate })` 重新读取当前 callable 工具表，走参数校验、权限钩子和原生 handler；不能直接调用真实定义的 `execute` 绕过管线。
- Pi 在调用钩子之前已选定工具 handler；仅在 `tool_call` 钩子里换定义不能把当前调用自动切成新 handler。首次交接必须发生在 stub 自己的执行中。
- Pi 不提供“同名祖先调用自动防递归”；覆盖失败必须主动识别，不能指望嵌套记录数上限阻止递归。
- 原生工具通常不能真正 unregister；退役 stub 须登记为 hidden 并保留拒绝执行的代际检查，不能仅删宿主 Map。

实际代码布局在实施时确定，建议在第一步控制器旁增加会话级 `mcp-lazy-tools` 模块，负责投影、stub 身份、调用交接与退役；第二步继续独立负责持久化。内部对象不是产品插件系统，不新增 HTTP/WebSocket 调用协议。

## 3. 缓存投影与原生发现

### 3.1 占位定义准入

每次会话绑定/原生 reload 先读取第二步按当前会话过滤的目录，只接受身份、格式、生产者规则与配置/权限分区匹配且 fresh 的快照。

从可信宿主下发的元数据建立 stub，记录私有的工作空间/服务身份、原始工具名、缓存原生名、snapshotRevision、配置/授权 epoch 与 stub 代际；这些身份不作为模型可传参数。只复制已校验的描述、规范化 schema、允许的 annotations 和 `{ name, description? }` namespace，不注入缓存中的 instructions、配置或秘密。

- hidden、未选中、未授权及被工具过滤排除的项不投影为可发现/可启动的 stub。
- direct、deferred、codemode 继续使用当前 Pi 曝光/激活规则；direct 仅在当前 active/allowlist 允许时可调用，不为使 stub 可达而扩大 active tools。
- 不把 deferred/codemode 全部升成 direct，不把全量 schema 塞进系统提示词；缓存 annotations 不提供授权。
- 缺失、过期、损坏、身份不明或不可跨会话复用的目录不生成当前 stub；通过第二步显式发现/刷新流程恢复，不隐式扫描全部服务。

### 3.2 名称与所有权

缓存原生名只是候选。投影前检查当前 registry/命名环境，不能覆盖其他服务、内置工具或外部 factory 的同名定义；发现冲突则拒绝该工具投影，返回脱敏目录诊断，要求显式刷新/重建投影。不得自行复刻 Pi 命名哈希算法、按 label 反推原始工具名或注册另一个隐藏调用别名。

本步采取保守策略：真实发现后若同一原始工具的实际原生名与 stub 名不同，本次调用报“工具目录已变化，需要刷新”，不自动改名交给另一个工具。记录最新映射供第二步提交，待安全更新投影后由模型重新发起调用。

### 3.3 复用现有发现入口

通过注册表使 stub 进入 Pi 原生 codemode 的 `searchTools/describeTool/describeNamespace/ALL_TOOLS` 和 deferred 的 tool_search 发现，显式验证当前策略允许的原生发现入口处于 active；不为 lazy 强行开启原本禁用的入口，不另造搜索工具或改写脚本协议。不得为了列出 dormant 服务把它们提前塞进原生 enabled MCP 集合。codemode 持有本次脚本开始时的工具声明/输出契约快照，真实注册刷新不会自动更新已运行脚本，因此输入和输出契约都必须在首次派发前核验。

零连接保证针对目录/占位发现不新增激活。Pi 对**已经激活**服务的原生就绪等待仍保留；不能宣称其他服务正在连接时，所有搜索都必定立即完成。需用真实 codemode 解释器和 tool_search 验证 dormant 工具确实可被发现，不能只检查 `getAllTools()` 或手工调用 stub。

## 4. 首次调用交接契约

### 4.1 执行顺序

1. **外层原生入口**：Pi 对 stub 按缓存 schema 校验并执行权限钩子；拒绝时 stub handler 不进入，零激活。
2. **调用准入**：stub 捕获本次调用身份、signal、当前 run 授权与连接绑定，复核当前工作空间/服务授权、配置/权限 epoch、过滤和缓存可用性。signal 已取消、目录已过期或身份失效时不激活；普通 TTL 变化不影响已经由当前原生真实定义接管的工具。
3. **激活与等待**：复用第一步的同服务 single-flight，等待本次服务/代际的真实目标定义已登记且 callable。注册 API 返回 void、事件结束或第二步缓存存在均不能代替该 gate。
4. **防递归与身份核验**：确认当前注册表目标不是任意 stub/旧定义/外部同名定义，服务身份、原始工具名、实际原生名与当前 generation 对应；规范化输入和输出 schema 摘要均与该调用使用的 stub 契约一致，检查本调用交接次数尚为 0。任一失败有界退出，不再次执行 stub。
5. **原生内层执行**：创建调用级交接上下文，立即调用 `ctx.executeTool`，原生按真实 schema 再校验同一份参数并重新执行权限/调用钩子。不得直接执行 handler、静默修改参数或跳过第二次校验。
6. **结果与清理**：传播原生结果、isError、进度和取消；释放本调用等待器/监听器及交接上下文。后续新调用直接命中原生真实定义。已提前选中的旧 stub handler 可以完成一次受控交接，但不得再登记 stub 覆盖真实工具。

### 4.2 调用级代际保护

只有在交接前查询一次 generation 不够：内层工具选择、权限等待、取消/reload 可能交错。必须将调用开始时的服务身份与配置/授权 epoch 绑定到**本次调用**，在真实 handler 入口、实际原生派发前再次检查；失效则拒绝，不能把旧调用悄悄迁到替换后的服务配置。

可采用经过并发验证的宿主调用上下文或窄的原生前派发观察/校验入口；具体载体实施时确定。不得把令牌塞进模型参数、使用会话全局 `currentCall`，或在迟到回调中重新贴新 run lease。真实定义的安全包装只能做本代际准入并委托原生 handler，不能替代原生工具管线。无法可靠关联调用与代际时视为实现阻塞，不以“通常不会 reload”放宽。

**旧脚本也可能绕过 stub：** 并发调用先用新 schema 覆盖定义后，持有旧快照的脚本再按名称调用会直接命中真实工具；同一脚本后续调用也可能遇到再次刷新。因此必须把脚本实际捕获的工具契约身份沿可信调用上下文传播至每次真实派发，涵盖不再经过 stub 的调用，并对照当前目标的输入/输出契约；不兼容时业务 call 为 0。不能从派发时的当前注册表反推旧脚本身份，不能仅保护第一次 stub 交接。该载体也是必要前置：须用经验证的宿主包装捕获与 codemode 完全一致的快照，或在受维护 Pi 源码提供正式窄快照/派发钩子；公开 `ctx.executeTool` 本身不携带这一身份，未解决不能验收。

入口检查不能冒充最终派发检查：REA 预算/控制调用、原生 getClient 或既有恢复重连仍可能 await，之后每次实际 `tools/call` 发送前都须核验本调用准入与连接绑定。若宿主包装无法覆盖这些内部等待，所需正式窄派发校验钩子也是实现前置，不深导入或接管协议来绕过。REA 内部受控子调用须按自己的真实目标检查当前绑定/许可，不能误用原业务工具名的一次性交接令牌，也不能借此放宽权限。

**防递归至少三重约束：** 当前真实定义身份检查、调用级最多一次 stub→真实交接、拒绝该调用重新进入任意 stub。不能用服务级布尔锁阻止递归而误伤十路合法并发。

### 4.3 schema 变化与失败语义

- 缓存 schema 可能先拒绝本来适用于新工具的参数；这是缓存入口校验的已知限制。保留原生验证错误，由既有显式刷新流程恢复；本步不承诺未执行的 stub 能附加提示，也不为提示新增前置拦截器，不放宽 schema 或为此自动启动服务。
- 本步对输入/输出契约变化采取保守策略：即使参数碰巧仍兼容，只要规范化 schema 摘要变化（含输出 schema 的有无变化），本次调用就要求刷新并重新发起，业务 `tools/call` 为 0，避免旧 codemode 快照用错误输出契约解释已产生副作用的结果。摘要一致也必须再走原生实参校验；后续验证错误原样保留，不能因比对过摘要就绕过验证。不得自动改参重试。
- 真实工具已移除、hidden、过滤排除、direct 未 active、名称漂移或代际变化均不交接；完整真实目录同步触发第二步更新/失效。
- 连接失败、鉴权未完成、目标未出现等按第一步有界返回；公开信息不足时只报告脱敏的目标未就绪，不编造精确根因。
- 本步不增加业务自动重放。既有 Pi 协议 session 恢复和内置 REA 已审计恢复策略须单独保持、计数和披露，不能声称整个底层严格 at-most-once。已发出的调用可能已产生副作用，取消/超时不保证回滚。

## 5. 并发、退役与生命周期

- 同会话同服务/配置十路首次调用共享一次建连，但每个调用各有参数、signal、期限和结果。不同服务不能共享全局成功/失败 gate。
- 某等待者取消或超时仅结算该调用，不关闭其他调用需要的连接。最后一个等待者退出后，连接仍按第一步生命周期管理，不新增自动 idle 回收或重试。
- 激活等待、真实 gate 与嵌套排队均纳入宿主可配置的调用准入总期限；测试用短期限/假时钟，不把旧可行性测试的 250ms 当产品默认。Pi 顺序嵌套队列不保证取消时立即出队：若宿主有界返回，必须同时失效本调用准入，让以后排到的真实 handler 在派发前拒绝，观察并收尾后台 Promise。不能只 Promise.race 返回超时而留下日后执行副作用的队列项。
- 显式传递内层 signal 时必须合并/保留外层 signal 与本次期限取消；不能用新 signal 替换后丢失父调用取消。业务派发后的执行期限仍沿用原生工具/会话策略，不因首次连接而擅自改写。
- 授权撤销、配置替换、服务停用、reload、换绑和 shutdown 使相关 stub/等待者/调用上下文失效；旧代际回调不能放行、重登记或改写新状态。
- 第二步 TTL/目录失效时仅退役仍属于该快照的 stub；不得把同名已被原生真实定义接管的工具重新 hidden，也不因目录过期关闭正在使用的连接。替换/退役前必须检查当前定义所有权与身份。
- 真实完整快照到来后，用原始工具名和正式映射核对所有本服务 stub。真实列表中缺少的 stub 主动 hidden 且拒绝执行，不能让已经被选中的旧 handler 在撤回后重新启动服务。真实新增工具沿用原生注册。
- 主动停用但仍获授权的服务，不因恢复 stub 就被旧调用自动重新激活；本代际调用失败，是否重新启用由后续明确操作决定。授权撤销则始终禁止激活。
- worker idle 保留连接遵循第二步连接绑定身份，不能依赖已结束 run lease。新 run 的业务调用仍须有当前执行授权；不存在跨 run 复用旧业务调用许可。

## 6. 结果、钩子与可观测性兼容

### 6.1 不改造结果协议

交接必须转发 signal/onUpdate，返回包含原生 `outcome.result` 内容及 `outcome.isError` 的工具结果，不把失败 outcome 误当成功，也不把工具业务错误一律转成宿主异常。保留 content、details、structuredContent/图像相关结果语义和 Pi 输出 schema 适配；不重复拼装 MCP `CallToolResult`。

多层调用保留真实 parentToolCallId/nestedCalls。当前 [agent-worker.ts](../app/src/server/agent-worker.ts) 转发 tool 事件尚未保留 parentToolCallId，本步须补既有事件链的可选父子关联字段与消费兼容，而不是声称现有 UI 已能正确归并。进度可同时出现在原生内层事件和外层 onUpdate，不能将两者作为两次业务执行或重复写入同一展示流；嵌套 usage 已由 Pi 累计，外层不得再次相加。不吞掉有用进度。单独验收 direct、tool_search 加载后直接调用以及 codemode 结构化结果、错误和取消。

未知工具、参数校验失败和权限拒绝等提前退出不保证触发 tool_result 钩子；审计/清理须依据实际 outcome 与生命周期完成，不要求不存在的事件，也不补发伪造成功事件。

### 6.2 承认额外嵌套，不承诺零行为影响

首次调用会多一层 stub→真实工具的嵌套记录与权限/调用钩子。内层仍必须重新授权；不能把外层允许当成内层永久许可，也不静默跳过现有安全钩子。任一层拒绝都不得发送业务调用；内层拒绝时连接可能已经建立，不能误报零连接。

为自有计数/预算区分“发现占位/交接尝试”和“实际业务派发”，同时保留底层原始事件用于审计。真实 REA 工具继续经过[REA policy](../app/src/server/integrations/rea-tool-policy.ts)，stub 不套同一业务预算包装，防止预算锁/设置控制调用重复；不得绕过真实工具 policy。普通成功场景须证明无额外 REA 业务/控制请求，既有明确恢复例外另测。

若当前事件消费者或权限插件存在依赖单层调用的副作用，实施时必须验证兼容，无法保证时作为上线阻塞记录，不以隐藏嵌套或绕过原生管线掩盖。不得让同名真实定义的注册刷新造成 stub→真实→stub 循环。

## 8. 验收方案

### 8.1 分层与授权边界

1. **投影/控制单元测试**：合成快照、假时钟/调用上下文，验证权限、身份、退役、防递归和清理；禁网络/子进程。
2. **真实 Pi + 内存服务端**：正式依赖、真实 AgentSession/原生 MCP/工具管线；直接 driver 与真实 codemode 解释器分别测，合成 assistant 消息不算模型端到端。禁真实网络/子进程/模型。
3. **受控模型 fixture + worker**：独立临时根目录、受控回环 HTTP 模型输出工具调用，模拟 stdio 或内存 MCP；验证模型声明/搜索/执行链及历史记录。明确有本地请求/模拟子进程，不访问用户配置和凭据。

真实/付费模型、真实 MCP/REA/OAuth 验证须单独授权，未执行就列未覆盖。用 fixture 证明工程链路，不声称真实模型的工具选择质量或真实服务稳定性已验收。

### 8.2 必须通过的用例

| ID | 场景 | 验收断言 |
| --- | --- | --- |
| C01 | fresh 目录、空激活宿主仅发现 | codemode search/describe/ALL_TOOLS 与 tool_search 可找到获准 stub；start/initialize/list/call 均为 0 |
| C02 | 单工具首次调用（单页 fixture） | 仅目标服务 start/initialize/list 各 1，正常业务 call 1；真实 gate 后执行并返回预期结果 |

| C05 | 两服务交错、一服务失败 | 成功服务独立调用；失败有界退出且 call 0；不借用他方就绪信号 |

| C08 | 单等待者取消/超时及会话关闭 | 本调用及时结束且未派发；他人仍成功；shutdown 拒新激活、关闭并清理；派发后取消不声称回滚 |
| C09 | 输入/输出 schema 不一致及原生再校验 | 缓存先拒绝时不激活；输入/输出摘要变化即业务 call 0，即使参数兼容也不派发；覆盖并发先注册真实工具、旧脚本后调用，以及同脚本后续调用前再变更；摘要一致仍原生校验，无改参/重放 |
| C10 | 名称漂移/冲突、跨 factory 同名、工具撤回 | 不误覆盖/误转交；原始工具映射核验；缺失/hidden stub 退役；已选旧 handler 不能重新激活 |
| C11 | 错误覆盖或人为保留 stub | gate 不把 stub 当真实；每调用最多一次交接，重入任意 stub 有界失败；无栈溢出/业务请求 |
| C12 | reload/配置替换/换绑/ABA/迟到事件 | 调用级身份贯穿权限、REA 预算与原生重连等待至最终派发；旧调用不迁往新配置；受控子调用不误用目标令牌；旧成功/失败/清理不影响新状态 |
| C13 | TTL 失效、目录刷新及真实定义已接管 | 仅当前所属 stub 退役；不得隐藏同名真实工具或关闭在途连接；缺缓存/过期不隐式扫描 |
| C14 | 曝光与 active/allowlist | direct/deferred/codemode 分别验证原生声明和发现；hidden/过滤/未 active direct 不可启动；不强制扩大 active tools |
| C15 | 内容/结构化结果/图像/错误/进度 | direct、codemode 及 tool_search 激活后直接调用均符合原生契约；isError 不丢失、无二次结果转换；取消和进度不重复计作业务调用 |
| C16 | 嵌套事件、历史、权限和预算 | 外层/内层父子关系可追溯；非零 usage fixture 精确断言只累计一次，内层不跳权限；REA 正常路径预算/控制调用无新增重复，恢复例外单列 |
| C17 | worker idle/下一 run/另一会话 | 同 Pi 会话合法复用连接，新业务仍核当前许可；另一会话仅复用目录且独立建连，不共享结果或取消 |
| C18 | 失败、结果不确定与显式重试 | 不新增业务自动重放；失败后遵循第一步显式重试；底层既有恢复行为计数披露，不宣称严格 at-most-once |
| C19 | 不可信目录与状态输出 | 第二步分区/秘密检查/限额保持；模型输出/日志不泄漏配置、HMAC/ticket/凭据；不执行元数据代码 |
| C20 | 默认兼容与 fixture 模型闭环 | 默认预连接不变；空激活路径经模型 fixture 发现并首次调用；REA来源、legacy、无效 reload 基线及 A/B 回归通过 |
| C21 | 顺序嵌套排队取消/超时与无关服务挂起 | 本调用有界退出；队列以后释放也不发取消调用；父 signal 不丢；保留原生已有服务等待但可取消且不新增激活；等待器/异步任务有收尾证据 |

计数基于无恢复的正常单页 fixture；多页 list 次数按页数计，协议/REA 已有恢复例外单列。清理断言包含等待器、计时器、监听器、调用上下文、退役 stub 归属与已创建传输 close 完成，不只看退出码。
