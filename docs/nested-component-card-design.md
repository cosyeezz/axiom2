# 通用嵌套组件卡片设计

状态：递归展示 API 与现有适配器已部分实现，见[实际卡片布局](component-card-layout.md)；下文完整 `Source<T>`、安装实例和安装器注册控制器仍是设计契约，尚未全部实现，不表示当前各安装器已提供独立环境维护接口。

## 已确认的用户要求

- 一组可递归嵌套的小卡片。运行环境、工具依赖、组件依赖，统一归入“环境”；环境子项本身还是同一种组件卡片，可以继续包含环境。
- 主卡与子卡复用同一展示、状态与操作机制。名称字号一致，不因嵌套逐层缩小；操作属于各卡头部、紧跟名称与路径，正文展示信息。外卡完整明显外框包围内部较轻子卡。Node.js 与 npm 在宿主环境中并列；npm 依赖 Node.js，不把展示树画成 Node.js 依赖 npm。通用环境卡仍可继续递归。
- 图标同状态同颜色：默认系统灰色，可用图标交互时中性点亮；选中行灰色，不单独为重装等 primary 操作铺橙底。
- 头部顺序为类型图标、名称及紧邻下方的安装位置、操作、最后的当前／最新或推荐版本；版本来源分离。名称与路径分两行、左对齐、行盒间距仅 2px，窄卡可省略但保留完整提示；版本可移到末行。取消问号详情，描述和必要说明默认展开。每卡容器不足时折叠操作栏，展开仍独占头部一行、版本继续排在其后，不挤进正文。环境、Skill、MCP、依赖组件使用不同类型图标，原选七个组件／操作图形不换。
- 执行区只在活动时按执行器真实阶段显示，不一律写下载中；取消优先。成功／取消不保留完成面板，错误与待核实原因仍须明确。
- 图标位置和默认规则统一，允许接入者覆盖，未提供或无效时使用兜底图标。名称和描述可替换。
- 当前安装版本通过版本读取链接/接口动态取得；检查更新通过另一个链接/接口取得可用版本，与本地安装版本比较。
- 其他操作统一绑定链接或操作函数。新组件只实现契约，不另写一套卡片布局、按钮状态或确认逻辑。
- 不提供日志、历史查询入口，不设置用于承载这些入口的“更多”菜单。本要求不删除执行后端的持久化恢复和安全记录。
- 新接组件不因类型不同而另写页面控制器，差异仅通过数据源、操作适配器、能力与安装责任声明表达。
- 安装者负责卸载，安装在哪里就回到哪里卸载。不以“外部安装”笼统归类，也不默认把发现的文件当成自己拥有的安装。

## 结构

每张卡均由头部、默认展开的正文／必要说明、按需出现的执行／确认区域和递归环境子卡构成。头部名称在上、路径在下，左对齐且仅留 2px 行间距；操作接在这组紧凑信息之后，版本最后且右对齐；留白在操作与版本之间，不将操作推离标题。容器不足时只折叠动作，用具名、键盘可达的开关展开头部独立行，版本仍在最终行；不把动作挤进描述，也不提供问号详情。

缩进、完整边界和留白表达层级，名称字体不缩小。Node.js/npm 是宿主环境中的兄弟卡；其他依赖仍可按真实展示需要继续嵌套。类型图标由显式 kind 提供，不能把展示位置当成依赖边或安装所有权。

卡片没有通用日志／历史查询区或重复版本表。活动执行按真实阶段，失败原因、待核实与破坏性操作确认按需在本卡呈现；不能只靠颜色代替错误原因或确认范围。

## 接入契约

以下为概念接口，不是已经落地的生产类型：

```ts
type ActionKey = "install" | "update" | "reinstall" | "uninstall";

type Source<T> =
  | { url: string; decode?: (raw: unknown) => T }
  | ((context: ReadContext) => Promise<T>);

type Operation =
  | { url: string; method: "POST" | "DELETE" }
  | ((context: OperationContext) => Promise<OperationRef>);

interface ComponentDefinition {
  id: string;                       // 稳定身份，不用名称或数组位置做 key
  name: string;                     // 可替换，同一级和子级使用相同字号
  description: string;              // 可替换的简短说明
  icon?: string;                    // 默认 package；缺失/无效时兜底
  actionIcons?: Partial<Record<ActionKey | "checkUpdate", string>>;

  version: Source<InstalledSnapshot>;
  checkUpdate?: Source<ReleaseSnapshot>;
  compareVersions?: (local: string, candidate: string) => number;
  actions: Partial<Record<ActionKey, Operation>>;

  environment?: ComponentDefinition[];
  dependencies?: DependencyRequirement[]; // 建议扩展：真实依赖边，独立于展示树
}
```

`ReadContext` 提供取消信号和目标端身份；`OperationContext` 还包含组件 ID、安装实例身份、目标版本、revision/确认凭证、取消信号等。`OperationRef` 绑定真实任务身份和状态通道，不能把 HTTP 请求已受理当成操作完成。

`InstalledSnapshot` 至少区分 `unknown / missing / installed / incomplete`，版本可以未知，并携带安装实例引用及修订。没有 version 字符串不能直接判定 missing。

`ReleaseSnapshot` 提供可比较的候选版本、目标平台/渠道与兼容性依据；单纯版本更大不代表允许安装。兼容范围、商业安装器或特定渠道仍由提供方适配。

### 链接或操作的含义

- 读取版本链接返回真实的已安装状态，不拿远端最新版本冒充已安装版本。
- 检查更新链接返回候选版本。通用层比较已安装版本与候选版本；标准 semver 可复用比较器，非标准版本由接入者提供比较规则，不能按字符串排序。
- 普通结构化响应可直接使用统一 schema；已有 API 返回不同结构时使用薄适配器 `decode`，不要求 UI 理解每家安装器的私有 JSON。
- 修改安装状态的链接是操作端点，不是点击任意下载 URL 就当作安装成功，也不允许通过 GET 执行安装或卸载。
- 后台 API、桌面 IPC、系统安装器均可通过 Operation 适配，不要求都改造成 HTTP。鉴权、路径身份校验和确认仍由实际执行端负责。
- 接入方声明操作能力，通用控制器结合当前状态决定可用、禁用、忙碌和禁用原因。不存在的能力不可伪装成可点击操作。

## 相同机制，不伪造相同状态

父子复用的是同一状态规则和控制器，每个安装实例拥有自己的真实快照与任务。父卡完成安装不意味着所有可选依赖已经安装；子卡失败也不能把其他子卡标为失败。

任务定位至少绑定 componentId、installationId、endpointId、scope 和明确的 taskId/attemptId，不能仅凭显示名称或 resource 串把不同目标端的任务拼在一起。版本读取、更新检查与兼容性结果绑定安装修订及检查时间；安装切换后对相关旧结果做针对性失效，不能让迟到响应覆盖新状态。

通用控制器负责：

1. 读取/刷新安装版本，检查并比较可用版本。
2. 为稳定的操作槽位计算可用性、禁用原因、忙碌反馈和焦点/tooltip。
3. 请求确认并绑定目标版本、revision、安装实例身份，执行后按实际任务结果刷新，不乐观改写成成功。
4. 保留未知/中断/失败的可理解状态，不能把它们当作未安装或安全完成。
5. 父子操作涉及同一安装实例、目录或受占用依赖时，复用冲突/准入规则禁用或排队；独立安装实例不因为视觉嵌套就一律串行。

如果父安装器在同一真实任务里处理多个环境子项，应暴露关联任务和分项结果，子卡显示自己的实际阶段。安装顺序、是否联动与回退由安装者明确声明，不由递归 UI 猜测，更不因点击父卡卸载就无条件递归删除全部子项。

## 依赖关系与缺失提示（补充建议）

用户追问依赖 JDK 的组件应如何提示。建议显式记录依赖图，而不是只从卡片嵌套推断；本节仍是设计建议，不意味着已授权自动安装依赖。

```ts
interface DependencyRequirement {
  componentId: string;                       // 需要哪个组件/环境
  required: boolean;                         // 必需还是可选
  requiredFor: ("install" | "run")[];         // 在哪个阶段构成约束
  versionRange?: string;                     // 由提供方声明的版本约束
  capabilities?: string[];                   // 例如需要完整 JDK 的编译能力
}
```

依赖解析另行记录当前绑定的 installationId、目标端/作用域、检查修订和满足/缺失/不兼容/待检查等结果；同名 JDK 装在另一台机器或未被消费端选中，不能视为已经满足。版本范围之外还可检查架构、入口、完整能力及消费者自己的兼容性。

例如“分析组件 → JDK”，JDK 的版本约束由该分析组件声明，不写成所有组件统一要求同一个 Java 版本。当前 REA 下部分分析引擎需要 Java，不意味着整个 REA 主程序安装都必须被这些可选引擎阻塞。

提示与状态规则：

- 缺少必需依赖：消费组件正文显示“缺少必需环境：JDK（所需版本范围）”；对应 JDK 子卡显示真实未安装状态并突出可用安装图标，不增加日志/历史页面。
- 必需的安装时依赖未满足：禁用消费组件的安装图标，同时提供文字原因；不是只给无解释的灰色图标。
- 仅运行时依赖未满足：可以允许安装程序，但显示“已安装，环境未就绪”，阻止依赖它的运行能力，不能谎称程序完全可用。
- 已安装但不兼容：同时显示当前版本和要求，按实际能力提供更新/重装入口；待检查则先检查，检查失败保留原因。
- 可选依赖缺失：只提示对应功能不可用，不阻塞无关程序安装或其他已就绪功能。
- JDK 安装/切换成功后，重新核实其真实状态，并使引用它的相关依赖检查失效重验；确认满足后自动解除对应图标禁用，不自动开始之前被阻塞的安装任务。
- 卸载某依赖前查询反向引用，对仍需要它的组件说明影响；卸载权限仍由安装收据决定。依赖图要拒绝循环，并允许多个消费组件引用同一个安装实例。

因此至少分清三个关系：展示嵌套（放在哪里）、依赖边（谁需要谁）、安装归属（谁负责安装和卸载）。它们互相关联，但不能互相替代。

## 安装与卸载责任

每次成功安装登记安装实例，而不只保存版本字符串：

```text
installationId       安装实例的稳定身份
componentId          被安装的组件
installerId          实际安装者/执行适配器
endpointId + scope   实际安装到哪个端、哪个作用域
location + artifacts 安装位置及归其所有的文件/资源收据
revision             安装身份和配置修订
references           共享时哪些组件仍在使用
```

- 卸载交回原安装者，在原目标端和作用域依据安装收据卸载；后台、客户端、不同机器或不同目录不能混用。
- 展示父子关系不等于安装所有权。父卡引用某依赖，不代表它有权删除其他安装者的安装。
- 共用依赖只有在引用和占用规则允许时才能移除，不重复安装/删除同一实例。
- 归属未知显示“安装归属待确认”；原执行端暂时不可达显示具体原因并禁用破坏性操作，不贴“外部安装”标签，也不越权删除。
- 系统安装器安装的组件应回到该安装器的卸载机制，不以直接删目录代替。商业/交互安装器只暴露经验证的能力。

## 与当前实现的衔接

当前可复用：
- `app/src/client/maintenance/ComponentCard.tsx` 的基础展示、图标动作、原位确认和焦点/防重复机制。
- `app/src/shared/maintenance.ts`、`app/src/server/maintenance.ts` 的真实任务状态、任务身份、持久化恢复与安全门禁；不提供查询 UI 不等于删除这些记录。
- 各现有安装器的 revision/token、目录归属和进程占用检查。

当前缺口：
- 展示层 `ComponentCard.environment` 已是递归 `ComponentEnvironment[]`，`environmentContent` 可嵌入原任务适配器；但下文数据源、安装实例与注册控制器仍未完整落地，不能混同。
- REA/OpenCLI 当前程序与专属 Node/npm 以整体安装/重装处理，没有可直接声称独立存在的环境操作接口。
- 仍需提供完整通用版本源、更新源、操作适配器与安装实例身份控制器；当前递归渲染并不意味着独立维护和联动事务都已实现。
- 当前 component-tasks.ts 按 resource／可选任务编号选取，尚不是统一的 endpoint/scope/安装实例控制器；跨目标生命周期接入前还需完善明确身份选择。
- builtin-operation.ts 已有进程/目录身份和操作收据，cleanup-scope.ts 已将目录身份纳入确认修订；可作安全底座，但尚不是统一的安装者注册与卸载路由。
- 共同发布的程序和运行时可由同一个安装者负责，但如果要暴露独立操作，必须有真实的独立事务或清楚的联动影响确认。

本文不执行安装、卸载、后台重启、部署，也不修改现有卡片或安装器代码。
