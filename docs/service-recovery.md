# 服务重启后的自动续跑

本能力针对**由服务中断的 Agent 主会话及子任务**，不等同于浏览器断线重连，也不适用于安装、卸载、后台压缩等独立操作。

## 触发与调度

- 服务启动在归档活动执行前，事务保存 `service_recoveries` 恢复意图；正常退出也在停止 Agent 之前保存。
- 服务就绪约 2 秒后开始检查，每秒调度一次。主会话续跑与父会话结果通知共同受最多 3 个自动恢复执行的限制；子任务沿用现有全局任务并发和 FIFO 队列。
- 每个会话只保存一个当前恢复意图。新执行、子任务归属、输入交接与旧意图移除在同一数据库事务完成，避免重复重启重复投递旧意图。通知异步收尾只能清除自身原意图，不能删除新执行刚捕获的停机恢复记录；停机取消尚未完成的启动准备时，原意图保留 pending，供下次启动继续。
- 恢复新建 run 并记录 `resumedFromRunId`，不改写旧执行已结束的事实，也不新增一条“继续”的用户消息。

## 子任务与父会话

- 运行中的子任务从绑定的 Pi JSONL 续接；排队且从未交给工作进程的输入可以恢复，图片与技能引用随原输入身份保留。
- 运行中的子任务尚未交接的追加要求也会保留，排在续接控制条目之后；不是只恢复任务最初的正文。
- 子任务保留原队列顺序及工作／总结截止时间，重复重启不赠送新的时间预算。
- 父会话等待子任务恢复和活动执行结束，再恢复自身或处理结果通知。最后一个子任务已完成、但结果通知尚未确认时，也会保存恢复意图；先核对 JSONL 通知标记，再投递尚未消费的结果。

## 安全边界

- 用户已停止、正在停止、普通失败或已完成的执行不会被当作中断执行重新拉起。父会话仍在等待子任务的正常结果通知不属于重跑已完成的子任务。
- 已删除会话、归档工作空间、文件访问未授权等情况会阻止自动恢复，保留原因。模型／配置问题导致恢复未能启动时，保存失败或阻塞事实，不无限循环重试。
- 已交接但无法确认是否消费的追加输入保持 unknown，不自动再发。工具结果缺失时只补充“结果未知”的协议记录，不由宿主重放可能已执行的写入或 Shell 操作。
- 客户端重连只恢复订阅，不重发用户命令。服务端从当前意图与绑定 JSONL 续接，不从旧请求回执重建用户要求。
- 旧版本已经终结、没有恢复意图的历史中断不批量拉起。损坏或缺失的会话记录不静默替换成新对话；父通知因文件不可读而无法启动时保留 blocked 意图及未消费结果，不静默丢弃恢复入口。

```bash
cd app
node_modules/.bin/tsx --import ./tests/vite-assets.mjs --test \
  tests/service-recovery.test.ts tests/service-recovery-windows.test.ts \
  tests/native-retry.test.ts tests/task-reliability.test.ts \
```

测试仅使用临时 SQLite、临时 Pi 配置和 loopback 假模型。覆盖 10 会话分批恢复、连续重启、主动停止排除、运行及排队子任务恢复、未交接追加要求、原预算保留、最终子任务结果通知、通知并发限制、恢复队列幂等、通知收尾与停机捕获交错、停机取消恢复准备，以及缺失父会话文件时的阻塞记录。源码与测试通过不表示当前运行后台已经更新，启用仍需构建并重启后台。
