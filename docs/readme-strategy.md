# GitHub 首页：调研、定位与转化策略

本报告服务于 [README](../README.md) 的改版。调研基于当前源码、仓库文档、GitHub 公开发布与同类项目 README；不把设计目标、上游自述或本地假模型测试当作 Axiom2 的真实生产成绩。核实日期：2026-10-25。

## 1. 先回答：为什么值得试？

推荐定位：**面向长任务的本地 AI 编程工作台。**

主文案：**让 AI 工作，能看见，也能接着做。**

不要把产品仅归类成“支持多模型的聊天客户端”。真正值得解释的是三条相互配合的工作流：

1. **过程可见**：对话之外，有目标、步骤、状态、详情和主／子代理执行过程。
2. **工作可接续**：长对话与压缩之外，有持久化任务资料，减少再次解释背景的成本。
3. **经验可复用**：同一工作空间里已经完成的工作，可以进入索引，供后续任务按需查询。

这是差异化叙事，不是经对照实验验证的“独家能力”。不宣传其他产品做不到。

### 谁更可能留下来？

- 长期维护一个或多个代码库的独立开发者。
- 经常需要“调查 → 修改 → 验证 → 继续迭代”的开发与技术研究人员。
- 希望自行配置模型、工具和本地工作环境的用户。

小团队成员可以用于个人工作，但当前没有多人账户或协同权限体系，不应主打团队协作 SaaS。只想立即开始普通聊天、完全不愿配置模型的用户，不是第一优先受众。

## 3. 首页应该放什么，为什么这样排序？

| 阅读阶段 | 页面内容 | 要解决的问题 |

| 转化与反馈 | 文档、Issues、Star | 用过以后如何继续、求助或关注？ |

### 原首页的问题与处理

原 README 约 150 KB，是很有价值的工程交付资料，但难以承担营销首页职责：首屏先强调阶段验收，随后大量安装、更新、原生差异和实现细节，让读者还没理解价值就进入维护成本判断。

处理不是丢弃工程信息，而是分层：

- [README](../README.md)：价值、场景、上手、必要边界。
- [REFERENCE](../REFERENCE.md)：完整保留原工程说明与验收记录，头部明确历史信息的适用性。
- 现有 `docs/` 专题：机制、权限、限制与当前实现的依据。

保留原发布说明使用的 `#一行安装与客户端下载` 锚点，避免已有 Release 的首页链接失效。主按钮指向可执行安装路径，而不是没有任何客户端资产的最新后台 Release。

### 不能用的词

- “永不遗忘”“无限上下文”“永远不丢任务”。
- “全自动开发直到完成”“多个 Agent 同时改代码且零冲突”。
- “完全离线”“数据绝不上传”“绝对安全沙箱”。
- “精准实时账单”“保证省钱”“速度提升若干倍”。

- 未获得项目许可依据的“MIT 开源”“自由商用”。

## 5. 安装和版本信息的核实

通过 [仓库 API](https://api.github.com/repos/cosyeezz/axiom2) 核实公开仓库、默认分支 `master`，许可字段为 `null`。[最新发布 API](https://api.github.com/repos/cosyeezz/axiom2/releases/latest) 的快照结论：

- 最新正式后台 **v0.4.14**，发布于 2026-10-25；资产含 `axiom2.tgz`、Linux x64／arm64 安装监督器、`SHA256SUMS`，不含桌面或 Android 包。
- Windows MSI／EXE、macOS 通用 DMG 在 **v0.4.13**。
- Android APK／AAR 在 **v0.4.12**，原首页固定 v0.4.9 已过时。
- 根与 app 的 package.json 标记 0.4.1，不适合作为当前已发布版本依据。
- 发布附件清单及校验文件可访问，不等于本次已经下载、安装并验证所有二进制。

首页后台命令跟随 latest，客户端明确固定到存在安装包的版本；后续发布请分别更新，不要把桌面链接盲改为 `releases/latest/download/...`。

一行安装仍需 Node.js 22.19.0+、npm、网络和可写安装目录；OAuth、模型供应商费用、系统安装授权都不能被“开箱即用”掩盖。远程脚本直接执行的风险通过审阅入口和 npm 替代路径说明。

## 6. 视觉素材：现在有什么，接下来最值得做什么？

当前已经提供[工作台示例截图](images/workbench-demo.png)，使用当前真实组件和隔离数据拍摄，明确标注为示例；品牌图使用现有金色展翼源。不复用他人产品参考图、不展示私有会话或 API Key，也不把假数据的完成状态当作真实运行成绩。

**最优先补充的是一段真实的 45–60 秒演示，不是更多功能清单。** 建议镜头：

1. 打开一个可以公开的示例项目，发出明确小任务。
2. 展开主代理过程及子代理调查／验证卡片。
3. 查看实际修改、测试命令和退出结果；不要只拍“已完成”标签。
4. 打开任务树与一条关键决定详情。
5. 演示后续会话查询已经入索引的经验；若演示索引等待，应真实说明，不剪辑成即时记忆。

发布前需核对使用的后台版本、真实模型、项目授权、总费用和脱敏。若加速或剪辑，应注明。演示不是当前 README 完成的前置依赖，不放虚假的“观看 Demo”占位链接。

次优先：三篇短案例，各用“原问题 → 用户输入 → 真实产物 → 限制”四段讲清楚：给旧项目补测试、排查跨模块问题、研究陌生代码库。手机图应在真正安装包与设备上补拍，不把桌面窄窗口伪装成实体 Android 验收。

## 7. 仓库主页配套建议（未代为修改 GitHub 设置）

**About 描述建议：**

> Local-first AI coding workbench with visible task progress, queryable project memory, and main/sub-agent workflows.

**Topics 建议：** `ai-agent`、`coding-agent`、`local-first`、`developer-tools`、`agent-memory`、`mcp`、`typescript`。

Topics 是发现入口，不是许可证承诺；不要因仓库公开就添加带有错误许可暗示的文案。

**Social preview：** 使用现有品牌色与标语制作独立分享卡，文字在小尺寸下仍可读；避免直接缩小整张工作台截图。保持 README 首屏只放必要 Release／Node 徽章，不堆下载数字、Star 曲线、赞助商或缺乏依据的成熟度标签。

**Issue 收集：** 当前用既有 Issues，不新造社区链接。后续可加 Bug／使用场景模板，要求版本、平台、复现和脱敏日志；不要默认要求上传完整会话或凭据。

**许可是信任问题，不是可由文案解决的问题。** 当前 `UNLICENSED` 和缺少项目许可证会影响他人使用、贡献和再分发判断。应由仓库所有者决定授权策略，本轮不擅自添加许可证。

## 8. 如何判断首页是否有效？

不预设改版必然带来增长。先观察用户能否回答：这是什么、比现有工具多解决了什么、怎么试、第一件事做什么、有哪些风险。

可用指标：首次使用问题中安装／模型配置困惑是否减少，反馈是否开始描述具体工作场景，文档点击与可获得的发布下载趋势。GitHub Insights、下载计数和 Star 只是代理指标，不能等同活跃用户或留存；不为测转化默认引入应用遥测。

建议保持一个版本周期的稳定主定位，再根据真实反馈调整首屏或快速开始。不要一次同时更改定位、安装方式和发布渠道后，仅凭 Star 增长断言哪项改动有效。
