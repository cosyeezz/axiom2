# REA 自动环境与资源预算

Axiom 的内置 REA 默认使用自动策略，无需逐项登记环境变量。此策略只作用于内置连接，普通/回退 MCP 不会被改写。推荐版本为 REA 6.8.0。

## 依赖环境

`reaProcessEnvironment()` 统一生成会话、连接检查和组件检查使用的环境：

- 托管 JDK、Ghidra、JADX、WABT 和已配置引擎路径沿用组件记录与现有探测。
- 从继承的绝对 PATH 项、平台常用安装目录发现 Chromium、Rizin、adb、apktool、tshark、capinfos。Linux 额外发现 mitmdump 和 prlimit。PATH 属于后台已有的信任边界，不保证其中的绝对目录或符号链接都不指向工作区；这是发现机制，不是可执行文件安全沙箱。Windows 自动发现仅接受完整盘符本地路径，不探测 UNC、根相对或盘符相对路径；显式配置仍优先。
- 不执行 shell、不递归扫描工作区、不自动下载或安装软件、不改系统环境或后台进程环境。
- 显式依赖环境配置优先，即使配置失效也不静默换成另一个程序；工具最终验证版本、许可和平台支持。路径存在不等于端到端分析可用。
- Chromium 路径用于 REA 要求显式浏览器的能力，例如原生 ES module resolver；不是对所有网站分析能力的统一开关。mitmdump 的版本和 Linux 平台约束仍由 REA 检查。

JADX 新进程自动获得有界的 `REA_JADX_HEAP_MIB`、`REA_JADX_ACTIVE_PROCESSOR_COUNT`。显式较小值保留，超过自动上限的值夹紧。不能扩大已运行 JVM 的堆。配置变化需要新会话或主动能力重载，不在分析中自动重启。

## 预算与生效边界

预算按每次调用时的主机可用内存、Node 可见的容器约束、CPU 以及有界的目标文件 `stat` 计算；不递归扫描目录。macOS 的 Node 只报告空闲页，因此通过固定系统工具 `/usr/bin/vm_stat` 的有界读取估算可回收文件缓存，不计匿名非活跃页或压缩内存；读取失败退回保守的空闲页估算。这仍是可用量估算，不保证下一刻资源不会被其他程序占用。未知目标规模采用小档默认预算（1024 MiB / 300 秒，仍受资源上限约束）。

- 内存预算取总内存的一半、当前可用内存的 60%、扣除系统余量后的可用内存和 8192 MiB 中的最小值。系统余量为总内存的 1/8，限制在 512–2048 MiB。
- 单 worker 堆上限为预算的 70%；初始堆按目标规模为 1024/2048/4096 MiB，并受上限约束。JADX 最多 4096 MiB、最多 4 个处理器并给主机留余量。
- 初始分析时限为 300/480/600 秒；Ghidra 启动至少给 360 秒，最高 600 秒。正则截止最多 30 秒。regex/capture worker 堆分别最高 512/1024 MiB。
- 单个 MCP 请求超时 720 秒，大于受管理的分析时限；另外从已注册工具进入 `execute` 起计 25 分钟总墙钟期限，包含排队、调整、恢复和至多一次安全重试，并预留 7.5 秒用于有界关闭与进程组确认。首次连接/工具发现由 Pi 单独处理，不算在该工具执行期限内。进度通知不延长总期限；该协作式取消依赖工具遵守 AbortSignal，不是操作系统强制沙箱。
- 能力不足（如不足 128 MiB 堆预算）时拒绝生成新 REA 进程环境或启动分析，而不是突破余量。页面保留参考预算并显示不可启动提示。
- JavaScript 与 WASM 优先通过服务器声明的单次调用参数控制；REA 6.8 的 `inspect_analysis_settings` / `update_analysis_settings` 用于其他白名单预算。按 next_operation / next_worker / next_startup 生效，绝不声称会改变活跃工作。
- 修改运行时共享设置前保存原值，操作后恢复；调整和恢复走 Pi 公共 `ctx.executeTool()`，保留参数验证、权限和嵌套工具记录。显式较小的单次预算不因自动重试被覆盖。手动预算调整也不能超过上限。
- REA 6.7 不具备运行时设置工具时，仅使用其 schema 实际声明的已知单次参数；不猜测其他字段。

这些是**协作式分析预算，不是 OS 级内存沙箱**。Ghidra、商业引擎、外部桥接及驻留 JVM 的整个 RSS 不由 JS/regex worker 堆上限约束。空闲引擎仍可能驻留内存，后续操作以届时可用资源重新计算。不会通过关闭隔离、扩大输出缓冲或增加模型 token 来“解决”资源不足。

## 跨会话协调与重试

主会话运行于独立 worker。内置 REA 的实际 `ToolDefinition.execute` 被 Axiom 适配层包装（保留原工具名称/schema/输出/暴露策略），使用同一应用根目录中的 SQLite OS 锁串行调度；不是各 worker 各自的内存 semaphore。锁在实际执行的 `finally` 释放，排队支持取消。不同后台数据根目录的实例是独立预算域，不保证机器上所有程序的全局限制。

锁目录为 `integrations/rea/budget`。记录当前 worker 和 REA 进程归属，不以经过时间撤销活跃锁。进程崩溃后，若旧 owner/REA 进程组仍存在，拒绝重放而不是杀掉未知分析来抢占资源。不会在活跃锁期间卸载/删除锁文件；它不是引擎或程序版本目录的一部分。

自动升档目前仅开放给**已审计 REA 6.8.0 的 `search_strings` / `search_procedures`，且 `mode: "regex"`**。版本绑定到该连接的安装包，不对未知版本自动重放。还须同时满足服务器明确的幂等、非破坏、非开放世界注解，以及真实错误投影 `{error: {code: "resource_constraint", details: ...}}` 中匹配操作、cpu/memory 资源和已知可编辑 `details.limit` 的证据。仅调整 `regex.matching_deadline_ms` 或 `regex.worker_heap_request_mib`，到不超过两倍、REA 契约上限和本地资源上限，并重试一次。报告的有效值必须与本次预算吻合；较小的显式偏好保留。无结构化证据则保留原错误。

REA 的正则资源错误通常标记 `retryable:false`，表示原预算下原样重试无益。本例外依据已审计版本的 worker 在返回前 `finally await terminate()` 的契约，仅允许**改变预算后**的一次重试，不把缺失的清理字段视为通用安全证明。JavaScript/WASM 仍自动分配初始预算及夹紧参数，但不会自动重跑整包分析（可能执行外部工作或包含部分已完成结果）。

不对 provider timeout、传输异常、取消、许可缺失、目标修改、未知清理状态、目标执行或网络动作自动重放。取消/异常/清理未完成时关闭并隔离本次拥有的 REA 运行时，确认其进程组消失后才释放准入记录；无法确认时保留记录阻止后续重复分析，需要关闭原会话或重启后台后检查残留进程。Windows 不能仅凭父 PID 消失确认整棵进程树退出，因此取消/异常后的隔离记录会保守保留；不会自行删除记录抢占资源。不会自动重新分析。

为避免 Pi 隐式重连在排队或执行中换掉进程归属，每个策略实例只接受首次 transport；替代 transport 在 spawn 前即拒绝。取消、异常、断线或手动 MCP reconnect 后，需要主动重新加载技能与 MCP（创建新策略实例），不能靠再次调用旧工具偷偷重启。已关闭/未知 PID 的旧连接在准入前拒绝，不会为它制造阻塞新会话的归属记录。

## 可观察性

内置 REA 页面的“环境与资源”默认显示“自动”，折叠详情提供机器当前参考预算、依赖来源和路径；配套引擎仍由下方组件卡展示。每次调用通过工具执行更新及 result details 的 `reaBudget` / `reaBudgetAdjustments` 记录有效预算和升档原因。完整 MCP structuredContent 与原有输出 schema 保持不变，分页、落盘与结果截断继续由原工具负责。
