## Resident Definitions

A resident definition is `{name,description,usage,entry,files,options,appearance?}`. Register commands/tools in session.start with unique names prefixed by the Mod id. Implement command.run and tool.call hooks using shared business functions/state. `$.store` persists JSON; clock timers are revoked on disable/reload.

Create with `save {id,request:{definition}}`. Update only changed fields with `save {id,request:{revision,patch:{client:"changed source",files:{"register.ts":"changed host source"}}}}`. Omitted fields inherit the draft; file entries merge by path; `null` deletes a field/file. Other object fields replace as a whole. An invalid merged definition leaves the draft intact. Every mutation can advance revision, including install/enable: carry the latest returned revision. A conflict reports current revision/hash; reread and reapply the intended change.

Model draft operations return source-free receipts with `sources:[{file,bytes,lines}]` by default. For a local edit, read `get {id,request:{view:"source",file:"client"|"files/<path>",startLine?,limit?:1..200,revision?}}`. Continue from `source.nextLine` with the same revision; a conflict requires rereading, not joining mismatched versions. Use `get {id,request:{view:"full"}}` when the complete definition is actually needed, and summary receipts for validation/installation/status. `examples` lists names/descriptions; `examples {request:{name:"workbench-pet"}}` reads one full example. Avoid requesting every example source unless needed.

A source window is an excerpt, not a patch. `patch.client` and each `patch.files[path]` replace the complete selected source string: read/reconstruct all windows for that file before submitting it, preserve omitted files, and never save just the visible excerpt as the whole file.

Browser source belongs in `definition.client` (or `patch.client`), as a plain JavaScript function body returning `{inject,apply}`. Template literals, multiline CSS and regular expression literals are supported. `files` contains host modules with valid file paths/extensions; `files.client` is not the browser entry. Prefix CSS classes, keyframes and SVG ids with your Mod id to avoid collisions. This is authoring guidance, not a syntax restriction. Client parse diagnostics report `file`, `line` and `column` when V8 supplies the source location; repair that source with `save.patch` instead of resending the entire definition.

Use letters, digits and underscores in business tool names, such as `my_app_action`; keep registration, tool.call matchers, usage and Chat submissions on that same name. The SDK converts hyphens to underscores when exposing tools to the model. Plugin ids and slash command names can still use hyphens.

Resident definitions also accept category/tags and `storage:{global:JSONSchema,session:JSONSchema}`. Define exact fields for each used scope before delivery. Schemas validate the whole KV object during reads and before commit: a key called data is described by properties.data. Permit an empty initial store, lazily initialize missing keys, and validate each stored record strictly. Invalid or incompatible persisted data must be reported, not reset or hidden by removing the schema.

Return or await the entire asynchronous UI action, including wrappers that catch errors and invalidate. `onPress:()=>attempt(()=>save())` is correct; `onPress:()=>{attempt(()=>save());}` returns before the action completes and its later `$` calls are rejected as an ended Hook. Use `async` plus `await` when the callback has more statements. Do not bypass cancellation or retry an untracked mutation to hide this error.

Resident UI can compose published visual atoms with the same `components:{Row:{id,version}}` declaration and `Component({key:stableItemId,component:'Row',props:{...}})` factory. Keep parent keys stable too: nested layout identity owns child state. The parent runs business functions in CBC Mods; child atoms remain visual-only, with independent timers/actions and view/session/global storage. Examples may return ordered `dependencies:[{id,definition}]`; save, validate and publish those through Component before rendering. Reuse compatible versions when already present, and do not overwrite unrelated ids. `chat-notebook` demonstrates real Chat requests, editable session/global data, nested reusable cards and Markdown export.

For requested sharing, the installed CLI's `plugin export <resident-id> <new-directory>` carries the complete published atom dependency graph in `.cbc-components/manifest.json`, then build/pack/import use the ordinary package path. It does not export user state, KV or permissions. Imported package atoms resolve by fixed version inside that package, never by overwriting the user's global library. Preserve reference/occurrence identities; missing, disabled, corrupt or cyclic dependencies must be repaired before sharing. These are CLI operations, not invented Mods model-tool actions. Do not run sharing or external publishing unless requested.

Independent TypeScript/checked-JavaScript browser package authors can use the installed type-only `@tencent-ai/codebuddy-code/mods/client` SDK. It types declared services, native/child slot props, stores/actions, injected observable hooks and synchronous selectors, without host source or DI imports. Browser runtime remains the existing approved client evaluator; AI authored function bodies still use the tool contract and plain JavaScript, not runtime SDK imports.

Users export directly from functional/appearance details and the atomic library without asking AI. Functional and visual exports download ordinary `.tgz` packages; visual drafts have a package-local fixed root and their complete published dependency closure, not an implicit publish into the source library. Import and approval remain separate. Appearance exports contain only `{format:1,kind:'skin',id,definition}` JSON, including background/tokens, and do not apply the skin. Exports omit user KV/state, mounts, Chat, receipts and grants. Source/defaults are shared exactly as authored, so remove hardcoded secrets before requested external sharing. The management download API is not an additional Mods tool action; do not invent a model `export` call.

Use `Input({multiline:true,rows:5,...})` for notes, drafts or other multi-line content. A Chat transformation should save a separate suggestion when overwriting the user's current draft would be surprising; let the user adopt it directly, checking the original data revision first.

Resident runtime closures belong to the host Mod generation, not each session. Use `$.store.get(key,{scope:'session'})`, `set(key,value,{scope:'session'})`, `delete(key,{scope:'session'})` and `keys({scope:'session'})` for session-runtime data. Omitted scope or `global` uses durable plugin-isolated storage. Session data survives Mod reload/enable/disable until the actual Session runtime closes or the process restarts. Reload revokes old APIs and callbacks, not pending session records. Do not mark a request failed just because another Mod was installed. Updated schemas must validate preserved data. Do not claim per-session runtime isolation from a global closure.

Read `Mods capabilities` for the current host before choosing integrations. Existing host APIs include fs, process.run, http.fetch, model.complete, MCP routing, prompt fill/submit/suggest and UI, subject to approval. CBC `prompt.read()` returns `{text,cursor}` from the current session's latest admitted user query after native assembly; it excludes system context and credentials. Before assembly it returns `{text:'',cursor:0}`. The cursor is the projected text length, not a live composer selection. Native `model.fork` runs a tool-free isolated fork with inherited history/model, but does not wire in-flight caller cancellation or measured usage. Custom functions can be exposed through engine.create additions and invoked with `Mods call`. Audio and credential brokerage are not implemented; `session.authorize()` returns null.

`Mods mount` takes `{request:{revision,kind:'resident'|'component',plugin|component:{id,version}|component:{id,revision},placement:'chat'|'sidebar'|'dock'|'floating',width:120..600,height?:120..1200|null,props?,chrome?:'panel'|'minimal'}}` using the customization revision from skinList. Omitted/null height fits content; numeric height sizes the frame with internal scrolling, not text scaling. Draft component mounts follow current AI edits; published mounts pin a version. Use `updateMount` for placement, size, chrome, props or collapse changes, preserving unrelated mounts. Resident mounts require an enabled plugin. The Web UI supports inline chat, native left agent sidebar, shared workspace dock and floating layers. Sidebar/dock follow their native width and resize height only; opening a sidebar app reveals the native sidebar, not another column. Dragging moves between visible sidebar/dock and floating without recreating the view. `collapsed:true` minimizes the panel into the top bar's named app menu without closing its view or losing input; restoring keeps its position. These are browser surfaces, not OS desktop overlays; a rendered image alone is not a complete pet system.

`dock` uses the Apps tab in the existing workspace alongside files, search and terminals; it never allocates another dedicated sidebar. The user may switch tabs or collapse the workspace while the app remains resident. Mobile users manage these Mods in the Mod Center. Prefer `chat` for an inline helper or `floating` for an overlay when those match the request.

Users manage enable/disable, placement and uninstall directly in the Mod Center. AI is for creating or changing behavior, not routine activation. Display placements are persisted separately from active view resource budgets; do not remove user panels to free your own previews. Uninstall removes the app from the library while retaining recoverable source and business data.
