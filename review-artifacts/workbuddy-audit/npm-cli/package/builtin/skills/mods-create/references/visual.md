## Visual Definitions

Use the native atom factories and their default appearance for ordinary UI; avoid hardcoded surface/text palettes that defeat the current skin. Explicit artwork or brand styles remain scoped to the requested component. Native atoms inherit the renderer's theme; visual components do not automatically receive the browser `ctx.locale` service. If live language switching is required, use a localized browser parent and declared label props, or a contract-supported host language binding. Do not invent an injectable locale API or claim bilingual component text switches automatically.

A component definition is `{name,description,usage,propsSchema,initialProps,blueprint}` or `{name,description,usage,propsSchema,initialProps,entry,files}`. `initialProps` must satisfy synchronous JSON Schema. Source files are complete plugin-local TS/JS/TSX/JSON; no Node or third-party imports.

Blueprint: `{format:1,state:{...},root:{id,type,props,children}}`. Allowed atoms: Box, Fragment, Text, Button, Input, Select, Markdown, Code, Link, Image, Svg, Raster. Only Box/Fragment accept children. A `Component` node references `{component:{id,version},props,children:[]}` using a published version. Node ids are unique letter-led names.

Bind properties with `{$bind:'props'|'state',path:'field',fallback:...}`. Events are `onPress` on Button, `onInput` on Input, `onSelect` on Select, each an ordered array of `{type:'set'|'increment'|'decrement'|'multiply'|'toggle'|'push'|'removeAt',path:'stateField',value?,as?:'number'|'string'}`. Event values use `{$bind:'event',path:''}`. Use source for computations or animation beyond contract-supported actions.

Choose the data lifetime before saving. `view` is isolated temporary state; `session` shares data across this session's views until the session runtime closes; `global` shares durable data across sessions and restart. Blueprint state follows that scope. Source components must use `$.store` for shared/durable data; closures remain view-local. Legacy `persist:true` means global. Reused child components keep independent data by stable node occurrence id, so preserve ids when changing layout.

Define `stateSchema` for user data before delivery, validate realistic inputs and test the app's real effects. Infer a sensible lifetime from the request, such as global for a personal ledger or session for a conversation agenda. Ask about sharing only when the choice materially affects the user's intended behavior; do not require users to understand storage terminology.

For source components the schema describes the actual store object, including exact key names. `$.store.set('data',{tasks:[]})` means `stateSchema.properties.data.properties.tasks`, not a root `tasks` field. Initialize missing required store keys in `session.start` before the first render and preserve existing values. Fix a missing initial key by initializing it, not by dropping required fields or allowing arbitrary properties. Exercise invalid writes to confirm the schema protects the real stored fields.

Use contract-supported `push/removeAt` for collections and `decrement/multiply` for arithmetic. `map:{$bind:'state',path:'items'}` repeats an atom; descendants can bind `item/index` and target `items.{index}.field`. Do not invent unsupported operations; use source when the request needs richer business validation or calculations.

For editable lists assign unique stable item ids and use `map:{$bind:'state',path:'items',key:'id'}`. A mapped `Component` reference creates an independent instance per item, including nested dependencies. Its props are validated each frame. Removing a repeated instance stops its timers; session/global data remains available when that item returns. Keep both node and item ids when restyling an existing composition; omitted key uses indices for fixed lists.

For every blueprint node include `id`, `type`, `props` and `children`, including leaves (`children:[]`); `events` is beside `props`. Use the selected contract example instead of inventing field names. Repair the exact diagnostic path before creating another preview.

Exercise previews through `Component({action:'viewAction',id,request:{viewId,revision,actionId,requestId,value?}})`. Use the current frame's view revision and action ids, not the draft revision; omit value for press. Each reply replaces action ids. `viewGet` refreshes after timer updates and `dropView` releases a test instance. These visual actions cannot perform external business operations; resident actions use their separate runtime API. Track your preview ids and release them after errors as well. At a view limit, use `viewList` and drop only your own unused previews, preserving user panels.

Source exports `register(on,options)`. For UI register `on('ui.render',{component:'Pane'},async($,e)=>...)`, resolve factories with `await $.ui.resolve(e)`, return `{tree:Box({children:[Text({text:'...'}),Button({key:'stable',label:'...',onPress:()=>...})]})}`. Input callbacks receive committed strings, not DOM events. Closure state survives renders. Timers start in session.start, use `$.clock.every/after`, and invalidate via `$.ui.invalidate('ui.render')`; cancel them in session.end. Visual instances allow UI, local JSON store and clock, but not network, filesystem, models or tools.

Async callbacks must return or await every store write and invalidation: `onPress:async()=>{await save();}` or `onPress:()=>save()`. A fire-and-forget action outlives its completed Hook and is refused; fix the promise chain rather than bypassing lifetime guards.

Source components can also reuse published children: declare `components:{Row:{id:'published-row',version:1}}` in the definition, resolve `Component` from `$.ui.resolve(e)`, and emit `Component({key:stableItemId,component:'Row',props:{...}})`. Keys must be unique per alias in each parent instance. Dependencies remain pinned and each occurrence has independent state, timers and schema validation. This supports arbitrary source computations for list creation/reordering without duplicating the child component's code.

Nodes accept `props.style` with validated JSON flex/grid layout, sizing, spacing, color, borders and typography. No arbitrary HTML, browser scripts, selectors or fixed positioning. Charts/custom artwork can use Svg as an image document, or Image/Raster with real raster URLs. Use available image-generation or asset tools when needed; do not invent asset URLs.
