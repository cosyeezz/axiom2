## Appearance Mods

### Choose The Distribution Shape

A skin is data, but can be supplied by the same Mod as its functionality. For a shareable appearance or combined functional/appearance Mod, declare `theme` and call `ctx.theme.register(localId,UiSkin)` in apply; the ordinary Mod package carries the definition and optional owned CSS/slots. Registration only makes the theme available. Select it through `theme.select(localId)` when the user explicitly chooses it or has authorized application-wide restyling. Do not create a separate saved JSON skin just because a Mod has UI. Ordinary Mods inherit the native current appearance and language; see the browser reference.

Use standalone `skinSave`/JSON import for a user-owned palette/background, an explicitly requested independent preset, or a data-only copy of a contributed theme. This format shares the definition only, not its owner's CSS, slots or interactions. Export the whole Mod package when those are needed to reproduce the experience. A contributed theme is owned by its installed Mod lifecycle, while the user's saved selection, personal overrides and panel placements are host configuration, not package source. Do not migrate/delete existing saved skins or claim a new unified storage format is implemented.

### Art Direction And Surface Quality

For an explicitly illustrated skin, distinguish four layers: a clear background image, a localized readability veil, actual control surfaces, and separate decorative/foreground assets. A screenshot of a finished interface is a composition reference, not wallpaper: it includes UI chrome and baked-in text. Do not approximate detailed lace, ribbons, ornamental corners or characters with repeated generic borders or tiny stretched assets. Use suitable raster/transparent assets or the user's supplied artwork; keep them scoped to this Mod's actual native surfaces. Report missing assets rather than claiming that palette changes reproduce them.

Preserve the scene's focal point and reserve clear space for chat/composer. Navigation can stay nearly opaque even when the chat stage is clear. Set independent `sidebarOpacity`, `composerOpacity`, `messageOpacity` and `menuOpacity` instead of lowering a parent element's CSS opacity; text/icons must remain opaque. Blur readable surfaces only, not the wallpaper or foreground figures. Broad blur on multiple nested full-window layers is costly and muddies the image. The same background is shared across modes, so dark controls do not require darkening all artwork.

Use native material tokens that actually have consumers: `--shadow-composer` for input elevation, `--surface-panel-border` for navigation/composer edges, `--surface-panel-shadow` for navigation/workspace elevation, and `--surface-backdrop-saturation` for blurred surface color (start near 100%). Inspect current tokens first and provide both modes. Restraint matters: one coherent frame around a region, not an ornamental box around every button. Detailed edge textures need owned CSS/asset layers, not invented JSON skin fields. Prefer surface-local pseudo-elements or brand artwork slots; `app.overlay` is for genuine global decoration. Decoration must be pointer-transparent, hidden from accessibility, and leave native focus, scrolling and controls intact.

Validate the same composition with an empty chat, long messages, an expanded composer, menus and compact/mobile navigation in light and dark. Check readable text over the busiest part of the image, visible hover/focus/disabled states, no content overlap, and restoration after stopping the Mod. Foreground illustrations should shrink, move or disappear on narrow layouts instead of covering controls. Ordinary functional Mods still inherit the native style; these rules do not authorize application-wide restyling unless requested.

Use `Mods skinContract` before writing and `skinList` to read the selected saved definition. `skinSave {request:{id,definition,revision?}}` uses the skin's latest revision; `skinApply {request:{id,revision}}` and `skinDelete {request:{id,revision}}` use the registry revision. Save does not apply. `skinApply` with `id:null` restores default appearance; deletion of the active saved skin also restores default without deleting panels or business data. Users can do these actions directly, with AI approval checks retained for model-initiated changes.

All appearance discovery is source-free. The user may not have a repository checkout, so do not inspect `SkinService`, host files, generated bundles or filesystem paths. If `skinContract` is large, query its summary and the one named section needed for the next operation rather than reading or reconstructing the implementation. For live token names use `Mods inspectList` followed by `Mods inspectQuery` with `{platform:'client',provider:'Theme',method:'listTokens',input:{}}`; `Theme.listTokens` is not a separate top-level tool. Model-authored `skinSave` calls must use a user-supplied `http(s)` image URL or omit the image and tell the user to use native file import; never paste a large `data:image/...;base64` string or write the registry directly.

Only one whole skin is selected. Saved skin selection is Gateway-global. A user's Mod Center selection of a contributed skin is remembered by namespaced identity across reloads; the approved package must register it before it can apply. A Mod's own `theme.select` call is temporary and lifecycle-owned. Registration is not application. Stop withdraws visuals, not saved definitions or user business data. Do not stop a functional owner merely to deselect its skin. For background and palette changes preserve the rest of the current skin; for layout and interactions use a client Mod instead of expanding the skin schema.

Standard installed skin packages can inject `assets` and keep artwork in `assets/` instead of large base64 JSON imported into JavaScript. `assets.read(path,{signal?})` returns a Blob; `assets.url` returns an owned Blob URL and `assets.release(url)` frees it early. Per-file limit is 8 MiB; retained URLs are bounded to 64 / 32 MiB per Mod. Images from that same live asset service may be registered as `background.image` or `welcome.image`; foreign and released Blob URLs are rejected. Saved JSON skins still reject Blob URLs. Keep URLs alive while their theme uses them. Start loading in an owned effect/component with cancellation and late-result checks; do not make `apply` async. Stop releases all URLs and reads. Scripts/HTML/SVG are not resource types. Authored function bodies must first be exported and installed as a standard package to carry binary assets. No asset endpoints or package hashes belong in model prompts; use the public service.

Deselecting a contributed theme restores the user's saved appearance; it does not clear the saved selection. Restoring the default appearance is a separate explicit action. Saved appearance deletion uses its own revision-protected operation and leaves functional Mods, mounts and business data intact. Contributed appearance is managed through its owner rather than a standalone saved-skin delete.

Skin definition: `{name,description,light,dark,tokens?,font?:'system'|'mono',radius?:0..24,background?,welcome?}`. Palette keys are existing semantic tokens such as bg-primary/bg-secondary/bg-input/bg-card, text-primary/text-secondary, accent-brand/accent-brand-foreground/accent-blue, border-default/focus-ring. For whole-app skins inspect the supported palette and current definition; incomplete palettes leave default surfaces behind.

`tokens:{light:{'--design-variable':'CSS value'},dark:{...}}` opens typography, spacing, column width, shadows and custom component design variables. `Theme.listTokens` provides current native variables and variables declared by active Mods; use those names before inventing new ones. New variables affect only CSS that consumes them. Pair the same keys across light/dark. Native examples include `--shadow-composer`, `--conversation-content-max-width`, `--skin-font`, `--skin-radius` and `--font-mono`; keep controls readable and layouts responsive. Values are bounded CSS values such as quoted font families, lengths, shadows, var/calc/clamp and color functions, not CSS declarations, selectors, URLs or executable markup. Background image and opacity remain structured `background` fields. Layout replacement or new interaction needs a client Mod, not a fake data-only skin. All theme contributions use the existing painter and are withdrawn on stop; do not insert a second root-variable writer.

Background: `{image,size:'cover'|'contain'|'tile',position:'center'|'top'|'bottom'|'left'|'right',opacity,overlay,overlayOpacity,panelOpacity,chatOpacity?,sidebarOpacity?,composerOpacity?,messageOpacity?,menuOpacity?,settingsOpacity?,surfaceBlur?}`. Opacities are 0..1; blur is 0..24 pixels. Keep image visibility, surface tint and blur separate. Settings opacity is independent of messages. Welcome is `{mode:'default'|'hidden'|'image',image?}`. Use verified/user-provided image assets, preserve unrelated palette/background choices, and preview both themes and small screens.
